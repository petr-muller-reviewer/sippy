## Summary

Replaces `go-git` clone of `openshift/api` in the feature gate loader with GitHub Contents API calls (~3m10s -> ~7s), switches DB writes from GORM `CreateInBatches` to pgx COPY-into-temp-table + `INSERT ... ON CONFLICT` (via pre-existing `db.CopyToTempTable` helper), and drops `go-git` + 16 transitive deps (~117k vendored lines).

Since previous review: the loader was reworked to use the shared `pkg/dataloader/prowloader/github` GitHub client (GitHub App / PAT auth, exposed via new `Client.APIClient()`) instead of a hand-rolled `net/http.Client` reading `GITHUB_TOKEN` directly. This resolves the earlier "duplicate client" finding. It also dropped the download-host allowlist; on reflection that's a minor defense-in-depth regression rather than an exploitable issue, since `download_url` is generated entirely by GitHub's own API, not by repo content. CodeRabbit reviewed the new commit, raised two findings, both investigated and withdrawn, and approved.

## Findings

### [should-fix] No functional test for the new COPY/upsert SQL path
- where: `pkg/dataloader/featuregateloader/featuregateloader.go` (`upsertFeatureGates`)
- concern: This is new SQL (raw COPY + `INSERT ... ON CONFLICT`) that has not previously run in production. The project's convention (see `releasesync_functional_test.go`) is to cover DB-touching code with a functional test that skips unless credentials/env vars are supplied, rather than relying solely on manual staging verification. None exists for this path. Unchanged across commits.
- excerpt: |
    cleanup, err := db.CopyToTempTable(l.ctx, conn, "tmp_feature_gates", featureGates, featureGateTempCols)
    ...
    upsertTag, err := conn.Exec(l.ctx, `
        INSERT INTO feature_gates (release, topology, feature_set, feature_gate, status, created_at, updated_at)
        SELECT release, topology, feature_set, feature_gate, status, NOW(), NOW()
        FROM tmp_feature_gates
        ON CONFLICT (release, topology, feature_set, feature_gate) DO UPDATE SET
            status     = EXCLUDED.status,
            updated_at = NOW()
    `)

### [should-fix] GITHUB_TOKEN auth path still undocumented
- where: `pkg/dataloader/prowloader/github/github.go:159-177` (`newGHAuthClient`), now also exercised by `featuregateloader.New`
- concern: `GITHUB_TOKEN` (and the GitHub App credential env vars behind `newAppTokenSource()`) are pre-existing, undocumented config — not new in this PR — but this PR is what makes the feature-gate loader's correctness/rate-limit behavior depend on them for the first time. Neither `config/README.md` nor root `README.md` mentions `GITHUB_TOKEN`. Worth a doc note now that a second consumer depends on it.
- excerpt: |
    token := os.Getenv("GITHUB_TOKEN")

### [nit] Download request now carries GitHub credentials to a host GitHub itself names, with no local validation
- where: `pkg/dataloader/featuregateloader/featuregateloader.go:151-167` (`downloadFile`)
- concern: Before commit `2b9219966`, `downloadFile` checked `downloadURL` against a fixed host allowlist (`raw.githubusercontent.com`, `objects.githubusercontent.com`) and sent an unauthenticated request. Both are gone: the request now runs via `l.ghClient.Client().Do(req)`, a copy of the same `http.Client` whose `oauth2.Transport` attaches the GitHub App/PAT token to every request it makes regardless of host. In practice `download_url` is generated entirely by GitHub's own Contents API response, not by repo content, so exploiting this would require GitHub's own infrastructure being compromised or MITM'd (TLS cert validation already rules out the latter) — not something an attacker with only repo-write access to `openshift/api` could trigger. Downgraded from should-fix after discussion: this is a least-privilege / defense-in-depth loss (unnecessary credential exposure surface, no protection if this code is later reused for a less-trusted source), not a currently exploitable issue.
- excerpt: |
    resp, err := l.ghClient.Client().Do(req) //nolint:gosec // URL comes from GitHub Contents API response

## Resolved

### [resolved] New GitHub client duplicated and bypassed existing rate-limit-aware client
- was: `pkg/dataloader/featuregateloader/featuregateloader.go` used a hand-rolled `net/http.Client` reading `GITHUB_TOKEN` directly, with no rate-limit awareness, duplicating `pkg/dataloader/prowloader/github/github.go`'s existing GitHub App/PAT-authenticated client with `RateLimits()`/`IsWithinRateLimitThreshold()`.
- resolution: commit `2b9219966` adds `Client.APIClient()` to `prowloader/github` and threads that shared `*gh.Client` into `featuregateloader.New(ctx, dbc, ghc, releaseConfigs)` (wired in `cmd/sippy/load.go:362-363`). Listing now uses `ghClient.Repositories.GetContents`. Both loaders now share one auth path and one rate-limit budget.

### [resolved] `//nolint:gosec` lacked rationale comment
- was: suppression on `doGet`'s `l.httpClient.Do(req)` had no comment explaining why the variable URL was safe.
- resolution: the equivalent line now reads `//nolint:gosec // URL comes from GitHub Contents API response`.

### [resolved] GitHub auth header used legacy `token` scheme
- was: manual `req.Header.Set("Authorization", "token "+l.githubToken)`.
- resolution: auth is now handled entirely by the shared `oauth2.NewClient`-based transport in `prowloader/github`; the loader no longer sets `Authorization` manually.

## Checked

- `parseFeatureGateFilename` regex reproduces old suffix-splitting behavior exactly for both legacy and versioned filenames; unaffected by the latest commit.
- `dbErr` guard before constructing the feature-gate loader in `cmd/sippy/load.go` is consistent with every other loader branch in that function.
- Partial-failure handling improved in the latest commit: `fetchFeatureGatesForBranch` now appends to `l.errs` and `continue`s on download/unmarshal errors instead of aborting the whole branch — a single bad file no longer drops the rest of that release's feature gates.
- `db.CopyToTempTable` (pre-existing, untouched) validates identifiers via regex before use in raw SQL.
- Composite unique constraint / upsert semantics preserved from the old GORM `OnConflict` logic; the ON-CONFLICT cardinality-violation behavior on duplicate keys is an intentional data-integrity signal per author's response to CodeRabbit, not a bug.
- Verified independently that `(*github.Client).Client()` exists in `vendor/github.com/google/go-github/v45/github/github.go:212` — CodeRabbit's initial claim that the call was invalid was incorrect, and it correctly withdrew after the author's pushback.
- `download_url` from the GitHub Contents API is generated by GitHub's backend, not derived from repo file content — ruling out a repo-write-access attacker as a source of a malicious download host.
- Storing `ctx context.Context` on the `FeatureGateLoader` struct remains fine — `DataLoader.Load()` takes no arguments; this is the package's established convention.
- No reviews/comments beyond the CodeRabbit exchange and CI status; CodeRabbit's final state is `APPROVED`. PR remains open, not merged.
