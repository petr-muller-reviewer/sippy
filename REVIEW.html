Verdict

Request changes

The async architecture (River + batch tracking + status polling) is sound and reasonably tested, but the core execution path is broken: the daemon-side ReEvaluator used by the River worker never has its symptom cache populated, so every async re-evaluation job will fail with "symptom cache not initialized". That's a functional showstopper that must be fixed before merge; the remaining findings are real but lower severity.

What this PR does

  • Moves POST /api/jobs/runs/reevaluate from synchronous execution to an async batch workflow — non-dry-run requests are enqueued as River (Postgres-backed queue) jobs processed by sippy-daemon.
  • Adds pkg/sippyserver/workqueue (Submitter, StatusQuerier) plus a migration for workqueue_batches/workqueue_batch_items to track batch/item state against River job rows.
  • Wires a River worker (ReevaluateWorker) into sippy-daemon that delegates to the existing jobrunscan.ReEvaluator.reEvaluateOne logic.
  • Adds GET /api/jobs/runs/reevaluate/{batch_id} for polling batch status (counts + per-item state).
  • dry_run requests keep the old synchronous path, otherwise unchanged.

Findings

Blocking

Blockingasync ReEvaluator's symptom cache is never populated in sippy-daemon

cmd/sippy-daemon/main.go:202, pkg/api/jobrunscan/reevaluate_worker.go:52-60

setupRiverProcess() constructs evaluator := jobrunscan.NewReEvaluator(...) and registers NewReevaluateWorker(evaluator), but nothing ever calls evaluator.RefreshSymptomCache() on it. RefreshSymptomCache() is only invoked on a separate, short-lived ReEvaluator created in reEvaluateAsync just to compute a dedup hash, then discarded. ReevaluateWorker.Work calls w.evaluator.CachedSymptoms(), which is nil on the daemon's evaluator — every job fails with "symptom cache not initialized", and after MaxAttempts=3 the whole batch ends up failed/discarded. As wired, no async re-evaluation job can ever succeed.

// cmd/sippy-daemon/main.go
evaluator := jobrunscan.NewReEvaluator(bqClient, gcsClient, f.GoogleCloudFlags.StorageBucket, dbc, cacheClient, artifactMgr, false)
workers := river.NewWorkers()
river.AddWorker(workers, jobrunscan.NewReevaluateWorker(evaluator))
// no RefreshSymptomCache() call anywhere on `evaluator`

// pkg/api/jobrunscan/reevaluate_worker.go
func (w *ReevaluateWorker) Work(ctx context.Context, job *river.Job[ReevaluateJobRunArgs]) error {
    symptoms := w.evaluator.CachedSymptoms()
    if symptoms == nil {
        return fmt.Errorf("symptom cache not initialized")
    }

Should fix

Should fixasync path skips per-ID validation

pkg/sippyserver/job_run_scan.go:223-236

reEvaluateSynchronous calls apijobrunscan.ValidateReEvalRequest(buildIDs) before doing any work. reEvaluateAsync only checks the batch is non-empty and under MaxJobRunsPerBatch — it never validates individual build IDs. A non-numeric ID is accepted, enqueued as a River job, and only fails later inside the worker/BigQuery query, burning a queue slot and surfacing as an opaque per-item failure instead of an immediate 400.

if len(buildIDs) == 0 {
    failureResponse(w, http.StatusBadRequest, "prow_job_build_ids is required")
    return
}
if len(buildIDs) > apijobrunscan.MaxJobRunsPerBatch {
    failureResponse(w, http.StatusBadRequest, fmt.Sprintf("maximum %d job runs per batch", apijobrunscan.MaxJobRunsPerBatch))
    return
}
// no ValidateReEvalRequest(buildIDs) call here

Should fixbuildBatchItems pairs River job IDs to item keys purely by array index

pkg/sippyserver/workqueue/submitter.go:56, 73, 105-115

s.riverClient.InsertMany(ctx, items) returns results that buildBatchItems zips against itemKeys by position. This assumes River's underlying bulk INSERT ... SELECT FROM unnest(...) ... ON CONFLICT ... RETURNING (no ORDER BY) preserves input order in its output — true today for the vendored implementation, but an implicit contract on an unordered SQL statement rather than something the River client documents or enforces. If it doesn't hold, a batch item silently reports the wrong build's re-evaluation state.

func buildBatchItems(batchID uuid.UUID, results []*rivertype.JobInsertResult, itemKeys []string) []BatchItem {
    items := make([]BatchItem, len(results))
    for i, r := range results {
        items[i] = BatchItem{
            BatchID:    batchID,
            RiverJobID: r.Job.ID,
            ItemKey:    itemKeys[i],
        }
    }
    return items
}

Nits

Nitbatch status response has no HATEOAS links

pkg/sippyserver/workqueue/status.go:21-30, pkg/sippyserver/job_run_scan.go:264-288

Project convention requires HATEOAS in API responses. The sync re-eval response is annotated via InjectReEvalHATEOASLinks, and the batch-submit response includes a manual links.status, but jsonReEvaluateBatchStatus returns the raw BatchStatusResponse with no links field — a client polling status has no self/related links.

type BatchStatusResponse struct {
    BatchID   uuid.UUID    `json:"batch_id"`
    Status    BatchStatus  `json:"status"`
    Total     int          `json:"total"`
    Completed int          `json:"completed"`
    Failed    int          `json:"failed"`
    Running   int          `json:"running"`
    Pending   int          `json:"pending"`
    Items     []ItemStatus `json:"items"`
    // no links field
}

Things I checked and was fine with

  • dry_run path (reEvaluateSynchronous) is unchanged and still validates input and injects HATEOAS links.
  • Submitter.Submit correctly enqueues River jobs before creating batch/item tracking rows, with a documented harmless-orphan-jobs failure mode if the transaction fails.
  • River job uniqueness (ByArgs + ByPeriod via ProwJobBuildID+SymptomHash) looks sound for dedup semantics.
  • Migration for workqueue_batches/workqueue_batch_items not reviewed for schema-level issues beyond existence.

Open questions for the author

How was the async path tested end-to-end, given evaluator.RefreshSymptomCache() is never invoked on the daemon's ReEvaluator? Did any test exercise ReevaluateWorker.Work against a live symptom cache, or only in isolation with a pre-populated cache?
Is the per-index pairing in buildBatchItems guaranteed by River's InsertMany API contract, or would it be safer to key off something returned per-item instead of relying on SQL fetch order?
