Code Review

Verdict: Approve

Clean, well-scoped simplification. Moving Synthetic into the YAML config is the right call — the config is already the authoritative source for everything else about these releases, and the BigQuery dependency was purely incidental. The change is mechanically correct, all call sites are updated, no API consumers break, and test coverage is thorough. One renamed test case has a misleading name (nit only); nothing blocking.

What this PR does

  • Adds Synthetic bool to v1.ReleaseConfig and marks all 12 synthetic releases with synthetic: true in openshift-customizations.yaml (and the regenerated openshift.yaml).
  • Simplifies BuildSyntheticReleaseJobOverrides by removing the releaseConfigs []sippyv1.Release parameter — the function now reads releaseCfg.Synthetic directly from the config map.
  • Removes Synthetic from sippyv1.Release and sippyv1.ReleaseRow (the cached and BigQuery types), eliminating the BQ column dependency.
  • Strips GCP/BigQuery flags from VariantSnapshotFlags and the make update-variants Makefile target, so developers can run it without credentials.
  • Regenerates openshift.yaml locally — a preview that includes changes from the companion ci-tools PR #5210, which will be overwritten by the next generator run.

Things I checked and was satisfied with

  • API field removal is safe. sippyv1.Release.Synthetic was the only non-test consumer of the field, mapped via transformRelease() in pkg/api/releases.go:481. The frontend (sippy-ng/src/) has zero references to Synthetic. No downstream breakage.
  • All call sites updated. cmd/sippy/load.go, cmd/sippy/variants_generate.go, cmd/sippy/variants_snapshot.go, and both test files all consistently drop the releaseConfigs argument.
  • All 12 synthetic releases present. aro-integration, aro-stage, aro-production, aro-classic-integration, aro-classic-stage, aro-classic-production, rosa-stage, rosa-integration, rosa-production, rrp-integration, automation, ocp-hypershift — all marked in openshift-customizations.yaml and reflected in openshift.yaml.
  • aro-classic-* snapshot fixes are correct. The periodic aro-classic-{integration,stage,production} jobs in snapshot.yaml gain a Release: field (previously absent, meaning they weren't attributed to any synthetic release) and their JobTier changes from candidate to standard. Both are correct outcomes of synthetic release attribution now working.
  • TestVariantsSnapshot dependency is sound. The test reads the committed openshift.yaml from disk. Since that file has been regenerated with synthetic: true entries for all synthetic releases, the test validates the correct merged state.
  • No dead code. The deleted syntheticReleaseNames() helper had no callers outside the now-changed function. Clean removal.
  • openshift.yaml regeneration is documented. The PR description explicitly states it's a preview of ci-tools PR #5210 changes and will be overwritten on the next generator run. This is standard operating procedure for this repo.

Open questions for the author

  • TestVariantsSnapshot now depends on synthetic: true being present in the committed openshift.yaml. If someone regenerates that file before the ci-tools companion PR ships (and the generator doesn't yet emit synthetic: into the YAML), the test would still pass but with different semantics — synthetic releases wouldn't be attributed correctly at runtime. Is there a CI check or generator enforcement that would catch this gap? (Not a blocker given the companion PR is linked and the generator will emit the correct content once both merge.)
