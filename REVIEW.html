Verdict

NEEDS DISCUSSION

No correctness or safety bugs found that would block merge outright, but the PR (still labeled WIP) is missing test coverage on the two riskiest new mechanisms — the BQ/PG dispatch and the variant key encoding — plus a documentation update for a user-facing default change. Worth resolving before it comes off WIP.

What this PR does

  • Adds a dataSource query param and cookie-based UI toggle to route Component Readiness requests to BigQuery or PostgreSQL per request.
  • Rewrites the PG test-status query as a prefix-sum over test_cumulative_summaries, with SQL-level variant grouping via VALUES-clause joins, replacing per-row Go-side filtering.
  • Adds GA base-window routing (1/30/90 day) to a pre-computed prow_ga_raw_test_data table, and fixes a planner regression in test_details via a MATERIALIZED CTE.
  • Migrates TestStatus.Variants from []string to map[string]string, adds a deterministic null-byte-separated Encode()/DecodeColumnID() key scheme, and indexes FindOpenRegression by testID for O(1) lookup.
  • Merges CompareVariants into IncludeVariants for PG cross-compare parity, and bumps the UI's default base window from 27 to 30 days.

The PR description documents several accepted BQ/PG parity gaps (lastFailure scoping, InfraFailure inclusion, lifecycle filter, job scope) — those are not re-flagged here.

Findings

Should fix

should-fixEncodeVariants not provably collision-free
pkg/apis/api/componentreport/crtest/types.go:116-133
pairs = append(pairs, key+":"+value)
...
strings.Join(pairs, "\x00")

Keys/values aren't escaped for : or embedded \x00. Two distinct variant maps can encode identically (e.g. {"A":"B:C"} vs {"A:B":"C"}), and a value containing a literal null byte would corrupt DecodeColumnID's split. Low likelihood given the fixed variant vocabulary, but unenforced and untested.

should-fixBase window default change (27→30 days) undocumented
sippy-ng/src/component_readiness/CompReadyVars.jsx, ReleaseSelector.jsx

Applied consistently in both files, but this is a user-facing default behavior change and isn't mentioned in README.md or sippy-ng/README.md, contrary to project convention for documenting config/behavior changes in the same PR.

should-fixmixed provider dispatch has no test coverage
pkg/api/componentreadiness/dataprovider/mixed/provider.go

providerFor's BQ/PG routing is the core mechanism this PR introduces, yet there's no test file for the mixed package. queryparamparser_test.go also lacks a case for parsing dataSource.

should-fixNo test pinning DataSource in fallback cache key
pkg/api/componentreadiness/middleware/releasefallback/releasefallback.go:337,352

fallbackTestQueryReleasesGeneratorCacheKey appears to include DataSource, but nothing verifies this in a test. If it were ever dropped, BQ and PG requests could collide in cache and silently serve the wrong source's data.

Nits

nitShared mutable variant map aliased across TestStatus rows
pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:416-436

scanRows sets ts.Variants = variantMap, reusing the same map instance for every row in a variant group. No current mutation path found, but it's a latent hazard if any future code mutates TestStatus.Variants in place. Consider maps.Clone or a comment documenting the shared-ownership invariant.

nitGA window boundary logic untested directly
postgres/cr_queries.go:203, postgres/provider.go:230-257

baseMatchesGAWindow (1/30/90-day detection) and its re-derivation of windowDays in queryBaseTestStatusGA are algebraically consistent but only exercised transitively — no direct unit test for boundary conditions.

nitEncode/Decode roundtrip tests only cover alphanumeric values
pkg/apis/api/componentreport/crtest/types_test.go

No test covers colon- or null-byte-containing values — exactly the scenario the encoding's collision-freedom depends on.

nitInvalid dataSource silently falls back to BigQuery
pkg/util/param/param.go:67, utils/queryparamparser.go:93-95

Invalid values are logged and reset to "" rather than surfacing a 400, inconsistent with how other params reject invalid input. Low impact since the regex allowlist already blocks garbage before it's user-visible.

Things I checked and was fine with

  • SQL construction: all user-controlled variant keys/values go through ? placeholders; only integers are fmt.Sprintf'd into VALUES clauses — no injection risk.
  • Prefix-sum date-range math (AddDays(-1) half-open interval convention) traced correctly across sample/GA/placeholder query call sites.
  • FindOpenRegression testID indexing: correct (it's a pre-filter, not the full match), no collision risk, well tested.
  • Cookie-based dataSource UI toggle: written only from hardcoded constants, validated server-side by regex, safe default on missing/corrupt cookie.
  • Provider interface parity (BigQuery/Postgres/Mixed): verified via build and interface assertions.
  • HATEOAS: dataSource correctly propagated into generated links, covered by tests.
  • TestStatus.Variants type change: safe, that struct is internal-only and never crosses the API/cache boundary directly.
