Verdict: Request changes

The partition-pruning approach (adding prow_job_release and timestamp-window filters so Postgres can skip partitions) is sound and consistent with the stated goal (trt-2709). However, two of the narrowed queries change externally-visible behavior in ways that look unintentional: a UI-facing "last pass" timestamp and a fallback threshold used in release-comparison logic. Both should be confirmed with the author before merge.

What this PR does

  • Adds prow_job_release and/or timestamp-range filters to several queries across pkg/db and pkg/api so Postgres can prune to relevant partitions instead of scanning all of them.
  • Replaces an unbounded run-count lookup (ProwJobRunIDs) with a new ProwJobRunCount that counts within a fixed recent window.
  • Narrows the job_results SQL function's last-pass computation to the reporting window instead of the whole release history.
  • Scopes a job-run count metric to the current active release, pulled via a new CurrentActiveRelease helper.

Since previous review (63c97d78 → f96c187a): mstaeble flagged integration test failures in review comments (2026-08-18); author pushed 2 commits to fix them.

  • ProwJobRunCount and HasBuildClusterData now take an explicit since time.Time instead of hardcoding the interval inline — call sites still pass time.Now().Add(-14*24*time.Hour), so effective behavior is unchanged.
  • CurrentActiveRelease now returns an error instead of ("", nil) when release_definitions has no match.
  • LookupProwJobRunPartitionKeys now returns gorm.ErrRecordNotFound on a missing row instead of a zero-value struct.
  • Integration tests updated to match; CI (/test e2e) now passes. PR is still open.

Findings

Blocking

Blockingjob_results last_pass window narrowed

pkg/db/functions.go:122-126

lp AS (
    SELECT prow_job_runs.prow_job_id, max(prow_job_runs.timestamp)::timestamp without time zone as last_pass
      ...
      AND prow_job_runs.timestamp BETWEEN p_start AND p_endstamp

The lp CTE computing last_pass is now bounded to the reporting window (p_start..p_endstamp) instead of the full release history. A job that last passed outside that window now reports last_pass = NULL instead of the true timestamp — this is user-visible as the "Last pass" column in the Jobs UI.

BlockingProwJobRunCount hardcoded 14-day window breaks fallback threshold

pkg/db/query/job_queries.go:69-78 & pkg/api/job_runs.go:583

Status as of f96c187a: unresolved. Refactored to accept a since time.Time param (commit a6f4b5a77, improves testability), but the only call site still passes time.Now().Add(-14*24*time.Hour) — effective query window is unchanged.

func ProwJobRunCount(dbc *db.DB, prowJobID uint, release string, since time.Time) (int, error) {
	var count int64
	q := dbc.DB.Table("prow_job_runs").
		Where("prow_job_id = ?", prowJobID).
		Where("prow_job_release = ?", release).
		Where("timestamp > ?", since)

// pkg/api/job_runs.go:583
runCount, err := query.ProwJobRunCount(dbc, job.ID, compareRelease, time.Now().Add(-14*24*time.Hour))
...
if totalJobRuns < 20 {
    // falls back to comparing against the prior release

ProwJobRunCount is still effectively scoped to the last 14 days (previously an all-time count via ProwJobRunIDs). Its summed result feeds a totalJobRuns < 20 check in findReleaseMatchJobNames that triggers a fallback to the prior release. A job with hundreds of historical runs but fewer than 20 in the last 14 days will still spuriously look data-starved and trigger that fallback — a behavior change unrelated to partition pruning.

CurrentActiveRelease errors (or previously, returned ("", nil)) when release_definitions has no matching row (e.g. an under-populated dev/seed DB). The code only logs and continues. Open questions for the author

  • For job_results.last_pass: was bounding it to the reporting window intentional, or should it stay unbounded and accept the wider partition scan?
  • For ProwJobRunCount: now that the window is parameterized, should the findReleaseMatchJobNames call site pass a wider (or all-time) since rather than 14 days, given the result feeds a < 20 threshold that assumed all-time counts?
  • For cluster autocomplete: should the now-explicit error from CurrentActiveRelease be propagated as an error response instead of logged-and-ignored?
  • For tests.go: was narrowing jobRunsCount to the current release intentional? If so, should testIDsCount be narrowed to match, or should the metrics be documented as differently scoped?
