What this PR does

  • Replaces prow_job_runs_report_matview (~90s refresh) with a two-phase live query in JobsRunsReportFromDB (pkg/api/job_runs.go): phase 1 paginates prow_job_runs JOIN prow_jobs with conditional PR joins; phase 2 enriches the returned page (test-name arrays, PR data, annotations) concurrently via errgroup.
  • test_failures/test_flakes read directly from stored columns on prow_job_runs (populated at insert time by the prow loader, TRT-2834) instead of a runtime CTE.
  • Refactors pkg/filter: exports FilterItemToSQL/FilterFieldToSQL replacing unexported orFilterToSQL/andFilterToSQL; Filter.ToSQL now uses FilterFieldToSQL uniformly for AND and OR link operators.
  • Consolidates ILIKE wildcard escaping into exported filter.EscapeLikeMetachars, applied at all 12 ILIKE-pattern-construction sites — fixes previously-unescaped %/_ in user filter values acting as SQL wildcards.
  • Adds a 1387-line integration test suite (test/integration/job_runs_report_test.go): pagination (incl. tied-sort-key and no-sort determinism), all filter operators/dispatch paths, sorting, test-name EXISTS-subquery filters, PR/annotation enrichment, multi-PR dedup, unsortable-field rejection.
  • Adds sortable: false to hidden test-name array columns in the frontend, paired with a backend ValidationError for unsortable sort fields.

Findings

nitFilterItemToSQL OperatorIsEmpty is not array-aware

pkg/filter/filterable.go:771-776 (new FilterItemToSQL, OperatorIsEmpty/OperatorIsNotEmpty cases)

Unlike FilterFieldToSQL's isEmptyFilter (which special-cases arrays with IS NULL OR ARRAY_LENGTH(...) = 0), FilterItemToSQL emits a plain "%s IS NULL"/"%s IS NOT NULL". Documented as intentional in the doc comment ("no type-aware transformations... use FilterFieldToSQL when the column may be an array"). None of the current columnAliases callers are array-typed, so it's not a live bug — but a future caller adding an array-typed alias and using isEmpty/isNotEmpty would silently get wrong results.

case OperatorIsEmpty:
    sql = fmt.Sprintf("%s IS NULL", column)
case OperatorIsNotEmpty:
    sql = fmt.Sprintf("%s IS NOT NULL", column)

question%q-based identifier quoting reachable from job-runs filters

pkg/filter/filterable.go (FilterFieldToSQL), reached via pkg/api/job_runs.go (applyJobRunFilters fallback branch)

field := fmt.Sprintf("%q", f.Field) quotes a client-supplied filter field name using Go string-escaping, not SQL identifier-escaping. Pre-existing pattern, not introduced here, but now also reachable from the new job-runs filter path for any field not in columnAliases (e.g. cluster, labels, url). Worth confirming f.Field is allowlist-validated upstream before reaching this point.

Things I checked and was fine with

  • NOT/HasEntry semantics: old field IS NULL OR ? != ALL(field) vs new NOT(? = ANY(COALESCE(field,'{}'))) — verified equivalent for NULL and non-NULL cases; covered by new TestListFilteredJobIDs cases.
  • IsEmpty/IsNotEmpty NOT-wrapping in the FilterFieldToSQL path — truth table matches the old optNot(!f.Not) logic in orFilterToSQL, just expressed differently.
  • Duplicate-row fix for multi-PR-linked runs: DISTINCT ON(prow_job_run_id) ... ORDER BY prow_job_run_id, prow_pull_request_id DESC deterministically dedups, used consistently in both addPRJoin and enrichJobRunsWithPRData.
  • Pagination determinism: q.Order("prow_job_runs.id DESC") always appended after the user's sort field (GORM accumulates .Order() calls), acting as a tiebreaker. Exercised by TestJobRunsReport_PaginationStableWithTiedSortKey and TestJobRunsReport_PaginationDeterministicWithoutSort.
  • Conditional PR join wiring: joined pre-COUNT only when needed for filtering, post-COUNT when only needed for sorting; enrichment skips re-fetching PR data when already selected inline.
  • Concurrency safety of the 3 parallel errgroup enrichment functions writing disjoint struct fields of the same slice — safe under the Go memory model, no lock needed.
  • ILIKE-escaping fix applied consistently across all sites; all SQL parameterized via ? placeholders in both GORM .Where() and raw .Raw()/.Exec() calls; no string-interpolated user filter values found.
  • sets.New[string]() used per project convention; gofmt-clean; //nolint:gosec usage consistent with existing codebase patterns.
