Verdict

Approve

The fix is well-targeted and thoroughly tested: it closes a real PostgreSQL/BigQuery parity gap where tests below MinimumFailure that only existed on one side, or crossed the threshold between sides, were silently dropped instead of surfacing as MissingSample/MissingBasis. New integration tests cover all four quadrants (both above, one above/one below in each direction, both below, one-sided) plus a full end-to-end report test. No correctness issues found; remaining points are cleanup/design-quality and worth a comment but not blocking.

What this PR does

  • Fixes TRT-2883: PostgreSQL previously filtered out below-MinimumFailure tests at the SQL level, unlike BigQuery, causing one-sided or threshold-crossing tests to vanish from both result maps instead of showing as Missing*.
  • Standalone path (queryTestStatusCTE, feeds release-fallback) drops the SQL filter entirely — new testBranchTemplate replaces failureBranchTemplate — and relies on the existing Go-side check.
  • Combined path (queryCombinedTestStatus) keeps the per-side >= MinimumFailure filter and adds a new belowThresholdRescueBranchTemplate: a LEFT JOIN against a narrow materialized keysCTETemplate of the other side, rescuing rows with no counterpart or a counterpart at/above threshold.
  • minimumFailure removed from variantQuerySetup/prepareVariantQuery since only the combined path still needs it (passed directly as an SQL arg).
  • Integration tests: flipped an existing expectation (now correctly rescued), added both-below/one-sided coverage for the combined path, and extended TestGenerateReport_MinimumFailureThreshold with reverse-direction and both-below cases through full Fisher-exact analysis.

Findings

Should fix

Duplicated column list across three near-identical branch templates

pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:187-253

testBranchTemplate, failureBranchTemplate, and belowThresholdRescueBranchTemplate repeat the identical SELECT/FROM/JOIN column list, differing only in the WHERE clause / extra join. A future column change (e.g. for the row scanner) means editing three string constants in lockstep — miss one and you get a column-count/order mismatch that surfaces as a scan error or silently wrong data, not a compile failure.

const testBranchTemplate = `SELECT
    %spa.unique_id AS test_id, t.name AS test_name,
    COALESCE(su.name, '') AS test_suite, pa.component, pa.capabilities,
    pa.variant_group_id, pa.total_count, pa.success_count, pa.flake_count, pa.last_failure
FROM %s pa
JOIN tests t ON t.id = pa.test_id
LEFT JOIN suites su ON su.id = pa.suite_id`

Questions

Same invariant enforced via two independent mechanisms

cr_queries.go:274-310 (standalone) vs cr_queries.go:410-506 (combined)

The standalone path drops the SQL filter and relies solely on the Go-side check; the combined path keeps the filter and adds a bespoke rescue join. Both fix the same bug but share no code — a future change to MinimumFailure semantics needs updating both independently. Is this divergence intentional, or worth a shared test tying the two behaviors together as a guardrail?

queryTestStatusCTE now returns unfiltered base-side rows for release-fallback

cr_queries.go:274-310

queryTestStatusCTE feeds QueryBaseTestStatus, used by the release-fallback middleware, which caches per-release BaseStatus maps across fallback releases. Removing the SQL-side floor grows that result set (and the cache) to include all low-count tests. Not a correctness issue, but worth confirming this doesn't meaningfully increase fallback-cache memory for high-fanout scenarios.

Things I checked and was fine with

  • Argument-binding order for belowThresholdRescueBranchTemplate (two placeholders per side) matches the allArgs append order in queryCombinedTestStatus.
  • gofmt -l clean on the changed file.
  • BigQuery parity: BigQuery never had a SQL-side MinimumFailure filter, so this PR brings Postgres in line with BigQuery's existing behavior — no BigQuery-side change needed.
  • New integration tests cover all four quadrants (both above, each direction of one-above/one-below, both below, one-sided) plus a full report-level Fisher-exact test.
  • variantQuerySetup.minimumFailure field removal is fully reference-checked (only used by the now-removed standalone filter).

Open questions for the author

  • For large components/variant combinations, has the rescue join's plan cost against the materialized keys CTEs been compared to the old combined-query plan?
