Approve. High-quality proposal backed by real cost data, a correct diagnosis of the current query path, and experimental validation. The suggestions below are refinements worth addressing before implementation begins, but none block merging this planning document.

What this PR does

  • Adds a proposal document at docs/plans/bigquery-junit-clustering-proposal.md for clustering the 9.3-billion-row junit BigQuery table by a new release column.
  • Diagnoses that current release filtering happens post-scan via a JOIN to job_variants, costing ~$36K/month for ~55K queries.
  • Justifies a new release column over the existing branch column with a 4.55% mismatch analysis across four concrete failure categories of the regex-based branch derivation.
  • Includes experimental validation: a clustered copy of the table reduced a representative query from 214 GB to 70 GB (67% reduction), matching the theoretical prediction.
  • Projects $264K-$327K annual savings with a ~$6 one-time backfill cost.

Findings

should-fix Ingestion fallback to branch perpetuates mislabeling

docs/plans/bigquery-junit-clustering-proposal.md:289

release=get_release_for_job(self.prowjob_name) or self.branch,  # new field

The proposed ingestion code falls back to the regex-derived branch value for jobs not yet in the variant registry. The entire first half of the proposal demonstrates why branch is unreliable for release identification (4.55% mismatch). Falling back to it silently writes a potentially wrong release value into the clustered column. Using NULL would honestly mark unknown jobs and avoid clustering them into the wrong release block. Queries filtering on release = @SampleRelease would naturally exclude them, matching current behavior where unregistered jobs lack variant JOINs.

should-fix Ingestion gap during CTAS rebuild not mitigated

docs/plans/bigquery-junit-clustering-proposal.md:198-207

Tradeoff: Requires pausing the ingestion Cloud Function for 10-30 minutes
while the CTAS runs and the rename completes. Any junit data from Prow jobs
that complete during this window will be permanently lost — the ingestion
pipeline does not replay missed data.

The proposal acknowledges 10-30 minutes of permanent data loss but doesn't explore alternatives. For a $264K+/year savings initiative, the operational plan should describe whether the Cloud Function trigger can be disabled/re-enabled around the rename, or whether a two-phase approach (CTAS to junit_v2, then atomically switch readers while briefly pausing writes) could reduce the gap. Even a brief discussion of "we considered X but Y is simpler" would strengthen the proposal.

question Multi-release query savings estimate

docs/plans/bigquery-junit-clustering-proposal.md:155-167

Component Readiness compares a base release against a sample release. The code in querygenerators.go uses separate CTEs for base and sample scans, each filtering on its respective release. The savings estimate should confirm whether these are truly independent scans (each benefiting from clustering independently) or whether BigQuery might combine them. This affects whether the real-world savings match the single-release projections.

nit Cache staleness window not in risk table

docs/plans/bigquery-junit-clustering-proposal.md:319-327

The 6-hour cache TTL means a newly added job in the variant registry could produce junit rows with the fallback release value for up to 6 hours. This is a minor operational detail but fits naturally in the Risk Assessment table alongside the existing "stale values after variant registry fix" entry.

nit update_junit_release.py referenced but not listed as deliverable

docs/plans/bigquery-junit-clustering-proposal.md:329-350

The correction script is described in detail with usage examples but isn't listed in the "Implementation Sequence" section as an explicit step/deliverable. Adding it as step 5 or a sub-item of step 4 would make the full scope of work clearer.

Things I checked and was fine with

  • Current query path diagnosis is accurate. Verified in querygenerators.go: release filtering via jv_Release.variant_value = @BaseRelease (lines 79, 151) after a LEFT JOIN to job_variants (lines 388-389, 553-554). This confirms the "filter after full scan" claim.
  • @BaseRelease and @SampleRelease parameters exist and are used as the proposal describes throughout the query generators.
  • branch column exists in the junit data structures (pkg/api/tests.go) and is indeed regex-derived.
  • docs/plans/ directory already exists with other planning documents, so this follows an established pattern.
  • No code changes, zero operational risk from merging this PR as-is.
  • Cost projections are internally consistent. The 67% experimental reduction on release 4.22 (~34% of rows) aligns with the distribution data and the savings estimates.

Open questions for the author

  • For jobs not in the variant registry, should release be NULL rather than falling back to the regex-derived branch? This avoids silently mislabeling rows in the clustered column, which is exactly the problem the new column is designed to solve.
  • Has anyone estimated the actual ingestion gap duration during the CTAS rebuild? Could the Cloud Function trigger be paused/resumed programmatically to bound the data loss window?
  • Do Component Readiness queries scan the junit table once with both releases or twice independently? This affects whether the per-release savings estimates can be summed or must be combined differently.
