Needs Discussion — The middleware refactoring is well-executed and the spot-check concept is sound. Three issues need attention before merge: a cache key that omits the new SpotCheckJobSamples field (causing cross-request cache collisions), a default fallback that fires for 60 of 61 views and runs an unnecessary BigQuery scan on every component report, and a slice append that can mutate the caller's map entry. None are hard to fix, but the first two affect correctness and cost at scale.

What this PR does

  • Introduces spot-check jobs to Component Readiness: rarely-run CI jobs (cpu-partitioning, etcd-scaling) evaluated on a simple “did the job pass at least once in 30 days” heuristic, rather than per-test Fisher’s Exact analysis.
  • Adds SpotCheckComponent and SpotCheckCapability variant classification, a new spotcheck-30d job tier (with rare backward-compat fallback), and BigQuery queries to fetch job-level pass/fail data.
  • Implements a spotcheckjobs middleware that injects synthetic test results into the component report and claims analysis for spot-check tests via the new Analyze method.
  • Refactors the analysis pipeline: extracts assessComponentStatus into three middleware packages (NewTestPassRate, AllTestsPassRate, FisherExact) using a first-responder-wins Analyze(testKey, testStats) (bool, error) pattern on the middleware interface.
  • Frontend conditionally hides basis-related columns and stats for spot-check tests; view config gains spot_check_job_samples with per-tier time windows and variant filters.

Findings

Should Fix

should fix Cache key does not include SpotCheckJobSamples

pkg/api/componentreadiness/component_report.go:182-190

GeneratorCacheKey cherry-picks fields from RequestOptions but omits SpotCheckJobSamples. Two requests with identical base/sample releases and variants but different spot-check sample configurations (e.g., a view with explicit spotcheck-30d config vs one relying on the default fallback, or a future spotcheck-90d) produce the same cache key. The first cached result is silently returned for the second request, serving wrong spot-check data.

type GeneratorCacheKey struct {
    ReportModified *time.Time
    BaseRelease    reqopts.Release
    SampleRelease  reqopts.Release
    VariantOption  reqopts.Variants
    AdvancedOption reqopts.Advanced
    TestFilters    reqopts.TestFilters
    TestIDOptions  []reqopts.TestIdentification
    // SpotCheckJobSamples is missing
}

should fix Default SpotCheckJobSamples fallback causes BQ queries for 60 of 61 views

pkg/api/componentreadiness/utils/queryparamparser.go:237-251

When a view does not define spot_check_job_samples, the fallback creates a default spotcheck-30d entry as long as sample release dates are valid. Since all 60 views without explicit spot-check config have valid dates, SpotCheckJobs middleware is instantiated and its Query runs a BigQuery scan for every component report request across those views. The comment says “so spot-check middleware runs on drill-down requests too,” but this also fires for top-level reports where no spot-check analysis is intended.

// queryparamparser.go:237-251
if len(opts.SpotCheckJobSamples) == 0 &&
    !opts.SampleRelease.Start.IsZero() &&
    !opts.SampleRelease.End.IsZero() {
    opts.SpotCheckJobSamples = []reqopts.SpotCheckJobSampleOpts{
        {
            Name: "spotcheck-30d",
            ...
        },
    }
}

Consider gating the fallback on the presence of a spotcheck- prefixed TestID in TestIDOptions (drill-down only), or skipping middleware creation at the report level for views without explicit config.

should fix Appending ‘rare’ to spotCheckIncludeVariants slice may mutate caller’s map entry

pkg/api/componentreadiness/dataprovider/bigquery/provider.go:477-480, 637-640

Both QuerySpotCheckJobRuns and QuerySpotCheckJobRunDetails read a slice from the caller’s map and append to it. If the backing array has spare capacity, append writes "rare" past the map entry’s length. While the map entry’s slice header retains its original length (so the mutation doesn’t accumulate across calls), any concurrent reader of the backing array past the original length could observe the stale value.

values := spotCheckIncludeVariants[group]
if group == "JobTier" {
    values = append(values, "rare")
}

Copy before appending: values = append([]string(nil), spotCheckIncludeVariants[group]...).

Things I checked and was fine with

  • Analysis refactoring preserves behavioral equivalence. NewTestPassRate → AllTestsPassRate → FisherExact reproduces the exact control flow of the old assessComponentStatus — confidence initialization, MinimumFailure early return, pity factor, MissingBasis override all preserved.
  • Middleware ordering is correct. Synthetic injection (SpotCheckJobs) → data adjustment (ReleaseFallback, RegressionTracker, RegressionAllowances) → analysis (NewTestPassRate, AllTestsPassRate, FisherExact) → decoration (LinkInjector).
  • List.Analyze first-responder-wins semantics correctly short-circuits on first handled=true.
  • SpotCheckJobs.Analyze status ladder covers all cases: 0 runs (MissingSample), 1 failure (MissingSample/pending retry), 2 failures (SignificantRegression), 3+ failures (ExtremeRegression), any passes (NotSignificant).
  • Go 1.25 loop variable semantics — no loop variable capture bugs in the goroutine closures.
  • param.Cleanse is a no-op for all standard variant names (Platform, Architecture, Network, JobTier), so the cleanV change in QueryJobRuns and BuildComponentReportQuery is safe and improves consistency.
  • BQ queries use parameterized values for user-controlled inputs; variant names go through param.Cleanse consistent with existing patterns.
  • BQ transition strategy (IN ('spotcheck-30d', 'rare') + COALESCE fallback) is sound for the migration period.
  • Frontend isSpotCheck conditionals are null-safe (=== 'spot_check' is false for undefined). Pragmatic approach for the limited scope of UI changes.
  • Test coverage is solid. Unit tests for each middleware’s Analyze, spot-check status ladder, variant matching, query filtering.
  • Synthetic test ID round-trip is correct for current capability names (“CPU Partitioning”, “Scaling”) — neither contains hyphens, so the hyphen-to-space decoding is lossless.
  • Postgres provider stubs return nil, nil — acceptable as a BigQuery-only feature; the comment documents the intent.
  • Regression tracking works with spot-check tests because RegressionTracker.PostAnalysis only checks ReportStatus value, not basis data.

Open questions for the author

  • Is the always-on SpotCheckJobSamples fallback (queryparamparser.go:237-251) intentional for top-level report requests, or should it be limited to drill-down requests with a spotcheck- test ID?
  • Should GeneratorCacheKey include SpotCheckJobSamples to prevent cache collisions between spot-check and non-spot-check results?
