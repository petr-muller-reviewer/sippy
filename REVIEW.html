Verdict: Request changes

The partition-pruning approach (adding prow_job_release and timestamp-window filters so Postgres can skip partitions) is sound and consistent with the stated goal (trt-2709). However, two of the narrowed queries change externally-visible behavior in ways that look unintentional: a UI-facing "last pass" timestamp and a fallback threshold used in release-comparison logic. Both should be confirmed with the author before merge.

What this PR does

  • Adds prow_job_release and/or timestamp-range filters to several queries across pkg/db and pkg/api so Postgres can prune to relevant partitions instead of scanning all of them.
  • Replaces an unbounded run-count lookup (ProwJobRunIDs) with a new ProwJobRunCount that counts within a fixed recent window.
  • Narrows the job_results SQL function's last-pass computation to the reporting window instead of the whole release history.
  • Scopes a job-run count metric to the current active release, pulled via a new CurrentActiveRelease helper.

Findings

Blocking

Blockingjob_results last_pass window narrowed

pkg/db/functions.go:122-126

lp AS (
    SELECT prow_job_runs.prow_job_id, max(prow_job_runs.timestamp)::timestamp without time zone as last_pass
      ...
      AND prow_job_runs.timestamp BETWEEN p_start AND p_endstamp

The lp CTE computing last_pass is now bounded to the reporting window (p_start..p_endstamp) instead of the full release history. A job that last passed outside that window now reports last_pass = NULL instead of the true timestamp — this is user-visible as the "Last pass" column in the Jobs UI.

BlockingProwJobRunCount hardcoded 14-day window breaks fallback threshold

pkg/db/query/job_queries.go:69-78 & pkg/api/job_runs.go:582

func ProwJobRunCount(dbc *db.DB, prowJobID uint, release string) (int, error) {
	var count int64
	q := dbc.DB.Table("prow_job_runs").
		Where("prow_job_id = ?", prowJobID).
		Where("prow_job_release = ?", release).
		Where("timestamp > NOW() - INTERVAL '14 days'")

// pkg/api/job_runs.go
if totalJobRuns < 20 {
    // falls back to comparing against the prior release

ProwJobRunCount replaces a previously all-time count (ProwJobRunIDs) with one hardcoded to the last 14 days. Its summed result feeds a totalJobRuns < 20 check in findReleaseMatchJobNames that triggers a fallback to the prior release. A job with hundreds of historical runs but fewer than 20 in the last 14 days will now spuriously look data-starved and trigger that fallback — a behavior change unrelated to partition pruning.

Should fix

Should fixCluster autocomplete silently filters to empty release

pkg/api/autocomplete.go:80-91

clusterRelease, err = query.CurrentActiveRelease(dbc)
if err != nil {
	log.WithError(err).Warn("could not determine current development release for cluster autocomplete")
}
...
Where("prow_job_release = ?", clusterRelease).

CurrentActiveRelease can return ("", nil) when release_definitions has no matching row (e.g. an under-populated dev/seed DB). There's no error in that case, and even on an actual error the code only logs and continues. Either path leaves clusterRelease = "", which then filters on prow_job_release = '' and silently returns an empty list with HTTP 200.

Should fixjobRunsCount and testIDsCount lose scope parity

pkg/api/tests.go:414-436

release, err := query.CurrentActiveRelease(dbc)
...
err = dbc.DB.Table("prow_job_runs").
	Where("prow_job_release = ?", release).
	Where("timestamp > ? AND deleted_at IS NULL", ...).
	Count(&jobRunsCount)
...
err = dbc.DB.Table("release_definitions").
	Pluck("release", &releases)
// testIDsCount later aggregated across all `releases`

jobRunsCount is now scoped to a single CurrentActiveRelease, while testIDsCount (computed just after) still spans every release. These feed two related Prometheus gauges (matViewUniqueNumberOfJobRuns / matViewUniqueNumberOfTests in pkg/sippyserver/server.go) that no longer share the same scope, silently changing what the job-runs metric represents.

Things I checked and was fine with

  • Diffed the full PR against upstream/main and traced call sites of every function whose query semantics changed.
  • Verified the top findings against actual downstream consumers (not just the diff) — the fallback logic in job_runs.go and the metric exports in sippyserver.go.
  • The overall partition-pruning pattern (adding prow_job_release plus timestamp bounds) is consistent with trt-2709's goal and matches prior commits on this branch.

Open questions for the author

  • For job_results.last_pass: was bounding it to the reporting window intentional, or should it stay unbounded and accept the wider partition scan?
  • For ProwJobRunCount: should the 14-day window be a parameter matching the caller's actual comparison window, given it now backs a < 20 threshold that assumed all-time counts?
  • For cluster autocomplete: should an unresolved CurrentActiveRelease return an error instead of silently filtering to an empty release?
  • For tests.go: was narrowing jobRunsCount to the current release intentional? If so, should testIDsCount be narrowed to match, or should the metrics be documented as differently scoped?
