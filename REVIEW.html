Approve

Well-scoped performance optimization with strong benchmark evidence (2x-21x speedups). All query rewrites are semantically equivalent to the originals, with one intentional NULL-handling change that is explicitly justified. No correctness bugs found after verification. Two minor cleanup observations noted below.

What this PR does

  • Rewrites all variant-based WHERE clauses to look up variant_combination_id against the small variant_combinations table (~2K rows) instead of running array containment checks on large tables.
  • Drops the GIN index on prow_jobs.variants (migration 000004) since no query uses array operators on that column anymore.
  • Removes the GIN index tag from the GORM model struct so AutoMigrate stays consistent.
  • Rewrites PlatformInfraSuccess to join matview rows to variant_combinations via integer ID instead of unnesting the matview's own variants array.
  • Converts buildCollapsedMatViewSQL from per-variant NOT clauses to a single array overlap check against variant_combinations.

Findings

nit Identical excluded_vc CTE duplicated in two functions

pkg/db/query/test_queries.go:116,175

WITH excluded_vc AS (
    SELECT id FROM variant_combinations WHERE @excluded && variants
),

This CTE appears identically in TestReportsByVariant and TestReportExcludeVariants. If the exclusion logic ever needs refinement, both must be updated in lockstep. A shared constant or helper would reduce that risk, but it is not blocking.

nit Same variant subquery pattern repeated across 6 call sites

pkg/api/test_analysis.go:59,63,125,129 and pkg/db/query/test_queries.go:271,275,304,308

jq = jq.Where("prow_jobs.variant_combination_id NOT IN "+
    "(SELECT id FROM variant_combinations WHERE ? = any(variants))", bv)

Each blocked/allowed variant appends an individual WHERE clause with the same subquery template. A shared GORM scope (e.g., WithVariantFilter(q, included, excluded)) would centralize the pattern. Current form is correct and readable.

Things I checked and was fine with

  • NULL handling with NOT IN: The old pattern NOT(variants is not null and @excluded && variants) included NULL-variant rows; the new NOT IN excludes them. The PR description explicitly addresses this: the trigger ensures variant_combination_id is NULL only when variants is NULL, staging confirms zero matview rows have NULL, and such rows carry no meaningful data.
  • PlatformInfraSuccess double-counting: Variant assignment uses a map key (VariantPlatform), so only one Platform variant per job is possible. The old query also used unnest, so behavior is equivalent.
  • GIN index drop safety: Remaining unnest(prow_jobs.variants) queries are unaffected because GIN indexes do not help unnest(). The && operator is now only used against variant_combinations (a different, small table).
  • Per-variant subquery efficiency: N is typically small (~2 variants). Batching into && would change AND-to-OR semantics for inclusion filters, so separate subqueries are the correct form.
  • Migration 000004 up/down: Correct DROP INDEX IF EXISTS / CREATE INDEX IF NOT EXISTS pair.
  • GORM model tag removal: prow.go tag change matches the migration.
  • SQL injection in buildCollapsedMatViewSQL: CollapsedVariantExclusions is a hardcoded []string literal, not user input. Manual quoting is safe.
  • PlatformInfraSuccess mixed interpolation: table comes from a controlled switch on period, not user input. sql.Named for the other params is correct.

Open questions for the author

  • The NOT IN pattern silently drops rows with NULL variant_combination_id. Would it be worth adding a NOT NULL constraint on variant_combination_id in the matview definitions (or a CHECK on the underlying tables) to make this invariant explicit rather than relying on the trigger?
