Verdict

APPROVE

Both original bug fixes are correct. The two issues raised in the first review round (stale test_filters state on view switch, and the compareVariantsCheckedItems array/object mismatch) were fixed in 652b348ee, going further than requested by switching to React's functional updater form and adding unit tests. The one remaining open item — the Postgres provider's missing lifecycle filter — is real but confirmed low-severity: production traffic uses MixedProvider, which routes test-status queries to BigQuery, not Postgres, so this gap only affects the standalone dev/devcontainer/CI-seed path. Worth a follow-up ticket, not a merge blocker.

What this PR does

  • Fixes a React state mutation bug in replaceIncludeVariantsCheckedItems and replaceCompareVariantsCheckedItems: both were mutating the existing state object and calling the setter with the same reference, making the change invisible to React. Fixed with spread-into-new-object, later upgraded to the functional updater form.
  • Fixes updateVarsFromView() to sync test_filters.lifecycles and test_filters.capabilities from a selected view's config into React state (previously only variant_options and advanced_options were synced).
  • Adds Go-level capability filtering to the Postgres data provider's queryTestStatus, bringing it into parity with the pre-existing BigQuery SQL-level filtering.
  • Adds an Azure seed job and two test entries to the seed data, providing a job that is excluded from the default view, making variant-filter behavior testable end-to-end with seed data.

Findings

Question (downgraded from Blocking)

questionPostgres backend does not implement lifecycle filtering
pkg/api/componentreadiness/dataprovider/postgres/provider.go:349-503

reqOptions.Lifecycles is never passed to queryTestStatus; there is no SQL predicate for it, unlike BigQuery's COALESCE(NULLIF(lifecycle, ''), 'blocking') IN UNNEST(@Lifecycles). Originally flagged as blocking in the first review. Downgraded after verifying production wiring: cmd/sippy/serve.go builds a MixedProvider when BigQuery credentials are configured (the production case), and MixedProvider routes QueryBaseTestStatus/QuerySampleTestStatus to BigQuery, not Postgres (pkg/api/componentreadiness/dataprovider/mixed/provider.go:55-61). The pure-Postgres queryTestStatus path is only reached via --data-provider=postgres, which in practice means local dev/devcontainer/CI-seed, not production.

The independent /deep-review panel reached the same conclusion independently ("pre-existing, not introduced by this PR, Postgres provider is for local dev/testing only") and the author declined to fix it in this PR — a reasonable scope call. Still worth a tracking issue since the gap is real and would matter if --data-provider=postgres is ever run against production-scale data.
