Verdict: Request changes

The performance idea is sound and the refactor is clean, but the new lastFailureExpr silently depends on an invariant (an in-window failure exists) that only holds because of the HAVING clause — and that invariant breaks when a caller sets minFail=0, a validated, user-reachable query parameter. That's a real correctness gap relative to the old LATERAL join, and it's also a parity gap versus BigQuery's still window-scoped last_failure. Worth resolving or explicitly accepting before merge.

What this PR does

  • Replaces a LEFT JOIN LATERAL against prow_job_run_tests with an inline MAX(e.prefix_max_last_failure) read from test_cumulative_summaries, avoiding a per-partition table scan for every candidate test.
  • Adds a lastFailureExpr field to testStatusSpec so the sample (prefix-sum) and base/GA query paths share one query builder; GA opts out with NULL::timestamptz.
  • As a side effect, the new per-group MAX is scoped correctly per (test_id, suite_id, variant_group), fixing a previously-documented gap where the LATERAL wasn't scoped to the variant group.
  • Adds integration tests: MAX across multiple jobs, mixed NULL/non-NULL timestamps, and a GA-path NULL assertion.
  • Postgres-only change — BigQuery's equivalent query path is untouched.

Findings

Blocking

LastFailure unbounded below dateRange.Start when minFail=0

pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:153-179

prefix_max_last_failure is an all-time cumulative running max (pkg/db/cumulativesummary/cumulative_summary.go:148: GREATEST(prev.prefix_max_last_failure, tds.last_failure_timestamp)), never reset at the window start. The query bounds it only from above (e.date = lookupEnd) — unlike totalExpr/successExpr/flakeExpr, there's no diff against a start-of-window value. Correctness today relies entirely on HAVING SUM(failures) >= minimumFailure guaranteeing an in-window failure exists (monotonicity then guarantees the max reflects at least that failure). But minFail is user-controlled, validated only as v >= 0 (pkg/api/componentreadiness/utils/queryparamparser.go:384-385, default 3). With minFail=0, HAVING degrades to SUM(total) > 0 — no in-window failure required — so LastFailure can surface a timestamp from long before dateRange.Start for a test with zero failures in the actual reporting window. The old LATERAL was explicitly scoped by pjrt.prow_job_run_timestamp >= rangeStart AND < rangeEnd and didn't have this gap.

failureInner := fmt.Sprintf(`
    SELECT
        e.test_id, e.suite_id, vg.group_id AS variant_group_id,
        SUM(%s) AS total_count,
        SUM(%s) AS success_count,
        SUM(%s) AS flake_count,
        %s AS last_failure
    ...
    HAVING SUM(%s) > 0
        AND SUM(%s) - SUM(%s) - SUM(%s) >= ?`,
Should fix

BigQuery/Postgres parity not addressed

pkg/api/componentreadiness/dataprovider/bigquery/querygenerators.go:437 vs pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:238

Project convention requires parity between data providers for query-logic changes. BigQuery's last_failure is strictly scoped to the date-filtered junit_data CTE — window-bound today. Postgres's new expression is not window-bound (see blocking finding). This PR doesn't mention BigQuery at all; if the minFail=0 gap is real, the providers will diverge in reported LastFailure for that configuration. Even setting that aside, the PR should state explicitly whether this is an intentional postgres-only optimization with no observable semantic difference, or something that should also land on BigQuery.

lastFailureExpr: "MAX(e.prefix_max_last_failure)",   // postgres, not window-bound

MAX(CASE WHEN junit_data.success_val = 0
    THEN junit_data.prowjob_start ELSE NULL END) AS last_failure  // bigquery, window-bound
Nit

lastFailureExpr windowing behavior undocumented

pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:113-130

The testStatusSpec field comment and the queryTestStatus doc comment don't note that lastFailureExpr is not windowed the same way as totalExpr/successExpr/flakeExpr (those diff e against s; this one can't, since MAX isn't invertible). A future maintainer could reasonably assume all four share the same windowing semantics.

Things I checked and was fine with

  • Build passes (go build ./...), unit tests pass (go test ./pkg/api/componentreadiness/dataprovider/postgres/...).
  • Removed lastFailureLateral, spec.release, spec.dateRange, and the now-unused sippyv1 import are fully cleaned up — no dangling references.
  • Verified via a monotonicity argument that in the default/common case (minFail >= 1), MAX(e.prefix_max_last_failure) at lookupEnd is guaranteed >= any in-window failure timestamp, so the change is safe for the default configuration.
  • GROUP BY collapsing across multiple prow_job_id per variant group: MAX aggregation across jobs is correct — a job with only stale (pre-window) failures can't out-rank a job with an actual in-window failure.
  • New GA-path assertion (ts.LastFailure.IsZero()) and the multi-job/mixed-NULL integration tests are sound and match existing conventions.

Open questions for the author

  • Is minFail=0 a realistic/supported configuration in production, or effectively unreachable in practice? If unreachable, should that be enforced (v >= 1) or at least documented as a known limitation?
  • Should BigQuery receive the equivalent optimization, or is its current window-scoped last_failure already cheap enough that no change is needed there?
  • Would it be worth adding a lower-bound guard to lastFailureExpr (e.g. CASE WHEN e.prefix_max_last_failure >= ?rangeStart THEN e.prefix_max_last_failure END) so correctness doesn't depend implicitly on the HAVING clause?
