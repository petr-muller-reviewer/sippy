Verdict

Approve. Clean post-migration cleanup. The partition error handling change is the only substantive one and it is correct — failing fast is safer than silently degrading into a DEFAULT partition.

What this PR does

  • Reverts the load command timeout from 14 hours (temporarily raised for migration) back to the standard 4 hours.
  • Changes ensurePartitions() failure from a warn-and-continue to a hard abort of the load, preventing data from landing in a DEFAULT partition where it would be hard to manage.
  • Clarifies a comment in pkg/db/db.go about the ordering dependency between RunMigrations and AutoMigrate.

Findings

question Asymmetry between partition creation and cleanup error handling

pkg/dataloader/prowloader/prow.go:239-249

Partition creation failure now aborts the load (good), but partition cleanup failure (lines 245-249) still uses the old warn-and-continue pattern. This asymmetry is likely intentional — failing to detach old partitions is less critical than failing to create new ones — but worth confirming that this is the desired behavior and not an oversight.

// creation: now fatal
if err := pl.ensurePartitions(); err != nil {
    pl.errors = append(pl.errors, errors.Wrap(err, "failed to ensure partitions"))
    return
}

// cleanup: still warn-and-continue
if detached, dropped, err := pl.dbc.CleanupPartitions(false); err != nil {
    log.WithError(err).Warning("failed to cleanup old partitions, continuing with load")
}

Things I checked and was fine with

  • Error is appended to pl.errors following the same pattern used by other fatal errors in Load() (lines 228, 233).
  • The 4-hour timeout matches what was in place before the migration bump; no other code depends on the extended value.
  • Comment rewrite in db.go is grammatically correct and clearer than the original.
  • No test changes needed — this is configuration/control-flow only, and the existing error propagation paths are already exercised.

Open questions for the author

  • Is the asymmetry between partition creation (now fatal) and cleanup (warn-and-continue) intentional, or should cleanup failures also abort? I assume intentional since stale partitions don't affect correctness, but wanted to confirm.
