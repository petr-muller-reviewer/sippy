Verdict

Needs discussion

The core script remains well-organized and the escaping fragility from the last refresh has genuinely improved (delegating JSON-encoding to python3 instead of manual backslashes). But the surface area keeps growing one step at a time without the earlier operational rough edges being addressed — the hardcoded :latest image, uninformative --dry-run, hardcoded sippy_openshift database name, and default-secret question are all still open — and this update adds its own open questions (undocumented python3 dependency, unchanged 120m timeout despite added scope, an unverified test-plan item for the very feature just added). Nothing here is a proven correctness blocker; the new escaping and dynamic-SQL construction were hand-verified safe.

What this PR does

  • Adds scripts/analyze-db.sh, which runs a post-restore three-step "warmup" — ANALYZE VERBOSE, REINDEX DATABASE CONCURRENTLY, and a dynamic cache-warming pass — against the Sippy database via an oc run pod.
  • Supports --namespace, --db-secret, --wait, and --dry-run flags, defaulting to the sippy namespace and postgres-aws secret.
  • Hardens scripts/backfill-summaries.sh's argument parser so every flag that takes a value now errors clearly if the value is missing, instead of silently swallowing the next argument or a positional string.
  • Documents the new script's purpose, defaults, overrides, and all three warmup steps in the root README.md.
  • Since previous review: added a DO $$ ... $$ PL/pgSQL block that iterates every non-partition table in public, runs a (possibly date-scoped) SELECT count(*), and logs row counts via RAISE NOTICE; the pod's sh -c script is now built as a heredoc and JSON-encoded via python3 rather than manually escaped.

questionRecency column chosen alphabetically, not by relevance (new)

scripts/analyze-db.sh:75-81

When a table has multiple date/timestamp-typed columns, date_col is chosen via ORDER BY c.column_name LIMIT 1 — whichever column name sorts first alphabetically (e.g. archived_at would beat created_at). For the stated goal of warming recently-queried heap pages, this heuristic could pick a column that doesn't reflect actual query recency patterns. Likely low-impact, but worth confirming it's intentional.

SELECT c.column_name INTO date_col
FROM information_schema.columns c
WHERE c.table_schema = 'public'
  AND c.table_name = tbl.tablename
  AND c.data_type IN ('date', 'timestamp with time zone', 'timestamp without time zone')
ORDER BY c.column_name
LIMIT 1;

nitDelete step still swallows all errors, not just not-found (unresolved)

scripts/analyze-db.sh:47

--ignore-not-found already makes a missing pod a non-error; the trailing || true still hides real failures (e.g. expired oc auth), letting the script proceed silently into oc run, where the failure then resurfaces less clearly.

oc -n "$NAMESPACE" delete pod "$POD_NAME" --ignore-not-found --wait >/dev/null 2>&1 || true

nitoc wait failure path suppresses its own stderr (unresolved)

scripts/analyze-db.sh:136-141

oc ... wait ... 2>/dev/null || { ... } discards the wait command's own error output (e.g. a propagation delay right after creation, or an RBAC error on watch), relying entirely on the fallback oc get pod status check. Most failure modes are covered by the fallback, but a wait-specific error (malformed jsonpath, permission denied) would be silently dropped.

oc -n "$NAMESPACE" wait --for=jsonpath='{.status.phase}'=Succeeded --timeout=120m "pod/$POD_NAME" 2>/dev/null || {
    STATUS=$(oc -n "$NAMESPACE" get pod "$POD_NAME" -o jsonpath='{.status.phase}' 2>/dev/null || echo "Unknown")
    echo "Pod finished with status: $STATUS" >&2
    oc -n "$NAMESPACE" logs "$POD_NAME" --tail=20 2>/dev/null || true
    exit 1
}

Things I checked and was fine with

  • Verified by manual bash reproduction that $(echo "$WARMUP_SCRIPT" | python3 -c "...") works correctly even with unescaped double quotes inside the outer --overrides="..." string — command substitution $(...) is its own quoting context, so this isn't a bug. The resulting JSON is valid and the DSN reference is correctly deferred to container runtime (unexpanded at capture time via the quoted 'SCRIPT_EOF' heredoc delimiter).
  • The dynamic SQL in the DO $$ block builds table/column names via format(..., %I, ...) (identifier-quoting), and the values come from pg_tables/information_schema.columns (server catalog), not external input — no SQL injection surface.
  • REINDEX DATABASE CONCURRENTLY is valid Postgres 12+ syntax and avoids the exclusive lock a plain REINDEX DATABASE would take.
  • The partition-exclusion filter (NOT EXISTS (... pg_inherits ...)) correctly skips inheritance/declarative-partition child tables so they aren't redundantly warmed alongside their parent.
  • Credentials flow through secretKeyRef into the pod's env rather than being baked into the manifest, consistent with restore_prodlike_db.sh. Unchanged.
  • The backfill-summaries.sh flag-parsing fix ([[ $# -ge 2 ]] guards) is consistent with the file's existing style and error-message convention; unchanged by this refresh.
  • README and header comment updates are clear, match the project's existing style, and now describe all three warmup steps accurately.
  • No unresolved human review threads; only CI/bot comments since the last review (author requested @coderabbitai review, CodeRabbit reported nothing new via its incremental system, CI passed on 2026-07-25).

Open questions for the author

  • REINDEX DATABASE CONCURRENTLY sippy_openshift hardcodes the database name — will this script ever be pointed at a DSN/secret whose database isn't named exactly sippy_openshift? If not, this is fine; if so, it needs to derive the name from the DSN or a flag.
  • Is python3 guaranteed to be available wherever this script runs? Should the script check for it up front with a clear error, or avoid the dependency (e.g. jq -Rs . instead of python3 -c json.dumps)?
  • Is the 120-minute --wait timeout still comfortable now that a third step (full-table counts across all public tables) has been added?
  • Is the alphabetical ORDER BY c.column_name LIMIT 1 choice of recency column intentional, or should it prefer a specific column name/pattern (e.g. created_at)?
  • Has the cache-warming step actually been run against staging yet? The PR's own test plan checkbox for it is unchecked.
  • Should --image be added to analyze-db.sh for parity with backfill-summaries.sh's auto-detect/override pattern, and should the tag be pinned instead of :latest?
  • Should --dry-run print the full resolved oc run invocation (namespace, secret, image, and the warmup script) instead of just a one-line summary?
  • Is the postgres-aws default secret name confirmed correct, and should --db-secret be required the way it is in backfill-summaries.sh?
  • Now that the pod isn't --rm'd, is leftover-pod accumulation (when --wait isn't used) acceptable, or should the script warn about it / offer a cleanup flag?
  • Is the static POD_NAME collision risk (now more consequential since detached runs can be killed by a subsequent invocation, and runs are longer with three steps) acceptable given expected usage patterns?
