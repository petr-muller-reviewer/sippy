Verdict: Needs discussion

This is a well-executed refactor with strong test coverage (32 new integration tests) and a genuinely clean extraction of DB-write logic into a dedicated pgwriter package — diffed the moved SQL against the deleted originals and it's a byte-identical relocation. The blocker is a design question, not a bug: a single future-dated test result rolls back the entire batch (up to 100 job runs), and because those runs never get marked "loaded," this can become a poison pill that wedges ingestion indefinitely. Worth resolving with the author before merge — either by design decision or by scoping the rejection to the offending run.

What this PR does

  • Replaces the periodic full-table refresh of test_daily_totals/test_cumulative_summaries with per-batch incremental upserts run during prow loading.
  • Extracts DB-write logic from prow.go into a new pkg/dataloader/prowloader/pgwriter package with focused, single-responsibility functions per SQL step.
  • Parallelizes cross-release carry-forward using an errgroup (limit 4 workers).
  • Pins currentDate once at ProwLoader construction and threads it through all summary SQL to avoid midnight-crossing corruption.
  • Removes the old dailysummary.Refresh/cumulativesummary.Refresh calls from RefreshData; that code path is retained and still used by the existing sippy backfill command.

Findings

Blocking

BlockingFuture-dated test result rolls back the entire batch, not just the offending run

pkg/dataloader/prowloader/pgwriter/pgwriter.go:596-609

tomorrow := currentDate.AddDays(1)
var hasFuture bool
if err := tx.QueryRow(ctx, `SELECT EXISTS(SELECT 1 FROM batch_deltas WHERE batch_date > $1)`, tomorrow).Scan(&hasFuture); err != nil {
    return fmt.Errorf("checking for future-dated batch rows: %w", err)
}
if hasFuture {
    return fmt.Errorf("batch contains test results dated after %s; refusing to write summaries", tomorrow)
}

upsertSummaryTables checks for any row dated more than one day past currentDate, and if found, returns an error. That error propagates out of Write(), rolling back the whole transaction — including prow_job_runs, annotations, PR associations, and test inserts for every run in the batch (up to flushThreshold = 100). One job with a clock-skewed timestamp can drop up to 99 unrelated, valid runs. Because the failing run's ID never lands in prow_job_runs, it's never marked "loaded" and will be re-fetched and re-fail every subsequent load cycle — a poison pill that can wedge ingestion indefinitely. The only test covering this (TestFutureDatedTestResultsRejectBatch) uses a single-run batch, so the collateral damage to co-batched runs is untested.

Nits

NitPostgres-specific NULL-ignoring semantics of LEAST/GREATEST used without comment

pkg/dataloader/prowloader/pgwriter/pgwriter.go:720-742, 766-794

first_failure_timestamp = LEAST(dt.first_failure_timestamp, bd.min_failure_ts),
last_failure_timestamp = GREATEST(dt.last_failure_timestamp, bd.max_failure_ts),

Correct only because Postgres's LEAST/GREATEST ignore NULL arguments (non-ANSI-standard). Columns start NULL via ensureDailyTotalRows/ensureCumulativeSummaryRows. A one-line comment would help a future reader who assumes standard SQL NULL-propagation.

Questions

QuestionIs the batch-wide rejection on future-dated data an intentional tradeoff?

Is "fail the whole batch loudly" preferred over "skip/clamp the offending run's summary contribution and keep the rest"? If intentional, is there a runbook or tooling to identify and un-wedge a stuck batch in production?

Things I checked and was fine with

  • gofmt -l clean on all touched files; go vet ./pkg/dataloader/prowloader/... clean.
  • golang.org/x/sync/errgroup already a repo dependency (used elsewhere) — no new dependency risk.
  • Moved SQL/Go bodies (insertJobRuns, insertAnnotations, upsertPullRequests, insertPRAssociations, insertTestResults) are byte-identical to what was deleted from prow.go — pure relocation, no incidental behavior change.
  • ensureCumulativeSummaryRows's GROUP BY over query-literal columns is valid SQL, not a bug.
  • carryForwardRelease/findLatestDateWithData's day-by-day backward walk (capped at 30 days) is idempotent — confirmed against TestCarryForwardIsIdempotent and the "already up to date" short-circuit.
  • No BigQuery counterpart exists for these summary tables (Postgres-only ETL, not part of the dual-provider componentreadiness/dataprovider abstraction) — the project's BQ/Postgres parity rule doesn't apply here.
  • RefreshData's doc comment accurately reflects new behavior; dailysummary/cumulativesummary imports in server.go are still used by BackfillData — no dead code left behind.
  • accumulate_test.go mechanically updated to new pgwriter.JobRunResult/pgwriter.RunRow types and the refactored accumulateAndWrite(ctx, results, writerFunc) signature — correct, no behavior change.
  • Test coverage of happy paths, carry-forward parallelism, release scoping, soft-delete restoration, PR metadata preservation, and dedup is thorough.
  • No SQL string concatenation of untrusted input; all queries parameterized.
