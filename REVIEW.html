Verdict

Needs Discussion

Three of the original should-fix findings have been addressed (date filter, Manager per run, mergeLabels). Code quality is high, tests are solid, documentation is thorough. The remaining concern is the cancellation hazard in the write path: BQ and GCS calls use the request context, so a client disconnect can interrupt the delete-then-insert sequence mid-way, leaving inconsistent label state. The author's frontend-worker-pool design (single-run requests) reduces the likelihood of hitting proxy timeouts but does not eliminate the race. Worth discussing whether to use a detached context for the write path or accept the risk for v1.

What this PR does

  • Adds POST /api/jobs/runs/reevaluate endpoint that re-runs all symptom definitions against specified job run artifacts, updating BigQuery, GCS, and PostgreSQL.
  • Uses delete-then-insert strategy for idempotency: clears existing symptom-originated labels, re-scans artifacts, writes fresh results. Manually-applied labels (empty symptom_id) are preserved.
  • Extracts BulkInsertJobRunLabels from the annotator as a shared helper for BQ batch inserts.
  • Comprehensive documentation: detailed plan document, updated feature docs and API README, new BQ query labels.
  • APM/tooling updates: em-dash removal, sets.NewString() convention, no-mock testing guidance, agentic command templates for multiple editors.

Findings

Should fix

should fix Synchronous API with no cancellation safety
pkg/api/jobrunscan/reevaluate.go:123-127, pkg/sippyserver/job_run_scan.go:174-205

The request ctx is passed to BQ and GCS calls in clearAndWrite (which respect cancellation), but the artifact scanning in getJobRunFiles (query.go:134) uses context.Background(). If a proxy kills the connection, a race develops: the BQ DELETE in clearBQLabels may complete (ctx still alive), then a subsequent BQ insert or GCS write fails with context.Canceled, leaving the job run with cleared-but-not-rewritten labels.

Update: The author's comment (2026-06-23) describes the intended architecture: the frontend will run a pool of workers making single-run requests, reporting progress as they return. This reduces the timeout risk (single runs take seconds) but the cancellation hazard remains: if ctx cancels between the BQ delete and insert within a single run, the label state is inconsistent.

Discussion (2026-06-23): mstaeble raised concerns about concurrent requests and frontend cancellation, arguing backend orchestration is simpler for consistency. sosiouxme responded that operations are "idempotent-ish" and on cancellation: backend halts at context checkpoint, frontend can retry. Both agree the orchestration mechanism can iterate post-merge. A minimal fix: use a detached context for the write path so client disconnect doesn't corrupt state. 

// clearBQLabels passes ctx to BQ (respects cancellation):
q := r.bqClient.Query(ctx, bqlabel.JobRunLabelsReEvaluateDelete, queryStr)
_, err := q.Read(ctx)

// but getJobRunFiles ignores request ctx entirely:
// query.go:134:
ctx, cancel := context.WithTimeout(context.Background(), time.Second*30)

Questions

question Streaming buffer skip can produce duplicate BQ rows
pkg/api/jobrunscan/reevaluate.go:449-453

When clearBQLabels hits a streaming buffer error, it swallows the error and continues. New labels are still inserted, producing duplicates. The author confirmed (2026-06-22) this is acceptable: labels are collapsed on display, and failure to delete only means stale labels from changed symptoms may persist. Should the API README mention this limitation? 

if strings.Contains(err.Error(), "streaming buffer") {
    log.WithError(err).WithField("buildID", buildID).Warn(
        "symptom reEval: BQ delete hit streaming buffer, skipping")
    return nil  // swallows error, proceeds to insert
}
