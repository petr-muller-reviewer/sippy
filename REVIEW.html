Verdict

Request changes

The prior TOCTOU race and missing-HATEOAS findings are resolved by this round's rewrite, but the blocking multi-triage scoping gap survives the rewrite unchanged, and a new related issue surfaced: auto-resolution now mislabels triages that only resolved because their regressions were force-closed. These need addressing before merge.

What this PR does

  • Adds force-close for test regressions tied to a resolved triage: ForceCloseRegressions and a dry-run ForceClosePreview in pkg/api/componentreadiness/regressiontracker.go, exposed via jsonForceCloseRegressions/jsonForceClosePreview in pkg/sippyserver/server.go.
  • Force-closing is a single atomic UPDATE ... WHERE id IN (subquery on triage_regressions) AND closed IS NULL AND opened < closeTime ... RETURNING id, stamping force_closed, force_closed_by, force_closed_reason, force_closed_by_triage_id, and a closed timestamp from the triage's resolution time.
  • ResolveTriages's auto-resolution check now treats force_closed regressions as inactive, so a triage whose regressions are all force-closed can auto-resolve.
  • New response types carry HATEOAS Links via InjectForceCloseHATEOASLinks/InjectForceClosePreviewHATEOASLinks.
  • Adds integration coverage (test/integration/regression_forceclose_test.go, test/integration/util/fixtures.go); removes the redundant SQL migration.

Findings

Blocking force-close scoped only by the given triage, ignoring multi-triage regression linkage

pkg/api/componentreadiness/regressiontracker.go:379-382

TestRegression.Triages is many-to-many via triage_regressions, but the force-close UPDATE's eligibility subquery is scoped only to the given triage ID. If a regression is also linked to a different, still-open triage B, force-closing via triage A sets force_closed=true globally. Since ResolveTriages (line 233) excludes force_closed rows from its open-regression check, triage B can then auto-resolve using triage A's unrelated resolution time. Confirmed against the current query shape — this survived the rewrite from select-then-update to a single atomic UPDATE.

Where("test_regressions.id IN (?)",
    prs.dbc.DB.Table("triage_regressions").
        Select("test_regression_id").
        Where("triage_id = ?", triageID)).
Where("test_regressions.closed IS NULL").
Where("test_regressions.opened < ?", closeTime).

Should fix ResolveTriages mislabels force-closed triages as auto-resolved rollouts

pkg/api/componentreadiness/regressiontracker.go:266

Since the NOT EXISTS subquery at line 233 now treats force-closed regressions as inactive, a triage whose only regressions were force-closed can auto-resolve through this path. Line 266 unconditionally sets ResolutionReason = models.RegressionsRolledOff, mislabeling a deliberate human force-close as an automatic rollout and discarding the real force-close reason.

triage.ResolutionReason = models.RegressionsRolledOff

Should fix force-close endpoint has stricter auth behavior than sibling triage-write endpoints

pkg/sippyserver/server.go:488

jsonForceCloseRegressions hard-401s whenever getUserForRequest() returns empty, unlike jsonCreateTriage/jsonUpdateTriage/jsonDeleteTriage, which proceed and merely log the (possibly empty) user. getUserForRequest returns "" whenever X-Forwarded-User is unset and DEV_MODE != "1", so a developer who can otherwise manage triages locally gets an unexpected 401 specifically on force-close. May be intentional (audit requirement) but is an undocumented inconsistency.

Should fix deleting a triage leaves stale force_closed_by_triage_id references

pkg/db/models/triage.go:247

ForceClosedByTriageID has no FK/cascade handling, and jsonDeleteTriage never clears it. Deleting a triage that previously force-closed regressions leaves test_regressions.force_closed_by_triage_id pointing at a nonexistent row; the HATEOAS links built from that stale ID 404, and the audit trail can no longer be resolved.

Nit duplicated HATEOAS URL-building logic

pkg/api/componentreadiness/regressiontracker.go:388

forceCloseTriageLinks/regressionDetailLink hand-roll the same URL format strings already defined and used via injectHATEOASLinks/InjectRegressionHATEOASLinks in pkg/api/componentreadiness/triage.go. A route rename is likely to update only one copy.

Nit duplicated "load triage, check Resolved" validation

pkg/api/componentreadiness/regressiontracker.go:354

ForceCloseRegressions and ForceClosePreview duplicate an identical block that loads the triage, wraps the error, and checks Resolved.Valid.

Nit redundant paired queries in failure-gap lookup

pkg/api/componentreadiness/regressiontracker.go:286

queryRegressionFailureGaps runs two near-identical grouped queries against regression_job_runs that could be one conditional-aggregation query, doubling DB round trips per preview call.

Nit ad hoc, uncapped trailing-JSON body validation

pkg/sippyserver/server.go:503

The decode-twice-to-io.EOF trick for rejecting trailing JSON is reinvented ad hoc for this one endpoint, with no size cap, and no sibling write endpoint performs this check.

Things I checked and was fine with

  • The rewritten single-UPDATE force-close (subquery + closed IS NULL + opened < closeTime, RETURNING id) closes the prior TOCTOU race between select and update.
  • New response types now populate Links, addressing the prior missing-HATEOAS finding.
  • Handlers no longer echo raw err.Error() and handle gorm.ErrRecordNotFound with 404; user identity is no longer logged.
  • No SQL injection concerns; all queries are parameterized gorm calls.
  • New integration tests exercise the happy path and several edge cases, but do not appear to cover the multi-triage-sharing scenario in the blocking finding above.

Open questions for the author

  • Is a regression ever expected to be linked to more than one triage in practice, or is triage_regressions many-to-many purely a schema affordance that's unused today?
  • Is the force-close 401-on-missing-user behavior intentional and stricter than other triage-write endpoints by design, or an oversight from copying a different code path?
  • Should ResolveTriages record a different resolution reason (or preserve the force-close reason) when a triage auto-resolves purely because its regressions were force-closed?
