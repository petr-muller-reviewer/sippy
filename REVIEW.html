Verdict

Approve

Small, targeted, additive-only bugfix. Verified the registered Chart.js building blocks cover every chart type actually used in the codebase (Line and Doughnut), and that annotationPlugin is genuinely consumed elsewhere. No behavior change beyond fixing the crash; no risk found.

What this PR does

  • Adds sippy-ng/src/chartSetup.jsx, a side-effect module that calls Chart.register(...) for the controllers, elements, scales, and plugins the app's charts need (ArcElement, CategoryScale, DoughnutController, Filler, Legend, LinearScale, LineController, LineElement, PointElement, TimeScale, Title, Tooltip, plus chartjs-plugin-annotation).
  • Imports that module for its side effect at the very top of App.jsx so registration happens before any chart renders.
  • Fixes the runtime error Error: "arc" is not a registered element., most likely surfaced by the recent Vite migration — Chart.js v3's tree-shakeable build requires explicit registration, which the old bundling setup may have papered over.

Findings

No blocking issues, should-fix items, or nits found.

Things I checked and was fine with

  • Every chart type actually rendered in the app — Line (in BuildClusterHealthChart.jsx, JobStackedChart.jsx, JobAnalysis.jsx, TestStackedChart.jsx, TestPassRateCharts.jsx, TestDurationChart.jsx) and Doughnut (SummaryCard.jsx) — has every required chart.js building block present in the registered list.
  • No other chart types (Bar, Pie, Scatter, Radar, etc.) exist anywhere in sippy-ng/src, so the registration list isn't under-inclusive.
  • annotationPlugin is genuinely used (prow_job_runs/IntervalsChart.jsx, tests/FeatureGateDetail.jsx), not dead registration.
  • No duplicate Chart.register calls elsewhere in the codebase that this could conflict with.
  • Import ordering in App.jsx preserved — ./chartSetup sorts alphabetically before ./components/....
  • Registration is idempotent and global; registering elements not strictly needed today carries no real downside.

Open questions for the author

  • chartSetup.jsx contains no JSX — was .js considered, or is .jsx the deliberate convention for all files under src?
  • Existing tests mock react-chartjs-2 via setupTests.jsx, so this exact bug class (a missing Chart.register call) wouldn't have been caught by the test suite. Worth a lightweight smoke test that mounts a real chart component through actual Chart.js, so a future chart type added without updating this file fails in CI instead of production?
