Verdict: Approve

The refactoring is clean and the benchmarks are properly gated. The new commits significantly improve the benchmark framework and expand coverage. Remaining suggestions are quality-of-life improvements, none blocking.

What this PR does

  • Extracts the ProwJobRun database query from PrintJobDetailsReportFromDB into a new exported JobDetailsReport function, separating query logic from HTTP response handling.
  • Adds a benchmark test file gated behind db_benchmarking_dsn env var — skips in CI.
  • Benchmarks 10+ query patterns: FindTestsByRelease, TestDurations, TestOutputs, JobDetails, TestAnalysisOverall, TestAnalysisByJob (with and without variant filter), lookback count queries (14d/9d), and pass-rate analysis.
  • Since previous review: added benchmarkResult struct (min/max/avg/total), runBenchmarkCase and printSummaryTable helpers; iterations bumped to 3; new Test_BenchmarkFindTestsByRelease and Test_BenchmarkCombined entry points; benchmarkJobName constant extracted.

Findings

Resolved

resolved Custom timing framework — sufficiently improved

Original concern: duplicated timing with fmt.Printf, iterations hardcoded to 1. New code adds benchmarkResult with min/max/avg/total, runBenchmarkCase helper, printSummaryTable, and bumps iterations to 3. Still not testing.B / benchstat, but the custom framework is now genuinely useful.

Should fix

should fix Hardcoded release, test name, and job name constants will rot

pkg/flags/postgres_benchmarking_test.go:15-17

const benchmarkRelease = "4.22"
const benchmarkTestName = "[Monitor:legacy-test-framework-invariants-pathological][sig-arch] events should not repeat pathologically for ns/kube-system"
const benchmarkJobName = "periodic-ci-openshift-release-main-ci-4.22-e2e-aws-ovn"

All three become stale as releases advance. Someone will waste time debugging why benchmarks return zero results. Make them configurable via env var (like db_benchmarking_dsn already is), or document that they need periodic updates.

Nits

nit DB client never closed — leaked connections

pkg/flags/postgres_benchmarking_test.go — getBenchmarkDBClient

dbc, err := dbFlags.GetDBClient()
if err != nil {
    t.Fatalf("couldn't get DB client: %v", err)
}
return dbc

The helper opens a DB connection but registers no t.Cleanup to close it. Unlikely to matter in practice for a manual benchmark tool, but a t.Cleanup(func() { dbc.DB.Close() }) is good hygiene. (CodeRabbit also flagged this.)

nit Direct map index into getIndividualBenchmarkCases() can panic

pkg/flags/postgres_benchmarking_test.go — Test_BenchmarkFindTestsByRelease

bc := getIndividualBenchmarkCases()["FindTestsByRelease"]
r := runBenchmarkCase(t, dbc, bc, iterations)

If the key drifts (rename, typo), bc is a zero-value benchmarkCase and bc.fn is nil — calling it panics with no useful message. Use a comma-ok check and t.Fatal on miss.

nit Multiple benchmark cases use raw SQL not present in production

pkg/flags/postgres_benchmarking_test.go — FindTestsByRelease, TestCountsByLookback14ForRelease, TestCountsByLookback9ForRelease, TestAnalysisPassRate

Four cases embed raw SQL inline rather than calling production query functions. They benchmark queries that won't be optimized alongside production code. TestAnalysisPassRate uses query.QueryTestAnalysis (a real constant), which is better, but the call site still isn't the real production code path.

nit Per-row logging included in benchmark timing

pkg/flags/postgres_benchmarking_test.go — FindTestsByRelease fn body

for _, r := range results {
    log.Printf("  [%d] %s", r.ID, r.Name)
}

This runs inside the timed section, adding I/O noise to the measured query duration.

nit Test_BenchmarkGroup still uses iterations := 1

pkg/flags/postgres_benchmarking_test.go — Test_BenchmarkGroup

All other tests were bumped to 3 iterations; Test_BenchmarkGroup keeps 1. Likely intentional (group runs are expensive), but worth a comment if so.

nit Test_BenchmarkCombined runs FindTestsByRelease twice

pkg/flags/postgres_benchmarking_test.go — Test_BenchmarkCombined

It iterates both getBenchmarkCases() and getIndividualBenchmarkCases(), so FindTestsByRelease appears twice in the combined summary table — confusing when reading results.

nit Test file placement in pkg/flags

This file tests queries from pkg/api and pkg/db/query but lives in pkg/flags. The only pkg/flags dependency is PostgresFlags.GetDBClient(). Precedent exists (component_readiness_test.go), so not blocking.

Things I checked and was fine with

  • JobDetailsReport extraction is mechanically correct — same query, same field ordering, caller delegates properly.
  • Error handling preserved: PrintJobDetailsReportFromDB logs and returns the error from JobDetailsReport.
  • Removed comment about magic number 12 is pre-existing, not introduced here.
  • Tests gated behind db_benchmarking_dsn env var — skip in CI and normal make test.
  • No changes to any API contract or response format.
  • runBenchmarkCase properly resets min on first iteration (i == 0 check).
  • printSummaryTable sorts by avg descending — useful for identifying slowest queries at a glance.

Open questions for the author

  • Is the intent to run these manually against a prod-like DB before and after optimization? If so, benchstat on testing.B output would give statistically meaningful comparisons.
  • Should the raw SQL benchmark cases be extracted into production query functions for consistency with the other cases?
