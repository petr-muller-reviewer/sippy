Verdict: Approve — Well-structured change with thorough benchmarking. One parity concern worth discussing, no blocking issues.

What this PR does

  • Drops variant_combination_id from test_daily_summaries and resolves it at matview refresh time via JOIN to prow_jobs, fixing 49% stale variant associations.
  • Removes the prow_jobs JOIN from the daily summary INSERT query, making writes faster (single-table aggregation).
  • Adds 8 new variant keys to importantVariants (Procedure, Aggregation, NetworkAccess, Scheduler, Suite, ContainerRuntime, CGroupMode, LayeredProduct).
  • Introduces a migration MANIFEST file and make verify-migrations CI target to prevent concurrent PRs from silently merging duplicate migration version numbers.
  • Removes the TRUNCATE test_daily_summaries from ensureVariantCombinationTrigger since the column no longer exists.

Findings

should-fix Postgres provider fieldMap parity gap widened by new variant keys

pkg/api/componentreadiness/dataprovider/postgres/provider.go:253-262

fieldMap := map[string]string{
    "platform": "Platform",
    "network":  "Network",
    "arch":     "Architecture",
    "upgrade":  "Upgrade",
}
variantKey, ok := fieldMap[field]
if !ok {
    return []string{}, nil
}

The Postgres provider's QueryUniqueVariantValues hard-codes only 4 legacy variant keys. Any other field silently returns an empty slice. The BigQuery provider handles all variant keys dynamically via UNNEST. This gap predates the PR, but adding 8 new keys to importantVariants widens the discrepancy. CLAUDE.md requires parity between data providers.

question Down migration truncates daily summaries instead of backfilling

pkg/db/migrations/000004_drop_daily_summary_variant_combination.down.sql:1-2

TRUNCATE test_daily_summaries;
ALTER TABLE test_daily_summaries ADD COLUMN IF NOT EXISTS variant_combination_id BIGINT;

Rolling back destroys all daily summary data, requiring a full rebuild (hours). Since prow_job_id remains in the table and prow_jobs.variant_combination_id is intact, a backfill UPDATE could preserve data. The PR description acknowledges this tradeoff explicitly. Worth confirming this is the preferred approach over a slower but non-destructive rollback.

Things I checked and found no issues

  • pre_agg CTE correctness: JOIN and GROUP BY produce the same aggregation as the old design, just resolving variant_combination_id from prow_jobs at refresh time instead of from the stored column.
  • Daily summary INSERT SQL: variant_combination_id removed from SELECT list, GROUP BY, and valueColumns in lockstep; no orphaned references.
  • Migration 000004 up: Drops all 4 dependent matviews before the column drop; they are recreated by syncPostgresMaterializedViews on next startup.
  • MANIFEST mechanism: Genuinely prevents silent merge of duplicate migration versions. golang-migrate only detects collisions at runtime (too late); the MANIFEST forces a git merge conflict.
  • verify-migrations.sh edge cases: Handles empty lines, comments, and zero-padded numbers correctly. The continue on line 24 guards the arithmetic comparison from empty strings.
  • Retroactive variant resolution: Intentional design choice. Using current prow_jobs.variants at refresh time fixes the 49% stale data problem described in the PR.
  • ensureVariantCombinationTrigger: TRUNCATE removal is correct since the column no longer exists after migration 000004.
  • TestDailySummary struct: Field removal matches migration and SQL changes. No remaining references to test_daily_summaries.variant_combination_id in the codebase.
  • No cross-file breakage: All callers of changed functions, all references to removed fields traced; no orphaned usage found.

Open questions for the author

  • The fieldMap parity gap in the Postgres provider predates this PR. Is fixing it in scope here, or should it be tracked as a follow-up?
  • Is the TRUNCATE in the down migration a deliberate choice for rollback speed, or would a backfill-based rollback (slower but data-preserving) be acceptable?
