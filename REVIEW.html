Verdict

Approve.

Correct, minimal change. The 15-day time bound on the matview SQL is safe because the only consumer never needs data older than 14 days, and even if custom date params are passed via the API, results outside the window are discarded by the join against the time-bounded ByPeriod map.

What this PR does

  • Adds a WHERE pjrt.prow_job_run_timestamp > (NOW - 15 days) filter to the prowJobFailedTestsMatView SQL template in pkg/db/views.go.
  • This template backs both prow_job_failed_tests_by_day_matview and prow_job_failed_tests_by_hour_matview.
  • Previously these matviews scanned the entire prow_job_run_tests table with no time filter, taking ~3 minutes per refresh. The 15-day bound enables partition pruning, cutting refresh to ~1 minute.
  • Adds an explanatory comment at the consumer site (pkg/api/job_analysis.go:112) documenting the matview’s time constraint.
  • Presented as a smaller alternative to PR #3647 which removes these matviews entirely.

Findings

No findings. The change is correct and well-scoped.

Things I checked and was fine with

  • The |||TIMENOW||| placeholder substitution in pkg/db/views.go:151,189 handles the new interval correctly — same mechanism used by all other matviews.
  • The only consumer (PrintJobAnalysisJSONFromDB) uses a 14-day default window. Custom start/end params can be passed via the HTTP API, but the matview results are joined against results.ByPeriod (populated from the time-bounded sumResults query) — data outside the window is discarded by the if _, ok check at job_analysis.go:123.
  • The 15-day interval (14 + 1 buffer) is consistent with the pattern used by testAnalysisByJobMatView at views.go:419.
  • No other consumers of these matviews exist outside PrintJobAnalysisJSONFromDB.
