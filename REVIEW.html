Verdict

Approve

No blocking issues found. The filename-parsing regex, host allowlisting, and upsert semantics all correctly preserve prior behavior with good added unit test coverage. The should-fix items (a functional test for the new SQL path, documenting GITHUB_TOKEN, and reconsidering the ad hoc GitHub client vs. the existing rate-limit-aware one) are worth addressing but don't block merge.

What this PR does

  • Replaces the go-git clone of openshift/api with GitHub Contents API calls per release branch, cutting fetch time from ~3m10s to ~7s for 9 branches.
  • Adds a host allowlist (raw.githubusercontent.com, objects.githubusercontent.com) before following any download_url returned by the GitHub API.
  • Switches the DB write path from GORM CreateInBatches to pgx COPY-into-temp-table plus a raw INSERT ... ON CONFLICT upsert, using the pre-existing db.CopyToTempTable helper.
  • Replaces the ad hoc filename-suffix-splitting logic with a single regex that reproduces the same behavior for both legacy and versioned feature-gate filenames.
  • Removes the go-git dependency and 16 transitive packages (~117k lines of vendored code).

Should fixNew GitHub client duplicates and bypasses existing rate-limit-aware client

pkg/dataloader/featuregateloader/featuregateloader.go:41-51,192-218 (New, doGet) vs pkg/dataloader/prowloader/github/github.go

prowloader/github/github.go already implements a GitHub client with GitHub App installation-token auth (preferred, via newGHAuthClient) falling back to GITHUB_TOKEN, plus explicit RateLimits() checking and IsWithinRateLimitThreshold() so callers can back off before hitting 403s. The new loader reimplements a bare net/http.Client that only reads GITHUB_TOKEN directly, has no rate-limit awareness, and no retry/backoff on non-200/404 responses — a 403 rate-limit response is just a generic error, and that release's fetch is silently dropped for the cycle. Both loaders share the same GITHUB_TOKEN/api.github.com quota with zero coordination: this loader's listDirectory calls (~9/cycle) add to a budget prowloader actively monitors, invisibly to it. This loader's own footprint is small enough to be low-risk on its own (downloadFile targets raw.githubusercontent.com, which isn't part of the api.github.com quota), but it's an avoidable duplication of already-solved infrastructure.

Things I checked and was fine with

  • parseFeatureGateFilename regex reproduces old suffix-splitting behavior exactly for both legacy and versioned filenames; all pre-existing test cases pass unchanged.
  • isAllowedDownloadURL correctly restricts download_url (untrusted API response value) to the two expected GitHub raw-content hosts over HTTPS; covered by tests including scheme rejection and malformed URLs.
  • The added dbErr guard before constructing the feature-gate loader in load.go matches the exact pattern used by every other loader branch in that function — not a bug.
  • Partial-failure handling: a failed release fetch is recorded and the loop continues; an all-failed case short-circuits the upsert on an empty slice while still surfacing errors.
  • fetchFeatureGatesForBranch aborts on first error within a branch, discarding already-parsed files for that release — same as the old filepath.Walk behavior, not a regression.
  • db.CopyToTempTable (pre-existing, untouched by this PR) validates identifiers via regex before use in raw SQL — no injection risk from the fixed column definitions.
  • Composite unique constraint / upsert semantics preserved from the old GORM OnConflict logic.
  • Storing ctx context.Context on the FeatureGateLoader struct is not an anti-pattern here: the shared DataLoader interface's Load() takes no arguments, so a constructor-injected context is this package's established convention (gateststatus, testownershiploader do the same). Each loader is built fresh per CLI invocation and used once — no staleness/reuse risk.
  • Rate-limit exposure from this loader's own request volume is low on its own: listDirectory is ~9 calls/cycle against the rate-limited api.github.com; downloadFile targets the separately-throttled raw.githubusercontent.com.

Open questions for the author

  • Is a functional test (skipped without credentials) planned as a fast-follow for the COPY/upsert path, or intentionally out of scope here?
  • Should GITHUB_TOKEN be documented in config/README.md, or is it considered ops/deployment-only config?
  • Was reusing prowloader/github.Client (GitHub App auth + rate-limit checking) considered instead of a new bare HTTP client, given both now draw from the same GITHUB_TOKEN/api.github.com quota with no coordination?
