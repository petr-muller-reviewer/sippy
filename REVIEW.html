Verdict

Needs discussion

The core approach (deltas from cumulative summaries / GA raw data as a fallback for un-backfilled releases) is sound and mirrors existing patterns in this provider. But there's an unresolved correctness question about whether the all-or-nothing fallback trigger silently breaks the multi-test cache-priming path for partially-backfilled releases, and the implementation diverges from what the PR description says it does (no IsAggregate field exists). PR is explicitly marked work-in-progress, so these are likely already known to the author.

What this PR does

  • Adds a fallback in PostgresProvider.QueryBaseJobRunTestStatus: when the per-run query (prow_job_run_tests) returns nothing for the base release, queries test_cumulative_summaries (prefix-sum delta) or prow_ga_raw_test_data (GA-window releases) instead.
  • Threads a new *string explanation return value through TestDetailsQuerier.QueryBaseJobRunTestStatus → getJobRunTestStatus → internalGenerateTestDetailsReport, replacing a previous static "no backfill" message with a dynamic one only shown when the aggregate fallback actually fired.
  • Distinguishes synthetic aggregate rows from real per-run rows implicitly, via an empty ProwJobRunID; assessTestStats now skips building a JobRunStats entry when that's empty.
  • BigQuery and Mixed providers, plus the releasefallback middleware, are updated only to satisfy the new interface signature — no behavior change on the BQ side.
  • Substantial new integration test coverage for the fallback query itself (prefix-sum, GA, precedence, variant filtering, multi-job, HAVING-filter behavior, metadata population).

Findings

Blocking

blocking All-or-nothing fallback gate breaks multi-test cache priming
pkg/api/componentreadiness/dataprovider/postgres/provider.go:168-186

QueryBaseJobRunTestStatus only triggers the aggregate fallback when the per-run query's combined result across the entire reqOptions.TestIDOptions set is empty. GenerateTestDetailsReportMultiTest (used to cache-prime all test details for a view) calls this once for potentially hundreds of test IDs. If even one test/job in that batch has any per-run data for the base release, the fallback is skipped for every other test in the batch — regressing them to all-zero base stats, the exact bug this PR sets out to fix.

result, errs := p.queryTestDetails(...)
if len(errs) > 0 {
    return result, nil, errs
}
if len(result) > 0 {
    return result, nil, nil
}
result, source, errs := p.queryBaseAggregateTestDetails(ctx, reqOptions)

Needs confirmation that target releases are always fully-backfilled-or-fully-absent as a whole; otherwise this gate needs to be per-test/per-job rather than batch-wide.

Should fix

should-fix "IsAggregate" from the PR description doesn't exist; empty ProwJobRunID used as an implicit sentinel
pkg/api/componentreadiness/test_details.go:562 · pkg/api/componentreadiness/dataprovider/postgres/provider.go:396-409

The PR/commit description states aggregate rows are "marked with IsAggregate=true," but no such field was added to crstatus.TestJobRunRows. Instead:

*testStats = testStats.AddTestCount(jobRow.Count, flakeAsFailure)
if jobRow.ProwJobRunID != "" {
    *jobRunStatsList = append(*jobRunStatsList, c.getJobRunStats(jobRow))
}

Traced both providers to confirm this is safe today: Postgres per-run rows always set ProwJobRunID from pjr.id, and BigQuery always sets it from junit.prowjob_build_id, which is guaranteed non-empty by an inner join. But it's an undocumented, implicit contract rather than the explicit flag described — a future data source that legitimately omits a run ID would be silently miscategorized with no compile-time signal.

should-fix No end-to-end test coverage for explanation propagation or JobRunStats exclusion
pkg/api/componentreadiness/component_report_test.go:1571-1638 · test/integration/component_readiness_test.go:1594-1112

The new TestQueryBaseJobRunTestStatus_AggregateFallback integration tests thoroughly cover the provider-level query in isolation, but nothing exercises the full pipeline: no test confirms baseExplanation actually reaches testdetails.Report.Analyses[*].Explanations, or that aggregate rows are excluded from JobStats.BaseJobRunStats while still contributing to BaseStats totals. The component_report_test.go edit adds a ProwJobRunID to every fixture row specifically to dodge the new skip branch, so that branch is unexercised at the unit level. The multi-test all-or-nothing concern above also has no covering test.

Questions

question Is the Postgres-only fallback intentionally exempt from the data-provider parity convention?
pkg/api/componentreadiness/dataprovider/bigquery/provider.go:93-111 · interface.go:27

The interface signature change touches BigQuery/Mixed providers, but the fallback behavior is Postgres-only (BQ always returns a nil explanation). Presumably intentional since this targets a Postgres-specific historical backfill gap — worth stating explicitly in the PR description.

Things I checked and was fine with

  • gofmt clean on all touched files.
  • Prefix-sum delta pattern (self-join with COALESCE, HAVING SUM(...) > 0) matches the existing pattern in queryTestStatusPrefixSum/cr_queries.go — not a new risk.
  • Only total_count delta is checked in the HAVING filter (not success/flake deltas) — matches existing precedent, not a regression introduced here.
  • Frontend (TestDetailsReport.jsx) already renders explanations generically; no frontend change needed.
  • No feature doc or README references this code path; the project's docs-in-same-PR rule isn't triggered.
  • Confirmed via a trace of the BigQuery query generator that ProwJobRunID is effectively always non-empty for legitimate per-run rows on both providers, so the new filter is a no-op for BQ.
