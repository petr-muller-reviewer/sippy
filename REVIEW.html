Verdict

Approve. This is a small, additive, well-scoped classification change that follows an existing established pattern exactly (mirrors the 4.22-LP-Interop--lpMainline view). The snapshot and test updates are consistent with the intended behavior, including the automatic JobTier downgrade. Only cosmetic nits remain.

What this PR does

  • Adds a new LayeredProduct classification value, lp-interop--OPP, matched via the job-name substring -interop-opp-.
  • Adds a new component-readiness view 4.22-LP-Interop--OPP in config/views.yaml, structurally identical to the existing 4.22-LP-Interop--lpMainline view.
  • Regenerates pkg/variantregistry/snapshot.yaml for the 5 real affected jobs (4.22 and 5.0 releases, aws/vsphere/upgrade), flipping LayeredProduct: none → lp-interop--OPP and JobTier: informing → candidate.
  • Adds two new table-driven test cases (aws, vsphere) verifying full expected variant maps for the new classification.

Findings

Nit

Inconsistent casing for the new LayeredProduct value

pkg/variantregistry/ocp.go:1374

{"-coo-", "lp-interop-coo"},
{"-acm-cnv-", "lp-interop--acm-virt"},
{"-acm-virt-", "lp-interop--acm-virt"},
{"-interop-opp-", "lp-interop--OPP"},

Every other entry in this pattern list is lowercase (lp-interop-coo, lp-interop--acm-virt, lp-ocp-compat--odf--lpGA), but this one uses lp-interop--OPP. Harmless functionally — matching runs on strings.ToLower(jobName) and the value is opaque — but it breaks the established lowercase convention for variant values that also propagate into config/views.yaml and snapshot.yaml.

Nit

Test job names don't match real job name shape

pkg/variantregistry/ocp_test.go:1802,1831

job: "periodic-ci-stolostron-policy-collection-main-ocp4.22-lp-interop-opp-aws"

Test fixtures use ...ocp4.22-lp-interop-opp-aws / ...vsphere, but the real jobs in snapshot.yaml are named ...ocp4.22-interop-opp-aws (no lp- segment). Both match the -interop-opp- substring so the tests still exercise the correct code path, but the fixture doesn't mirror production job naming.

Things I checked and was fine with

  • Pattern placement in setLayeredProduct (ocp.go:1371-1374): specific substring, no collision risk with other lp-interop-*/-virt/-cnv entries, correctly ordered before generic fallbacks.
  • snapshot.yaml diff: exactly the 5 real affected jobs (4.22 and 5.0 releases, aws/vsphere/upgrade) flip LayeredProduct: none → lp-interop--OPP.
  • JobTier: informing → candidate downgrade in the snapshot is expected/automatic via adjustJobTierBasedOnView (ocp.go:379) since the new LP value isn't in the main release view's include_variants — consistent with prior LP additions, not a manual/separate change.
  • config/views.yaml new view (4.22-LP-Interop--OPP) is a structural clone of 4.22-LP-Interop--lpMainline (same column_group_by/db_group_by/advanced_options); only include_variants.LayeredProduct differs.
  • No other files reference layered-product identifiers (lp-interop-coo, lp-interop--acm-virt, lp-ocp-compat--acs) outside the four changed files, so no missed touch points.
  • Two new table-driven test cases (aws, vsphere) cover full expected variant maps including the new field.

Open questions for the author

  • Was lp-interop--OPP casing intentional (branding/acronym), or should it be lp-interop--opp for consistency with sibling values?
