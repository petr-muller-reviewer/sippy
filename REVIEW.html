Request changes

The SQL rewrite collapsing the old self-join into a grouped CASE-WHEN prefix-sum aggregation drops prow_job_id and lifecycle from the GROUP BY, which can corrupt total_count/success_count/flake_count whenever a summary key exists at one end of the lookup window but not the other (e.g. a lifecycle reclassification) — this needs to be fixed or explicitly ruled out before merge. The remaining findings are duplication/maintainability concerns, not correctness blockers.

What this PR does

  • Introduces queryCombinedTestStatus, which folds the sample and base test-status queries into a single SQL statement using two materialized CTEs (sample_agg, base_agg) joined via UNION ALL, instead of running them as two separate queries.
  • Goal: eliminate concurrent partition scans / buffer cache contention from running sample and base queries in parallel against the same tables.
  • Rewrites the prefix-sum base-status query (prefixSumSpec) from a self-join pairing each key's start/end row to a grouped SUM(CASE WHEN date = end ...) - SUM(CASE WHEN date = start ...) aggregation.
  • Refactors join/filter construction (prepareVariantQuery, buildInnerAggregation, buildStatusCTE) but duplicates parts of it inline for the new combined path rather than fully reusing the existing helpers.

Findings

Blocking

Blocking prefixSumSpec GROUP BY drops prow_job_id/lifecycle, corrupting totals when a key vanishes across the window
pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:150 (GROUP BY), cr_queries.go:272-289 (prefixSumSpec CASE-WHEN) 
// buildInnerAggregation, cr_queries.go:150
GROUP BY e.test_id, e.suite_id, vg.group_id%s

// prefixSumSpec, cr_queries.go:277-284
selectCols: `SUM(CASE WHEN e.date = ? THEN e.prefix_sum_runs ELSE 0 END)
  - SUM(CASE WHEN e.date = ? THEN e.prefix_sum_runs ELSE 0 END) AS total_count, ...`

buildInnerAggregation's GROUP BY (test_id, suite_id, variant_group_id — no prow_job_id/lifecycle) is shared by prefixSumSpec, which computes SUM(end) - SUM(start) across the whole group. The prior self-join paired each (test_id, prow_job_id, suite_id, lifecycle) key's own start/end rows before subtracting. Now, a key present only at lookupStart (e.g. because it was reclassified to a new lifecycle key, which pkg/db/cumulativesummary/cumulative_summary.go's delete+insert design explicitly anticipates) still contributes its full start-of-window value to the group sum with nothing at lookupEnd to offset it.

Worked example: a test's lifecycle reclassifies from blocking to informing mid-window. Old key: prefix_sum_runs=500 at lookupStart, no row at lookupEnd. New key: prefix_sum_runs=50 at lookupEnd only.
Old (self-join) result: 50 - 0 = 50 — correct.
New (grouped CASE-WHEN) result: SUM(end)=50, SUM(start)=500 → total_count = 50 - 500 = -450.
Via WHERE agg.total_count > 0 this can also silently drop real data (MissingSample/MissingBasis) or understate counts when other jobs in the same group are positive.

Should fix

Should fix prow_jobs join template duplicated verbatim between two functions
cr_queries.go:246-250 (inline in queryTestStatusCTE) vs cr_queries.go:446-451 (prowJobJoinTemplate in queryCombinedTestStatus)
JOIN prow_jobs pj ON pj.id = e.prow_job_id

Identical join predicate exists in two places with no shared constant/helper. A future edit to the join is easy to apply once and miss in the other copy.

Both places independently decide gaSpec vs prefixSumSpec. A future change to GA-window eligibility applied to one call site and missed in the other would make the combined and releasefallback paths silently disagree for the same release.

Things I checked and was fine with

  • BigQuery provider parity: this PR only touches the Postgres provider; no BigQuery-side aggregation logic changed. (Worth separately checking whether BigQuery's equivalent aggregation has the same start/end-pairing assumption as the blocking finding above.)
  • No obvious formatting issues in the modified file.
  • The shared failureBranchTemplate/placeholderBranchTemplate UNION branch templates are unchanged and correctly shared, not duplicated.

Open questions for the author

  • Is dropping prow_job_id/lifecycle from the GROUP BY (cr_queries.go:150) intentional — is there a reason lifecycle reclassification can't happen within a lookup window in practice — or is this a regression from collapsing the self-join into CASE-WHEN aggregation?
  • Was this rewrite validated against the old self-join query's output on a dataset that includes a lifecycle transition or variant-combination change within the base/sample window?
  • Given the duplication between the two prow_jobs join templates, would it make sense to extract a single shared helper while both call sites are fresh?
