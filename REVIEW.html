Verdict: Needs Discussion

The approach is sound and the execution is careful, but the deployment ordering question needs resolution. Queries that dropped joins now depend entirely on denormalized columns being populated. If backfill hasn't run, several views and API endpoints will silently return incomplete results. The new commits make this more urgent by adding join table filters that actively query the denormalized columns on prow_job_run_prow_pull_requests.

  • Converts prow_job_run_prow_pull_requests from a GORM auto-managed join table to an explicit model with SetupJoinTable, enabling denormalized fields.
  • Updates seed data, test fixtures, benchmark queries, and the data loader to populate the new fields on insert.
  • Adds three plan documents describing the phased partitioning approach.

should fix Dropped-join queries break before backfill
pkg/db/functions.go:53, pkg/db/views.go:233,265,291, pkg/db/query/job_queries.go:76-80, pkg/db/query/test_queries.go:320-333

Several queries now filter solely on denormalized columns after dropping joins to prow_job_runs/prow_jobs. Historical rows with NULL/empty/zero denormalized columns will be silently excluded if deployed before backfill. Meanwhile, other queries in this same PR use the safer redundant-filter approach. The inconsistency means some pages degrade pre-backfill and others don't.

should fix historicalTestCount cache key bug — release-scoped counts keyed only by job ID
pkg/sippyserver/pr_new_tests_worker.go:235-244

pgJobRunFilter.historicalTestCount is map[uint]int, keyed by run.ProwJob.ID. But ProwJobHistoricalTestCounts now returns release-scoped counts (added in 912c2faec). If the same job ID appears across multiple releases, the first cached result is returned for all subsequent releases, corrupting the PR new-tests detection logic. Fix: composite cache key fmt.Sprintf("%d:%s", run.ProwJob.ID, run.ProwJob.Release) (spotted by CodeRabbit, 2026-06-03).

// Cache keyed only by job ID — stale if same job in multiple releases:
historicalCount, ok := jrf.historicalTestCount[run.ProwJob.ID]
if !ok {
    historicalCount, err = query.ProwJobHistoricalTestCounts(jrf.dbc, run.ProwJobID, run.ProwJob.Release)
    jrf.historicalTestCount[run.ProwJob.ID] = historicalCount  // should be "id:release"
}

Questions

question force_custom_plan is global — performance trade-off for non-partitioned queries
pkg/db/db.go:56-74

The new pgx adapter sets plan_cache_mode = "force_custom_plan" as a runtime parameter on all connections. This prevents PostgreSQL from caching generic plans for any prepared statement, not just the partitioned tables that motivated the change. Queries on small, non-partitioned tables lose plan reuse. For a system with many short repeated queries (cache lookups, variant registry queries, etc.) this could add per-query planning overhead. Was the global scope intentional, or was a per-query or per-table approach considered?

pgxConfig.RuntimeParams["plan_cache_mode"] = "force_custom_plan"

question GatherLabelsFromBQ date filter relaxed
pkg/dataloader/prowloader/prow.go:1133-1134

The batch refactor changed DATE(prowjob_start) = DATE(@StartTime) (exact date match) to DATE(prowjob_start) >= DATE(@ReleaseTime) (open-ended range). For the single-build-ID caller this is fine, but the batch form could scan a wider BigQuery partition range. There's no upper bound. The parameter was also renamed from StartTime to ReleaseTime — the caller passes pj.Status.StartTime, not a release time, so the name is misleading.

-- Before (single):
WHERE prowjob_build_id = @BuildID
  AND DATE(prowjob_start) = DATE(@StartTime)
-- After (batch):
WHERE prowjob_build_id IN UNNEST(@BuildIDs)
  AND DATE(prowjob_start) >= DATE(@ReleaseTime)
