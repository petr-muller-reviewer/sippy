Verdict

Needs discussion

The core change — adding lifecycle as a key column and fixing every self-join on test_cumulative_summaries to avoid a Cartesian blow-up — is correct and well tested. It's marked [WIP]/do-not-merge for a reason, and there's one real open question worth resolving before merge: the Postgres component-readiness provider doesn't wire up the Lifecycles filter that BigQuery already supports, which may or may not be in scope for this PR.

What this PR does

  • Adds a lifecycle (blocking/informing) column to test_daily_totals and test_cumulative_summaries, folded into both primary keys (migration 000011).
  • Daily/cumulative aggregation now groups by lifecycle from prow_job_run_tests.lifecycle, instead of collapsing blocking and informing results into a single row.
  • Fixes every self-join on test_cumulative_summaries to also match on lifecycle, preventing the new row-per-lifecycle split from turning into a cross-product that inflates counts.
  • Adds an integration test reproducing exactly that inflation scenario and asserting correct counts.
  • Updates the AI chat tool's schema documentation and example queries to mention the new column.

Findings

Should fix

should-fixPostgres CR provider doesn't apply the existing Lifecycles filter
pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:210-242 (queryTestStatusPrefixSum)

BigQuery's provider already filters sample results by lifecycle via reqOptions.Lifecycles (bigquery/querygenerators.go:497-503: AND COALESCE(NULLIF(lifecycle,''),'blocking') IN UNNEST(@Lifecycles)). This PR gives Postgres everything needed to do the same — the lifecycle column, correctly joined — but never references reqOptions.Lifecycles; the final GROUP BY still combines blocking+informing into one total. A caller setting testLifecycles would get filtered results from BigQuery and unfiltered results from Postgres. CLAUDE.md requires BigQuery/Postgres parity for data-provider query changes — though given the [WIP] label this may be intentionally deferred rather than an oversight.

Questions

questionPrimary key reorder on test_cumulative_summaries implies a full index rebuild
pkg/db/migrations/000011_add_lifecycle_to_summaries.up.sql:16-19

Beyond adding lifecycle, the migration reorders the PK from (date, release, ...) to (release, date, ...), aligning with the table's LIST by release, RANGE by date partitioning — reasonable, but it means a full PK rebuild on what's likely one of the largest tables in the schema. Worth confirming the production rollout plan (locking/duration).

ALTER TABLE test_cumulative_summaries

ALTER TABLE test_cumulative_summaries

Things I checked and was fine with

  • All self-joins on test_cumulative_summaries (cr_queries.go, cumulative_query.go, feature_gates.go, test_queries.go ×3) got the s.lifecycle = e.lifecycle fix — swept the whole codebase for other usages.
  • UpdateDateForRelease (cumulative_summary.go) correctly threads lifecycle through the FULL OUTER JOIN and the COALESCE(prev.lifecycle, tds.lifecycle, 'blocking') fallback.
  • pkg/api/test_analysis.go (untouched) only SUM()s test_daily_totals without a self-join or lifecycle grouping, so the new row split just re-combines into the same totals as before — not a bug.

  • gofmt -l clean on all modified Go files.
