Verdict

Approve

Correct, well-targeted fix for a real bug (SHA mismatch caused 82% of rows to never get merged_at set), consistent with existing code patterns in the file (temp-table COPY + bulk SQL idiom already used elsewhere). The one behavioral regression (partial progress discarded on rate-limit) is low severity and self-healing on the next scheduled run, so it doesn't block merging.

What this PR does

  • Adds MergedPR type and ListRecentlyMergedPRs to the GitHub client, returning Head.SHA (the real PR head commit) instead of the previously (incorrectly) used MergeCommitSHA.
  • Rewrites syncPRStatus from a per-row loop with individual Save() calls into a batch pipeline: distinct (org, repo) pairs → fetch recently-merged PRs per repo → COPY into a Postgres temp table → bulk UPDATE of merged_at and bulk DELETE of stale risk-analysis comment records.
  • Reuses the same lazy closedCache already used by IsPrRecentlyMerged.
  • Adds TestClient_ListRecentlyMergedPRs, explicitly asserting the returned SHA is Head.SHA and not MergeCommitSHA.

Findings

Should fix

Should fix Partial progress discarded on rate-limit error mid-loop
pkg/dataloader/prowloader/prow.go:840-856

The old per-PR loop called Save() immediately per row, so a later rate-limit error still left earlier rows durably updated. The new code accumulates all repos' results into allMerged in memory and only writes once at the end. If ListRecentlyMergedPRs hits a rate-limit error partway through the repos loop, the function returns early and everything already collected is discarded — nothing is persisted this cycle. Low severity since this loader runs periodically and unprocessed rows are simply retried next cycle.

for _, r := range repos {
    merged, err := pl.githubClient.ListRecentlyMergedPRs(r.Org, r.Repo)
    if err != nil {
        if pl.githubClient.IsWithinRateLimitThreshold() {
            return err
        }
        continue
    }
    ...
}

Nits

Nit Inconsistent join key between the two bulk statements
pkg/dataloader/prowloader/prow.go:895-908

The UPDATE joins the temp table to prow_pull_requests on sha alone, while the DELETE a few lines later joins pull_request_comments on the full (org, repo, number) tuple. SHA collisions across repos are practically impossible, so this isn't a correctness bug (and mirrors the original code's SHA-only matching) — but the asymmetry within the same function is worth a comment or aligning both on the full tuple.

UPDATE prow_pull_requests p
SET merged_at = t.merged_at, updated_at = NOW()
FROM tmp_merged_prs t
WHERE p.sha = t.sha AND p.merged_at IS NULL
...
DELETE FROM pull_request_comments c
USING (SELECT DISTINCT org, repo, number FROM tmp_merged_prs) t
WHERE c.org = t.org AND c.repo = t.repo AND c.pull_number = t.number
    AND c.comment_type = $1

Things I checked and was fine with

  • Core fix confirmed: ListRecentlyMergedPRs returns Head.SHA, not MergeCommitSHA — verified in code and asserted explicitly in the new test.
  • ClearPendingRecord/QueryPRPendingComments (replaced by the bulk DELETE) only touch the DB, not the GitHub API — the bulk DELETE is behaviorally equivalent.
  • db.CopyToTempTable + stdlib.AcquireConn/ReleaseConn usage matches the existing idiom already used in the same file (findNewJobRunIDs) and in bugloader.go/releasesync.go.
  • gofmt -l is clean and go build ./... passes for all three changed files.
  • Removed gorm import is correctly unused elsewhere in the file (gorm.io/gorm/clause is imported separately and still used).
  • No BigQuery equivalent of syncPRStatus/prow_pull_requests exists, so the provider-parity project rule doesn't apply here.
  • SQL is parameterized ($1 for comment_type); CopyToTempTable validates identifiers before building DDL.
  • New test covers not-merged PRs, missing Head, and cache reuse on second call.

Open questions for the author
