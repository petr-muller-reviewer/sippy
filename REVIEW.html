Verdict

Needs discussion — one real bug (missing HTTP status check on the symptoms fetch), one defensive gap worth raising. The rest is solid reuse of an existing component.

What this PR does

  • Reuses the TriageSymptoms component (previously triage-page only) on the test details report page.
  • Adds a useEffect in TestDetailsReport that counts symptom occurrences across sample job runs from data.analyses[0].job_stats, fetches symptom metadata from /api/jobs/symptoms, computes prevalence percentages, and passes the result to TriageSymptoms.
  • Makes the "Regressions" column in TriageSymptoms conditional: shown on the triage page (where regression_count exists), hidden on the test details page (where it doesn't).
  • Adapts tooltip text and filter button visibility based on which context the component is rendered in.
  • Makes setSymptomFilter prop optional (was .isRequired) since the test details usage doesn't need filtering.

Findings

Should fix — No HTTP status check on symptoms fetch

TestDetailsReport.js:237-239 
fetch(process.env.REACT_APP_API_URL + '/api/jobs/symptoms', {
  signal: controller.signal,
})
  .then((r) => r.json())

The response is unconditionally parsed as JSON without checking r.ok or the status code. If the API returns a 500 or 404, r.json() will either throw on a non-JSON body or silently parse an error payload, producing a bogus lookup table where no symptom IDs match. The result: symptoms display with raw IDs instead of summaries, with no error indication to the user.

Compare with the existing fetch pattern in the same file (lines 168-178) which explicitly checks data.code. At minimum, a if (!r.ok) throw new Error(...) guard would be consistent.

Nit — setSymptomFilter callable when undefined

TriageSymptoms.js:108-113 
onClick={() =>
  setSymptomFilter(
    symptomFilter === ss.symptom.id
      ? null
      : ss.symptom.id
  )
}

setSymptomFilter was changed from PropTypes.func.isRequired to PropTypes.func, but the click handler on the filter IconButton calls it without a guard. Currently safe because the button only renders when showRegressions is true (meaning regression data is present, meaning the triage page caller is in play, meaning the prop is always provided). But if someone later passes symptomSummaries with regression_count set without also providing setSymptomFilter, the click handler throws. Low risk, but worth a setSymptomFilter?.() or documenting the invariant.

Question — useEffect dependency on [data] object reference

TestDetailsReport.js:214-260

The symptom-counting effect depends on [data]. Since data is always a fresh object from setData(json), this works today: it re-runs once per data fetch. But the dependency is on object identity, not content. I'm not sure whether this was an intentional "re-run whenever data changes" choice or just the simplest thing. Worth confirming the author considered this — it's not a bug now, but it's the kind of thing that breaks quietly if someone adds a setData({...data, field: x}) call later.

Things I checked and was fine with

  • AbortController cleanup in the new useEffect — correctly returns () => controller.abort(), and the catch handler properly ignores AbortError.
  • Early return when data.analyses or job_stats is missing — correctly clears symptomSummaries to [].
  • showRegressions heuristic — checking symptomSummaries[0].regression_count !== undefined is a reasonable duck-type to distinguish triage vs. test-details context. Consistent across the header and body rows.
  • Existing Triage.js call site still passes all three props (symptomSummaries, symptomFilter, setSymptomFilter) — no regression there.
  • The total = totalRuns || 1 guard prevents division by zero.
  • Symptom ID used as fallback summary (lookup[id] || id) — acceptable degradation if the metadata fetch returns something unexpected.
  • Sort order (descending by job_run_count) makes sense for the UI.

Open questions for the author

  • The /api/jobs/symptoms fetch doesn't check r.ok before calling r.json(). Was this intentional, or should we add a status check consistent with the test details fetch above it?
  • Should setSymptomFilter use optional chaining (setSymptomFilter?.()) now that it's no longer required, or is the invariant "if regression_count is present, setSymptomFilter must be provided" intentional and worth documenting?
