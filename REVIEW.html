Verdict

Needs discussion — The partition management infrastructure is well-built with good safety measures, but there are two blocking issues: a copy-paste bug in range display and unclear migration sequencing for the model PK change. Several should-fix items around error handling and logging also need attention before merge.

What this PR does

  • Adds automated partition lifecycle management to the ProwLoader: creates future partitions, detaches old ones after 95 days, drops detached ones after 100 days.
  • Introduces a multi-step migration workflow (MigrateToPartitionedTable → UpdatePartitionedTableMigration → FinalizePartitionedTableMigration) for converting existing tables to partitioned ones.
  • Provides comprehensive partition utilities: listing, stats, retention validation, attach/detach/drop operations with safety checks.
  • Adds schema utilities for table column verification, FK relationship analysis and migration, atomic table renaming with sequence/constraint/index renaming.
  • Changes ProwJobRunTest and ProwJobRunTestOutput models from gorm.Model to explicit fields with composite PK (id, created_at) to support range partitioning.

Findings

Blocking

blocking OldestDate used where NewestDate intended

pkg/dataloader/prowloader/prow.go:443

Copy-paste error. The end-of-range display reads stats.OldestDate.Time inside a block guarded by stats.NewestDate.Valid. The partition range display will show the oldest date twice instead of showing oldest-to-newest.

if stats.NewestDate.Valid {
    endRange = stats.OldestDate.Time.Format("2006-01-02")  // should be NewestDate
}

blocking Model PK change needs migration sequencing clarity

pkg/db/models/prow.go:86-92, 109-115

Removing gorm.Model and switching the PK from (id) to (id, created_at) is a breaking schema change for the existing non-partitioned tables. The comments on both structs say "Do not update until after partitions have been enabled", yet this PR updates them. If GORM's auto-migrate runs against the existing table before the partition migration completes, it will attempt to alter the PK on a production table with hundreds of millions of rows.

// Do not update until after partitions have been enabled
// Remove gorm.model on Partitioned tables so we can manage the primary key and index
type ProwJobRunTest struct {
    ID        uint      `gorm:"primaryKey;autoIncrement"`
    CreatedAt time.Time `gorm:"primaryKey;index"`

The PR needs to clarify: does the partition migration run before this code deploys? Is auto-migrate disabled for these tables? What prevents this from breaking the existing schema?

Should Fix

should fix fmt.Printf in production code

pkg/dataloader/prowloader/prow.go:431, 445

preparePartitions uses fmt.Printf instead of log.Infof. This bypasses structured logging and won't appear in log aggregation systems. Every other function in this PR correctly uses logrus.

fmt.Printf("  Total: %d partitions (%s)\n", stats.TotalPartitions, stats.TotalSizePretty)
...
fmt.Printf("  Range: %s to %s\n", startRange, endRange)

should fix Partition failure blocks all data loading

pkg/dataloader/prowloader/prow.go:232-243

Any partition management error — including failing to detach a 95-day-old partition — aborts the entire load cycle. A failure to clean up old data should not prevent loading new data. Consider separating aging failures (detach/drop) from preparation failures (create new partitions), and only blocking on the latter.

for _, config := range partitionConfigs {
    err := pl.updatePartitions(config)
    if err != nil {
        pl.errors = append(pl.errors, err)
        return  // blocks ALL loading
    }
}

should fix Incomplete composite index idx_pjrt_run_test_status

pkg/db/models/prow.go:94, 101

The composite index idx_pjrt_run_test_status has priority:1 on ProwJobRunID and priority:3 on Status, with no priority:2 column. Either a column is missing or the priorities are wrong. GORM will create a two-column index but the gap in priorities is suspicious.

ProwJobRunID uint `gorm:"index;index:idx_pjrt_run_test_status,priority:1"`
...
Status   int `gorm:"index;...;index:idx_pjrt_run_test_status,priority:3"`

should fix OnDelete:CASCADE on soon-to-be-partitioned table

pkg/db/models/prow.go:106

ProwJobRunTestOutput still declares constraint:OnDelete:CASCADE, but this PR explicitly discusses removing FK cascades for partitioned tables. PostgreSQL cannot enforce cascading deletes across partitions in the standard way. Is this constraint declaration still correct?

ProwJobRunTestOutput *ProwJobRunTestOutput `gorm:"constraint:OnDelete:CASCADE;"`

Each file is 2100+ lines. FK operations, sequence operations, table rename logic, and column verification could be split into separate files for maintainability.

Questions

question DeleteTestsByName in a single transaction

pkg/db/migration.go:682-731

This deletes from 6 tables in a single transaction using LIKE patterns. For production-sized data (millions of matching rows), this could hold locks for extended periods and cause replication lag. Is this intended for one-off maintenance only, or could it run during normal operations?

Things I checked and was fine with

  • SQL injection prevention: pq.QuoteIdentifier used consistently for dynamic identifiers, sql.Named for values, escapeForLike for LIKE patterns.
  • Partition name validation (isValidPartitionName) properly restricts format to prevent accidental drops.
  • Transaction handling with proper rollback in defer across all mutation functions.
  • Retention policy validation (90-day minimum, 75% partition threshold, 80% storage threshold) is sensible.
  • NextDay removal is safe: the only caller was the inline partition creation in loadDailyTestAnalysisByJob, which is also removed.
  • strings import removal is correct: no other usage in prow.go after the inline partition SQL is removed.
  • Dry-run support is comprehensive throughout all destructive operations.

Open questions for the author

  • What is the expected deployment sequence? Does the partition migration (MigrateToPartitionedTable + Finalize) run before this code deploys, or does this PR need to handle the non-partitioned case?
  • Is the idx_pjrt_run_test_status index intentionally missing a priority:2 column, or should TestID (or another column) be included?
  • Should aging errors (detach/drop old partitions) really block the entire load, or can they be logged and continued past?
