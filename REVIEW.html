Needs discussion

The core optimization strategy is sound — the join reversal and use of denormalized partition columns match the table's actual partitioning scheme, and the day-walking findLastPass approach is a reasonable way to stay partition-aligned. However, two behavior changes (dropped deleted_at checks on prow_job_runs/prow_jobs, and a fixed 90-day last-pass lookback replacing the period-derived one) need explicit confirmation from the author before merge, and the rewrite currently ships with zero unit tests despite introducing several new non-trivial functions.

What this PR does

  • Reverses the main aggregation's join order: filters prow_job_run_tests by status/partition columns first, then joins tests/suites/test_ownerships onto the already-aggregated result.
  • Drops the prow_job_runs/prow_jobs joins from the main query, relying on denormalized prow_job_run_release/prow_job_run_timestamp columns instead (these are the actual partition keys).
  • Runs the COUNT and Scan queries concurrently via errgroup and cloned gorm.Sessions.
  • Scopes the findLastPass and fetchOutputs follow-up queries to only the current page (5–25 rows) instead of the whole result set.
  • Correlates everything on (test_id, suite_id) instead of test_id alone, fixing a pre-existing bug where suite was ignored.

Findings

Should fix

should-fixInconsistent deleted_at handling across query paths pkg/api/recent_test_failures.go:259-301, 313-364 vs 376-436

The original query filtered prow_job_runs.deleted_at IS NULL and prow_jobs.deleted_at IS NULL everywhere. The new main aggregation, its NOT EXISTS subquery, and findLastPass no longer join those tables and only check prow_job_run_tests.deleted_at. fetchOutputs still joins both tables and checks their deleted_at. If those tables are ever soft-deleted independently of prow_job_run_tests, failure counts / last-pass timestamps could include soft-deleted runs while outputs would exclude them.

FROM prow_job_run_tests pjrt
WHERE pjrt.status = ?
    AND pjrt.prow_job_run_release = ?
    AND pjrt.prow_job_run_timestamp >= ? AND pjrt.prow_job_run_timestamp < ?
    AND pjrt.deleted_at IS NULL
-- no prow_job_runs/prow_jobs join or deleted_at check, unlike fetchOutputs
should-fixfindLastPass lookback changed from period-derived to fixed 90 days pkg/api/recent_test_failures.go:326-328

Previously lastPassLookback was periodStart (or periodStart - previousPeriod), tied to the report's configured window. Now it's hardcoded to 90 days back from reportEnd. For any configuration where period + previousPeriod exceeds 90 days, this silently narrows the search and can return no last-pass where the old code would have found one.

endDate := civil.DateOf(reportEnd.UTC())
limitDate := endDate.AddDays(-90)
should-fixNo test coverage for new logic pkg/api/recent_test_failures.go:248-436

Substantial rewrite (buildRecentFailuresQuery, testSuiteKey, findLastPass, testIDsFromKeys, fetchOutputs) ships with zero unit tests. testSuiteKey construction and testIDsFromKeys are pure logic and should be table-driven tested; DB-dependent pieces fit the repo's existing functional-test-behind-env-var pattern.

type testSuiteKey struct {
    testID  uint
    suiteID uint // 0 represents NULL suite_id
}

Nits

nitfindLastPass worst case is 90 sequential per-day queries pkg/api/recent_test_failures.go:329-361

For a test that hasn't passed within 90 days, the loop runs all 90 day-partition queries before giving up. Fine for the common case (~3 iterations per the PR's own benchmarks), but a page dominated by never-passing tests could reintroduce a latency cliff. Worth a spot-check against a known always-failing test.

nitsuiteID 0 as NULL sentinel is implicit pkg/api/recent_test_failures.go:304-307

testSuiteKey{suiteID: 0} represents suite_id IS NULL. Verified Suite uses gorm.Model (auto-increment starting at 1), so this is safe in practice, but the invariant isn't documented beyond a one-word comment.

Questions

questionConcurrent Count/Scan via gorm Session cloning relies on non-obvious internals pkg/api/recent_test_failures.go:86-101

scanQuery/countQuery both derive from filteredQuery.Session(&gorm.Session{NewDB: false}) and run concurrently via errgroup. This avoids a data race only because Limit/Offset on scanQuery force gorm (v1.22.2) to clone its Statement before the goroutines are spawned; countQuery's clone happens lazily inside its own goroutine, reading (not writing) the shared original Statement. Correct today, but fragile if the pagination != nil guard changes or gorm's clone-on-write semantics change.

scanQuery := filteredQuery.Session(&gorm.Session{NewDB: false})
if pagination != nil {
    scanQuery = scanQuery.Limit(pagination.PerPage).Offset(pagination.Page * pagination.PerPage)
}
...
countQuery := filteredQuery.Session(&gorm.Session{NewDB: false})

Things I checked and was fine with

  • SQL injection via fmt.Sprintf embedding innerSQL into outerSQL: only static SQL text is interpolated, all dynamic values go through ? placeholders — no injection risk.
  • civil.Date passed directly as a query param in findLastPass: implements driver.Valuer (confirmed in vendored civil.go), works correctly with the postgres driver.
  • Denormalized prow_job_run_release/prow_job_run_timestamp columns replacing joined-table filters: these are the actual partition keys per the partitioned-tables migration, so the simplification is sound.
  • RecentTestFailure.SuiteID correctly threaded through GetNumericalValue for filter/sort parity.
  • Suite ID auto-increment starts at 1, making the suiteID: 0 NULL sentinel safe.

Open questions for the author

  • Is dropping the prow_job_runs/prow_jobs deleted_at checks in the main aggregation and findLastPass intentional, given fetchOutputs still applies them?
  • Should findLastPass's 90-day lookback instead be derived from period/previousPeriod as before, to avoid narrowing results for longer report windows?
  • Was go test -race run against the concurrent Count/Scan path to confirm there's no data race?
