Verdict: Request changes

The fix correctly stops the aggregate-fallback query from returning zero rows for older releases, but it does so by dropping the JobTier/Owner/CGroupMode/ContainerRuntime filters entirely rather than making them tolerant of missing data — nothing downstream re-applies those filters, so disallowed-tier jobs can now silently leak into base aggregate stats. A second, independent gap in the same function means an empty dbGroupBy silently disables all variant filtering, not just the newer keys. Worth resolving (or explicitly justifying as safe) before merge.

What this PR does

  • Fixes queryBaseAggregateTestDetails (fallback path used when prow_job_run_tests has no per-run data for the base release) returning zero rows for older releases (e.g. 4.21 in the 5.0-main view).
  • Root cause: the view's includeVariants (JobTier, CGroupMode, ContainerRuntime, Owner) was AND-ed wholesale into the SQL variant_combinations array-overlap filter, but older releases' rows lack those newer keys, so the filter always failed.
  • Fix: filterVariantsByDBGroupBy (variants.go) strips includeVariants down to only dbGroupBy keys before building the SQL WHERE clause.
  • PR is CLOSED (WIP label), never merged via GitHub (mergedAt/mergeCommit both null), but its single commit is already present on main.

Findings

Blocking

blockingvariants.go:171-183, provider.go:532, provider.go:667-713 (processAggregateRows), provider.go:84-105 (matchRequestedVariants) Stripped includeVariants keys are never re-applied, dropping JobTier/Owner/etc. filtering entirely in the aggregate fallback path

filterVariantsByDBGroupBy removes JobTier/Owner/CGroupMode/ContainerRuntime from the SQL filter, but nothing re-applies them afterward. processAggregateRows → matchRequestedVariants only checks (a) reqOptions.TestIDOptions[].RequestedVariants (a narrow single-test override) and (b) filterByDBGroupBy, which only labels the output key rather than excluding anything. matchesIncludeVariants (provider.go:119) does the correct check but is wired into an unrelated code path (provider.go:786), not into processAggregateRows. No earlier stage narrows candidate jobs by these keys either — IncludeVariants comes straight from view config (e.g. JobTier: [blocking, informing, standard], never in db_group_by). Net effect: aggregate base stats can now silently include jobs of any JobTier/Owner/CGroupMode/ContainerRuntime value. This also breaks parity with BigQuery's NewBaseTestDetailsQueryGenerator, which passes the full unstripped IncludeVariants.

func filterVariantsByDBGroupBy(includeVariants map[string][]string, dbGroupBy sets.Set[string]) map[string][]string {
    filtered := make(map[string][]string, dbGroupBy.Len())
    for k, v := range includeVariants {
        if dbGroupBy.Has(k) {
            filtered[k] = v
        }
    }
    return filtered
}
blockingvariants.go:175, provider.go:613-618,651-656 (buildAggregatePrefixSumQuery, buildAggregateGAQuery), pkg/api/utils.go:14-27 (VariantsStringToSet) Empty-but-non-nil DBGroupBy silently disables variant filtering entirely

VariantsStringToSet returns a non-nil empty sets.Set[string]{} whenever the dbGroupBy query param is absent/empty, not nil. filterVariantsByDBGroupBy then strips includeVariants down to {} since dbGroupBy.Has(k) is false for every key. Both SQL builders guard with if len(includeVariants) > 0, treating the emptied map as "no filter requested" rather than "filter matches nothing" — a caller intending to filter to e.g. Platform:aws/Network:ovn instead silently gets results summed across every combination in the release. This is distinct from the JobTier/Owner leak above: it applies to all includeVariants keys whenever dbGroupBy itself is empty.

Open questions for the author

  • Does any release actually have a mix of allowed/disallowed JobTier (or Owner) values among jobs that share the same dbGroupBy dimensions? If so, this fix as written will silently include disallowed jobs in base aggregate stats.
  • Should processAggregateRows re-apply matchesIncludeVariants (guarded on the key being present in the row's own variants, to avoid resurrecting the zero-rows bug) instead of dropping the constraint universally in SQL?
  • Can reqOptions.VariantOption.DBGroupBy actually be empty for requests that reach queryBaseAggregateTestDetails in production? If so, includeVariants filtering is silently disabled for those requests today.
