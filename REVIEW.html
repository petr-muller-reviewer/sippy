Verdict

Needs discussion

The core script remains small and follows the repo's existing shell-script conventions. The WIP label and self-approval suggest the author considers this ready, but the operational rough edges from prior reviews are still present — the hardcoded :latest image tag, an uninformative --dry-run, and the default-secret question — and the new REINDEX step adds a hardcoded database name and a more fragile, triple-escaped shell command. Nothing here is a proven correctness blocker (the escaping was hand-verified correct), but the hardcoded database name is a real failure mode if this script is ever pointed at a differently-named database.

What this PR does

  • Adds scripts/analyze-db.sh, which runs a post-restore "warmup" — ANALYZE VERBOSE followed by REINDEX DATABASE CONCURRENTLY — against the Sippy database via an oc run pod.
  • Supports --namespace, --db-secret, --wait, and --dry-run flags, defaulting to the sippy namespace and postgres-aws secret.
  • Hardens scripts/backfill-summaries.sh's argument parser so every flag that takes a value now errors clearly if the value is missing, instead of silently swallowing the next argument or a positional string.
  • Documents the new script's purpose, defaults, overrides, and the ANALYZE+REINDEX rationale (stale planner stats plus lazy-loaded EBS storage) in the root README.md.
  • Since previous review: pod command switched to sh -c to sequence a second psql call running REINDEX DATABASE CONCURRENTLY sippy_openshift; --wait timeout raised from 30m to 120m; PR self-approved with green CI, but its description/test plan weren't updated for the REINDEX addition.

scripts/analyze-db.sh:18

oc -n "$NAMESPACE" run "$POD_NAME" --restart=Never \

should-fix--dry-run output is uninformative (unresolved)

scripts/analyze-db.sh:39-42

Dry-run text was updated to mention the new step ("...to run ANALYZE VERBOSE and REINDEX") but still omits the namespace, secret, and image, so it still doesn't let an operator verify the invocation before running it for real — more important now that the pod also runs a REINDEX.

if [[ "$DRY_RUN" == "true" ]]; then

should-fixHardcoded database name in REINDEX, unlike the parameterized DSN (new)

scripts/analyze-db.sh:56

REINDEX DATABASE CONCURRENTLY sippy_openshift; hardcodes the database name while everything else (namespace, secret, DSN) is parameterized. Postgres requires REINDEX DATABASE to name the currently-connected database, so a DSN whose database isn't literally named sippy_openshift would fail this statement while the preceding ANALYZE VERBOSE (no name required) succeeds — a confusing partial failure.

"args": ["echo 'Starting ANALYZE VERBOSE...' && psql \"$SIPPY_DATABASE_DSN\" -c 'ANALYZE VERBOSE;' &&
  echo 'Starting REINDEX DATABASE...' && psql \"$SIPPY_DATABASE_DSN\" -c 'REINDEX DATABASE CONCURRENTLY sippy_openshift;' &&
  echo 'Warmup complete.'"]

nitTriple-nested string escaping for the pod command is fragile to review (new)

scripts/analyze-db.sh:55-56

The sh -c argument is escaped through three layers (bash double-quoted string → JSON string → shell metacharacters) to sequence two psql calls with &&/echo. I hand-traced the escaping and it is currently correct — but this is exactly the kind of construct where one missed backslash silently breaks quoting instead of erroring. Worth a comment on the escaping layers, or moving to a heredoc/ConfigMap to reduce depth.

"command": ["sh", "-c"],
"args": ["echo 'Starting ANALYZE VERBOSE...' && psql \"$SIPPY_DATABASE_DSN\" -c 'ANALYZE VERBOSE;' && ..."]

nitPod no longer self-removes; litter accumulates without --wait (unresolved)

scripts/analyze-db.sh:36,44

--rm is still dropped, so a run without --wait leaves the pod (running, then completed) in the namespace indefinitely — cleaned up only by the next invocation's delete-before-create step, or manually. Presumably intentional (README explains detached mode is for long warmup runs where the local machine shouldn't need to stay connected), but there's still no automatic GC and no mention of the tradeoff in the dry-run/help text.

POD_NAME="sippy-analyze-db"
IMAGE="registry.redhat.io/rhel9/postgresql-16:latest"
...
oc -n "$NAMESPACE" run "$POD_NAME" --restart=Never \

nitStatic pod name can still race under concurrent use (unresolved, now more consequential)

scripts/analyze-db.sh:36,44

POD_NAME="sippy-analyze-db" is still static. Now that the pod isn't --rm'd, a re-run while a prior detached run is still in progress collides more visibly: the delete-before-create step kills the in-flight ANALYZE+REINDEX from the previous invocation.

POD_NAME="sippy-analyze-db"
...
oc -n "$NAMESPACE" delete pod "$POD_NAME" --ignore-not-found --wait >/dev/null 2>&1 || true

nitDelete step still swallows all errors, not just not-found (unresolved)

scripts/analyze-db.sh:44

--ignore-not-found already makes a missing pod a non-error; the trailing || true still hides real failures (e.g. expired oc auth), letting the script proceed silently into oc run, where the failure then resurfaces less clearly.

oc -n "$NAMESPACE" delete pod "$POD_NAME" --ignore-not-found --wait >/dev/null 2>&1 || true

nitoc wait failure path suppresses its own stderr (unresolved)

scripts/analyze-db.sh:67-72

oc ... wait ... 2>/dev/null || { ... } discards the wait command's own error output (e.g. a propagation delay right after creation, or an RBAC error on watch), relying entirely on the fallback oc get pod status check. Most failure modes are covered by the fallback, but a wait-specific error (malformed jsonpath, permission denied) would be silently dropped. Timeout was raised 30m→120m in this update, unrelated to the stderr-suppression concern.

oc -n "$NAMESPACE" wait --for=jsonpath='{.status.phase}'=Succeeded --timeout=120m "pod/$POD_NAME" 2>/dev/null || {
    STATUS=$(oc -n "$NAMESPACE" get pod "$POD_NAME" -o jsonpath='{.status.phase}' 2>/dev/null || echo "Unknown")
    echo "Pod finished with status: $STATUS" >&2
    oc -n "$NAMESPACE" logs "$POD_NAME" --tail=20 2>/dev/null || true
    exit 1
}

questionIs postgres-aws the right default secret, and should it be required? (unresolved)

scripts/analyze-db.sh:22

backfill-summaries.sh requires --db-secret with no default (errors if unset); analyze-db.sh still silently defaults to postgres-aws. Worth confirming this default is intentional and correct for the target environment, rather than a divergence from the sibling script's stricter pattern.

DB_SECRET="postgres-aws"

Things I checked and was fine with

  • Hand-traced the new triple-escaped sh -c args string end to end (bash → JSON → container shell): it decodes correctly to psql "$SIPPY_DATABASE_DSN" -c 'ANALYZE VERBOSE;' && ... psql "$SIPPY_DATABASE_DSN" -c 'REINDEX DATABASE CONCURRENTLY sippy_openshift;', with the DSN properly double-quoted inside the container's shell. No injection or quoting bug found (see fragility nit above, though).
  • REINDEX DATABASE CONCURRENTLY is valid Postgres 12+ syntax and avoids the exclusive lock a plain REINDEX DATABASE would take — consistent with wanting this safe to run against a live-ish staging DB.
  • Credentials flow through secretKeyRef into the pod's env rather than being baked into the manifest, consistent with restore_prodlike_db.sh. Unchanged.
  • The backfill-summaries.sh flag-parsing fix ([[ $# -ge 2 ]] guards) is consistent with the file's existing style and error-message convention; unchanged by this refresh.
  • --wait timeout bump 30m→120m is a sensible adjustment given REINDEX CONCURRENTLY on a full database can run substantially longer than ANALYZE alone.
  • README addition/update is clear, matches the project's existing style (no header-heavy formatting, no em dashes), and now explains the EBS-lazy-loading rationale for REINDEX.
  • No unresolved human review threads; only CI/bot comments since the last review (self-approval notice, test scheduling, all tests passed on 2026-07-25).
  • PR description/test plan is stale (still describes ANALYZE-only, no mention of REINDEX or --wait) — noted as an open question below, not a code finding.

Open questions for the author

  • REINDEX DATABASE CONCURRENTLY sippy_openshift hardcodes the database name — will this script ever be pointed at a DSN/secret whose database isn't named exactly sippy_openshift? If not, this is fine; if so, it needs to derive the name from the DSN or a flag.
  • Should --image be added to analyze-db.sh for parity with backfill-summaries.sh's auto-detect/override pattern, and should the tag be pinned instead of :latest?
  • Should --dry-run print the full resolved oc run invocation (namespace, secret, image, and now the two-statement SQL) instead of just the pod name?
  • Is the postgres-aws default secret name confirmed correct, and should --db-secret be required the way it is in backfill-summaries.sh?
  • Now that the pod isn't --rm'd, is leftover-pod accumulation (when --wait isn't used) acceptable, or should the script warn about it / offer a cleanup flag?
  • Is the static POD_NAME collision risk (now more consequential since detached runs can be killed by a subsequent invocation, and runs are longer with REINDEX added) acceptable given expected usage patterns?
  • Can the PR description/test plan be updated to reflect the REINDEX step and --wait flag before merge?
