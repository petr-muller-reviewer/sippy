Verdict: Request Changes

The core BQ/PG routing and HATEOAS propagation work correctly and I found no SQL injection risk. But the PR is missing test coverage for its riskiest new code (hand-built SQL with manually-ordered bind args), silently bypasses the new toggle in three MixedProvider methods, ships a frontend default-state bug that shows the wrong active backend on first visit, and is missing the README updates this repo's conventions require. This lines up with the PR's own do-not-merge/work-in-progress label — good candidate to fix these before requesting full review.

What this PR does

  • Adds a validated dataSource query param (bigquery|postgres) so MixedProvider can route Component Readiness queries per-request.
  • Replaces PG's Go-side filtering with SQL push-down: a prefix-sum self-join over test_cumulative_summaries for arbitrary windows, and a GA-aligned path over prow_ga_raw_test_data (new 421-line file postgres/cr_queries.go).
  • Adds a parallel "existence/placeholder" query so PG grid cells with runs but no failures render NotSignificant instead of vanishing.
  • Bundles an orthogonal refactor: KeyWithVariants/ColumnIdentification switch from JSON-encoded map keys to a custom Encode().
  • Frontend: cookie-based BQ/PG toggle, dataSource propagated through query state and HATEOAS links, default base window bumped 27→30 days to match ga-30d configs.

Since previous review: two targeted bugfix commits landed, no new architecture or files.

  • f4a7251d7 removes SET LOCAL enable_nestloop = off from scanGroupedResults — it was unintentionally forcing a bad plan on the unrelated LATERAL last_failure subquery, a 142s-vs-3.5s warm-cache regression. Now relies on existing session tuning instead.
  • 37f6d3e58 fixes baseMatchesGAWindow to use GORM First instead of Pluck into *time.Time — Pluck silently failed to scan the date column, permanently forcing the slow prefix-sum fallback instead of the GA-optimized path. This introduces a new should-fix (below).

Blocking

BlockingMixedProvider bypasses dataSource toggle for variant/job-variant lookups
pkg/api/componentreadiness/dataprovider/mixed/provider.go:59-61,78-83
func (p *MixedProvider) QueryUniqueVariantValues(...) {
	return p.bq.QueryUniqueVariantValues(...)
}
func (p *MixedProvider) QueryJobVariantValues(...) {
	return p.bq.QueryJobVariantValues(...)
}
func (p *MixedProvider) LookupJobVariants(...) {
	return p.bq.LookupJobVariants(...)

These three methods are hard-wired to p.bq, unlike every other method which routes via providerFor(reqOptions). When a user selects dataSource=postgres, filter-dropdown population and job-variant lookups still hit BigQuery while the report data comes from Postgres — a parity gap the project's conventions explicitly call out as something to avoid, unless deliberately documented.

BlockingNew SQL push-down logic has zero test coverage
pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go (421 new lines), variants.go (206 new lines)
failureArgs := make([]any, len(joinArgs))
copy(failureArgs, joinArgs)
failureArgs = append(failureArgs, minimumFailure, release, start, end)

No unit tests for the pure-logic builders (buildVariantFilterClause, buildVariantGroupMapping, buildColumnGroupMapping) and no functional test against real Postgres, despite the repo having an established pattern for exactly this (releasesync_functional_test.go). The query builders assemble 3-4 layers of nested fmt.Sprintf SQL and hand-reconstruct matching []any arg slices in the same order, with nothing tying arg order to placeholder order at compile time or runtime. I traced both queries and today's ordering is correct, but a future edit reordering a WHERE/HAVING clause would silently desync args from placeholders — wrong data, no error, and nothing would catch it.

Should fix

Should fixPlaceholder/existence query can misattribute capability on grouped cells
postgres/cr_queries.go (placeholderOuterQuery, runFailureAndExistence)
const placeholderOuterQuery = `SELECT DISTINCT
    'grid:' || tow.component AS test_id,
    ...
    tow.capabilities,
    cm.col_group_id AS variant_group_id, ...`

SELECT DISTINCT is over (component, col_group_id) but still carries one real test's capabilities. Merged results are keyed by TestID+Variants only, so when multiple tests share a component+column with different capability sets, only one arbitrary capability set survives per synthetic placeholder row — on capability-grouped views this can attribute a NotSignificant placeholder to the wrong capability, or drop one. Not covered by the PR's manual test plan (which checked standard/cross-compare views, not capability drilldown).

Should fixGA-date lookup now warns on the routine "not yet GA" case
postgres/provider.go (baseMatchesGAWindow, commit 37f6d3e58)
var rd models.ReleaseDefinition
err := p.dbc.DB.WithContext(ctx).
	Select("ga_date").
	Where("release = ? AND ga_date < CURRENT_DATE", reqOptions.BaseRelease.Name).
	First(&rd).Error
if err != nil {
	log.WithError(err).WithField("release", reqOptions.BaseRelease.Name).
		Warn("failed to query GA date, falling back to prefix-sum query")
	return false
}

The fix (switching Pluck to First) is correct, but First returns gorm.ErrRecordNotFound whenever the release isn't GA yet — the normal, expected case for any pre-GA release or `ga-Nd` cross-compare view. The err != nil branch logs a warning unconditionally, so every request against a non-GA base release will now emit a misleading "failed" warning for routine, expected fallback behavior. Should distinguish ErrRecordNotFound (expected, no/low-level log) from other DB errors.

Questions

QuestionIs BQ-only routing for variant/job-variant lookups intentional?

Is the bypass in the three MixedProvider methods above deliberate (reference data assumed identical across backends), or an oversight?

QuestionIs the GA window day-truncation robust to future changes?

windowDays := int(End.Sub(Start).Hours() / 24) relies on End/Start being rounded to specific times of day so the ~30.9999-day span truncates to exactly 30. Verified correct today but undocumented — guaranteed by an invariant, or fragile?

QuestionShould BQ/PG grid-cell equivalence be tested explicitly?

BQ has no placeholder/existence mechanism; PG needs one because its push-down filters aggressively. This looks intentional, but is there a plan to assert BQ and PG produce identical NotSignificant cells for the same data before this leaves WIP?
