Overview

This PR extracts a DataProvider interface from the BigQuery-coupled Component Readiness implementation, adds a PostgreSQL implementation, rewrites the seed data command to generate deterministic synthetic data, and significantly expands e2e test coverage.

The BigQuery provider preserves existing production behavior while the Postgres provider enables local development and e2e testing without GCS/BigQuery credentials.

Architecture

The interface extraction is well-structured. dataprovider.DataProvider composes TestStatusQuerier, TestDetailsQuerier, MetadataQuerier, and JobQuerier — good separation of concerns.

  • bq package renamed to crstatus — types are now backend-agnostic
  • civil.DateTime → time.Time conversion in TestJobRunRows.StartTime and TestStatus.LastFailure makes types portable across backends
  • Middleware pattern for release fallback, regression tracking, link injection
  • GORM-based PostgreSQL queries with parameterized SQL

High Priority Issues

1. last_failure type assertion will panic

pkg/api/componentreadiness/query/querygenerators.go:783-793 — prowjob_start safely handles both civil.DateTime and time.Time via type switch, but last_failure hard-casts to civil.DateTime only. This will panic if BigQuery returns time.Time. Should use the same type-switch pattern.

Also flagged by CodeRabbit (Critical)

2. variantManager nil panic in postgres mode

cmd/sippy/serve.go:169-172 — variantManager is only initialized when bigQueryClient != nil. The /api/jobs/runs/risk_analysis endpoint is still reachable via LocalDBCapability and dereferences s.variantManager, causing a nil pointer panic in postgres-only mode. Initialize a no-op variant manager as fallback.

Also flagged by CodeRabbit (Critical)

3. Hardcoded release metadata in Postgres provider

pkg/api/componentreadiness/dataprovider/postgres/provider.go — the releaseMetadata map hardcodes GA dates and release relationships (4.17–5.0). This will need manual updates each release cycle and will drift. Consider deriving this from the database or configuration.

4. QueryReleases derives GA dates from current clock

postgres/provider.go:184 — every call shifts GADate forward because it uses the current time. This makes results non-deterministic and will produce different reports depending on when they're generated.

Also flagged by CodeRabbit (Major)

5. Production database safety check is fragile

cmd/sippy/seed_data.go:56 — strings.Contains(f.DBFlags.DSN, "amazonaws.com") is a weak guard against accidentally seeding production. Only catches AWS-hosted databases. Consider a more robust mechanism (e.g., an explicit --i-know-what-i-am-doing flag, or checking for a sentinel table/row).

6. ComponentReadinessCapability is too broad

pkg/sippyserver/server.go:414-416 — in postgres mode, this advertises and enables routes like /api/job/run/payload, /api/pull_requests/test_results, /api/tests/v2/runs, etc., but each handler immediately fails when s.bigQueryClient == nil. Should split into separate capabilities for CR-only vs. BigQuery-dependent routes.

Also flagged by CodeRabbit (Major)

Medium Priority Issues

7. successful_runs overcounting in BigQuery provider

bigquery/provider.go:236-250 — total_runs counts distinct build IDs, but successful_runs uses COUNTIF without deduplication. Pass rate can theoretically exceed 100%. Use COUNT(DISTINCT CASE WHEN ... THEN build_id END) instead.

Also flagged by CodeRabbit (Major)

8. Variant lookup failure masked as empty result

postgres/provider.go:397-418 — fetchJobVariants logs DB errors and returns {}. Callers see an empty report instead of the underlying failure. Should propagate the error.

Also flagged by CodeRabbit (Major)

9. Partial fallback data cached as success

middleware/releasefallback/releasefallback.go:384-404 — if one per-release goroutine fails, the error is only logged. Incomplete fallback data gets cached for the full TTL. Collect goroutine errors and avoid caching partial results.

Also flagged by CodeRabbit (Major)

10. Mixed release catalogs between request parsing and execution

pkg/sippyserver/server.go:190 — release catalog helper now prefers BigQuery, but componentreadiness may use the Postgres provider. Mixing catalogs could produce inconsistent behavior.

Also flagged by CodeRabbit (Major)

11. Hard-wired BigQuery provider in non-serve paths

cmd/sippy/load.go:321-323 and cmd/sippy/component_readiness.go:202-213 hard-wire bqprovider.NewBigQueryProvider instead of using the configured data provider. These paths won't work with postgres.

Also flagged by CodeRabbit (Major)

12. seed-data is not idempotent

cmd/sippy/seed_data.go:62 — the command bails if any prow_jobs row exists. Re-running can't refresh or repair a partial dataset. Should support a --force / --refresh flag or use upsert semantics.

Also flagged by CodeRabbit (Major)

13. Regression-tracker failures silently ignored in seed

cmd/sippy/seed_data.go:682-688 — tracker.Errors() is logged but not returned. Seeding reports success even when regression tracking failed.

Also flagged by CodeRabbit (Major)

14. N+1-style variant lookups in Postgres provider

queryTestDetails duplicates variant-fetching logic inline instead of calling fetchJobVariants. Consider extracting the shared pattern to reduce duplication and risk of divergence.

15. Reserved infra runs steal rows from max-sized scenarios

cmd/sippy/seed_data.go:518-565 — the global testableRuns value reduces every test's inserted rows by 2. When counts.total == runCount, this steals result rows. Should compute assignment limits per-test.

Also flagged by CodeRabbit (Major)

16. GCS client created unconditionally

cmd/sippy/serve.go — GCS client creation was moved outside the BigQuery conditional. A --data-provider postgres user will see warnings if no GCS credential file is present.

17. noOpCache error semantics

noOpCache.Get returns fmt.Errorf("cache miss") — verify callers treat this as a normal cache miss without error-level logging that could pollute output.

18. Shell script cache priming doesn't fail fast

scripts/e2e.sh:105-121 — jq failure inside the for VIEW in $(...) command substitution is not checked. Malformed /views output silently produces no iterations instead of failing. Should parse views into a checked variable first.

Also flagged by CodeRabbit (Major, duplicate across rounds)

19. Nil-check missing for provider in JiraAutomator

pkg/componentreadiness/jiraautomator/jiraautomator.go:73-77 — the constructor guards bqClient but not provider. getComponentReportForView will panic on nil dataProvider.

Also flagged by CodeRabbit (Nitpick)

Low Priority / Nits

20. Error details discarded in GetJobVariants callers

cmd/sippy/annotatejobruns.go:183-186 and cmd/sippy/automatejira.go:173-176 — underlying errors from GetJobVariants are dropped. Return "failed to get job variants: %v", errs instead.

21. TestKey fields missing bigquery:"-" tags

pkg/apis/api/componentreport/crstatus/types.go:56-57 — TestKey and TestKeyStr are local bookkeeping fields, not query columns. Add bigquery:"-" to be explicit.

22. Generated views file committed to the repo

config/e2e-views.yaml is a generated file checked into the repo. The seed-data command overwrites it via writeSyntheticViewsFile(). Running seed-data locally will dirty the working tree. Consider .gitignore-ing it or generating to a temp path.

23. Leftover comment

component_report_test.go:3065 has a comment about a moved test that is no longer useful.

24. Non-deterministic variant ordering

variantMapToArray iterates a map non-deterministically — add sort.Strings(result) for reproducible output.

25. Datasync e2e test missing error assertions and timeout

test/e2e/datasync/datasync_test.go:23 — sippy load output errors are not asserted. Should add DB error assertions and a timeout to avoid flaky/hanging e2e runs.

Also flagged by CodeRabbit (Major)

26. Coverage build overhead

Coverage infrastructure adds build time via a second binary in the Dockerfile. Acceptable for CI, but worth noting.

Verdict

Solid refactoring that properly abstracts the data layer. The interface design is clean and the test coverage improvements are substantial.

Since initial review, CodeRabbit surfaced several additional issues worth attention: the last_failure panic path (#1), variantManager nil crash in postgres mode (#2), successful_runs overcounting (#7), and several error-swallowing patterns (#8, #9, #13). The new commits are CI plumbing fixes and don't change the core architecture.

Main blockers before merge: fix the two panic paths (#1, #2), address the overbroad capability registration (#6), and decide on the release metadata strategy (#3, #4). The remaining items are quality improvements that can be addressed incrementally.
