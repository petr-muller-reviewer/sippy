Verdict

Request changes

The performance approach is sound and well-benchmarked, and the date-boundary math (hand-verified) is correct and consistent between the two returned counts. But there's a real goroutine leak on the errgroup error path, an unnecessarily indirect fan-in mechanism that's the source of that leak, and a latent correctness risk from querying date = today in test_cumulative_summaries without the defensive "clamp to latest available date" pattern every other caller in the codebase uses. None are blockers for the happy path, but all should be fixed before merge given this runs on every refresh cycle.

What this PR does

  • Replaces the single COUNT(DISTINCT) query against prow_job_run_tests (~70M rows, no partition pruning) with two targeted queries.
  • Job-run count now comes from a direct COUNT against prow_job_runs (indexed on timestamp, much smaller table).
  • Test-ID count is computed per-release via a self-join on test_cumulative_summaries (pre-aggregated by test_id before joining), run concurrently across releases (errgroup, concurrency 4) and merged into a dedup set in Go.
  • Refactors the function into GetJobRunTestsCountByLookbackAt(dbc, lookbackDays, today civil.Date) for deterministic testing, with the original name as a thin wrapper.
  • Adds a substantial new integration test suite exercising cross-release dedup, zero/negative delta exclusion, missing prior-day rows, soft-deleted runs, and multi-job aggregation.

Findings

should-fixGoroutine leak when an errgroup release query fails

pkg/api/tests.go:419-465

ch is only closed on the success path (line 464). If g.Wait() returns an error, the function returns immediately without closing ch. The background collector goroutine (for ids := range ch, lines 421-427) then blocks forever, since the channel is never closed. The buffered channel's capacity equals len(releases), so non-failing goroutines' sends never block on it — meaning every send from a completed goroutine has already landed by the time g.Wait() returns, and the leak is real, not masked by a deadlock. This function runs on every RefreshData cycle, so a transient per-release failure leaks a goroutine each time.

if err := g.Wait(); err != nil {
    return -1, -1, err
}
close(ch)
<-done

Fix: close (and drain) before checking the error, e.g. err := g.Wait(); close(ch); <-done; if err != nil { return -1, -1, err }.

should-fixChannel/collector-goroutine fan-in is unnecessary indirection

pkg/api/tests.go:419-427,457,464-465

The channel plus separate collector goroutine exists only to merge per-release []int64 results into a sets.Set[int64]. A sync.Mutex guarding testIDs.Insert(ids...) called directly inside each g.Go closure gives the same result with less code, no channel lifecycle to manage, and removes the leak above entirely — there's nothing to forget to close. It would also be more consistent with the simpler errgroup fan-out pattern already used in pkg/api/job_runs.go.

ch := make(chan []int64, len(releases))
testIDs := sets.New[int64]()
done := make(chan struct{})
go func() {
    for ids := range ch {
        testIDs.Insert(ids...)
    }
    close(done)
}()

should-fixNo defensive clamp to MAX(date) before querying date = today

pkg/api/tests.go:434-451

Every other caller that self-joins test_cumulative_summaries (pkg/db/query/cumulative_query.go's resolvePrefixSumDates, pkg/db/query/feature_gates.go:18-24) first clamps via ResolveDateRanges to the latest available date for the release, because "today"'s cumulative row only exists once cumulativesummary.Refresh completes for the day. This PR queries date = ? with the literal today value, with no such clamp.

WITH end_sums AS (
  SELECT test_id, SUM(prefix_sum_runs) AS total_runs
  FROM test_cumulative_summaries
  WHERE release = ? AND date = ?
  GROUP BY test_id
),

It's currently safe only because the sole call site (refreshMaterializedViews, server.go:411) runs strictly after cumulativesummary.Refresh inside RefreshData (server.go:399-411). That ordering is an implicit invariant, not an enforced one — any future caller invoked before the daily refresh completes will silently undercount rather than error.

nitConfusing variable name startMinusOne

pkg/api/tests.go:391

It's not "start minus one" — it's "the day before the window's exclusive start boundary" for the prefix-sum delta. Something like windowStartExclusive would read more clearly against the P(End) - P(Start) convention used elsewhere.

startMinusOne := today.AddDays(-lookbackDays - 1)

questionNo parity test between the two count windows

test/integration/lookback_count_test.go

The new tests cover cross-release dedup, zero/negative delta exclusion, missing prior-day rows, soft-deleted runs, and multi-job aggregation individually, but nothing directly asserts that jobRunsCount's window and testIDsCount's window cover the same span (they do, per manual verification — but it's easy to regress silently since the two counts come from separately-computed boundaries).

Things I checked and was fine with

  • Date-boundary math for both counts hand-verified against the P(End-1) - P(Start-1) convention in cumulative_query.go — consistent, no off-by-one between the job-run and test-ID windows (both resolve to a lookbackDays+1-day span).
  • prow_job_runs soft-delete: using .Table() bypasses GORM's automatic scope, so the explicit deleted_at IS NULL clause is required and correct; covered by TestLookbackCount_JobRunsCountExcludesDeleted.
  • SQL injection: release values are parameterized bind params sourced from release_definitions, not user input.
  • Loop variable capture in g.Go(func() error { ... release ... }) — safe under Go 1.25 per-iteration loop var semantics (confirmed via go.mod).
  • Structured logging (log.WithField(s)) used instead of Infof string formatting, per project convention.
  • sets.New[int64]() used for dedup per project convention (no hand-rolled map[string]bool).
  • No BigQuery counterpart exists for GetJobRunTestsCountByLookback, so the CLAUDE.md provider-parity rule does not apply here.
  • gofmt/style of new code visually consistent with the rest of the file (could not run gofmt/go vet directly — toolchain unavailable in this sandbox).

Open questions for the author

  • Is there a reason GetJobRunTestsCountByLookbackAt doesn't clamp to MAX(date) like ResolveDateRanges does elsewhere, or is refreshMaterializedViews's post-cumulative-refresh call order considered a sufficient guarantee going forward?
  • Was the goroutine-leak-on-error path noticed during benchmarking, or did all iterations succeed so it never triggered?
  • Any reason to prefer the channel-based fan-in over a mutex-guarded set insert, given the latter is both simpler and avoids the leak?
