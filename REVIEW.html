Verdict: Needs discussion

The core migration infrastructure (the pkg/db/migrate package, SQL migrations, CLI commands, and e2e tests) is well-designed and sound. However, the PR bundles several unrelated changes (MCP server rewrite, frontend symptom removal, variant registry tier changes, lint script changes) that make independent review difficult and increase merge risk. I'd like to discuss splitting those out, and there are a few specific issues worth addressing before merge.

What this PR does

  • Introduces golang-migrate/migrate to manage tables GORM can't handle (partitioned tables), replacing the old syncPartitionedTables imperative approach with versioned, embedded SQL migrations.
  • Adds baseline detection: on existing databases that predate golang-migrate, stamps the migration version without re-running DDL.
  • Adds CLI subcommands (migrate version, migrate force, migrate down) for operational control.
  • Includes e2e migration tests verifying up/down/force/version lifecycle and that the shared GORM connection survives migration operations.
  • Bundles: MCP server rewrite (async→sync, removed tools), frontend symptom aggregation removal, variant registry tier promotions, lint script changes, test URL updates.

Findings

should fix Two migrate instances created in baseline path

pkg/db/migrate/migrate.go:101-118

When baseline stamping is needed, two separate migrate.Migrate instances are created — one for the Force() call and another for the subsequent Up(). Each opens its own postgres driver instance. A single instance with Force() then Up() would avoid the redundant allocation.

m, cleanup, err := newMigrate(gormDB)
...
if err := m.Force(baselineVersion); err != nil {
...
// second instance created here:
m, cleanup, err := newMigrate(gormDB)
...
if err := m.Up(); err != nil && err != migrate.ErrNoChange {

should fix Redis DB isolation removed in e2e

scripts/e2e.sh:73

Previously e2e used redis://sippy-redis:6379/1 (logical DB 1) to isolate from dev's DB 0. Now it uses the default DB 0 with no isolation. If a dev sippy serve and e2e run concurrently, they share the Redis keyspace, risking flaky tests. The explanatory comment was also removed.

-    export REDIS_URL="${SIPPY_E2E_REDIS_URL:-redis://sippy-redis:6379/1}"
+    export REDIS_URL="${REDIS_URL:-redis://sippy-redis:6379}"

should fix MCP silently ignores missing BigQuery creds for bigquery provider

mcp/server.py:343-345

Previously, calling sippy_serve with data_provider=bigquery without credentials returned a clear early error. Now the error is discarded (creds_path, _ = ...), the server starts without credentials, and crashes later with an opaque error.

-    creds_path, creds_err = _resolve_bigquery_creds(bigquery_credentials_file)
+    creds_path, _ = _resolve_bigquery_creds(bigquery_credentials_file)
     if creds_path:
         args.extend(["--google-service-account-credential-file", str(creds_path)])
-    elif data_provider == "bigquery":
-        return f"BigQuery credentials required for data_provider=bigquery: {creds_err}"

nit errors.Is vs == for sentinel errors

cmd/sippy/migrate.go:48 and pkg/db/migrate/migrate.go:118,123,157,179,184

Multiple places use ==/!= to compare against gomigrate.ErrNilVersion and migrate.ErrNoChange. While golang-migrate currently returns bare sentinels, errors.Is is idiomatic Go and future-proof against wrapping.

if err == gomigrate.ErrNilVersion {
if errors.Is(err, gomigrate.ErrNilVersion) {

question Scope of the PR

(whole PR)

The PR bundles migration infrastructure with: MCP server rewrite (async→sync, removed restore_prodlike_db/run_e2e tools, removed python-dotenv), frontend symptom aggregation removal from TestDetailsReport.js, variant registry tier promotions (vsphere hybrid-env → standard), lint script changes, e2e test URL updates. These are independent concerns that would be easier to review and safer to merge separately.

Things I checked and was fine with

  • Migration SQL is idempotent (CREATE TABLE IF NOT EXISTS, CREATE INDEX IF NOT EXISTS) — correct for baseline case.
  • Baseline detection logic: checks schema_migrations absence + test_analysis_by_job_by_dates presence before stamping — sound approach.
  • Connection preservation: cleanup function only closes iofs source, not the underlying *sql.DB — correct.
  • E2e migration tests use isolated tracking table (e2e_schema_migrations) — no interference with production migrations.
  • down migration drops entire partitioned table including partitions — expected, consistent with up.
  • Embedded SQL via //go:embed *.sql in migrations.go — standard pattern.
  • CLI subcommands (version, force, down) wire flags correctly via f.BindFlags.
  • go 1.25 → go 1.25.0 — no functional change.
  • Vendor diff is solely from the golang-migrate dependency and its transitive deps.

Open questions for the author

  • Is there a reason the baseline stamping and the subsequent Up() use two separate migrate.Migrate instances instead of reusing one?
  • Was the Redis DB isolation removal in e2e intentional? What prevents keyspace collisions with concurrent dev servers?
  • Should the MCP sippy_serve tool still validate BigQuery credentials when data_provider=bigquery is explicitly requested?
  • Are the bundled changes (MCP rewrite, frontend, variant registry) intended for this PR, or could they be split out?
