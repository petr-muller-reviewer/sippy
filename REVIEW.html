Verdict

Approve.

Straightforward removal of dead columns from two query paths. The columns were selected but never consumed by their respective deserializers. No functional change, reduces BigQuery bytes scanned.

What this PR does

  • Removes test_suite, file_path, and capabilities from the BigQuery buildTestDetailsQuery SELECT clause. These columns were returned but never parsed by deserializeRowToJobRunTestReportStatus.
  • Removes capabilities from the PostgreSQL testDetailRow struct and testDetailQuery SELECT, where the field was selected but never accessed in the row-processing loop.
  • Keeps file_path in the BigQuery GROUP BY clause to preserve correct aggregation semantics (valid SQL, intentional).
  • Removes stale TODO comments about unused columns and outdated debug log references in comment blocks.

Findings

No findings. The change is mechanical and correct.

Things I checked and was fine with

  • file_path remaining in GROUP BY (line 623) after removal from SELECT: valid BigQuery SQL, explicitly called out in the PR description as intentional.
  • deserializeRowToTestStatus still handles test_suite (line 805) and capabilities (line 824): this is correct because that deserializer serves BuildComponentReportQuery, which still selects those columns. The test details path uses a different deserializer (deserializeRowToJobRunTestReportStatus, line 1051) that never referenced the removed columns.
  • Both BigQuery deserializers use name-based column matching via fieldSchema.Name, not positional indexing. Removing columns from SELECT cannot cause index-shift bugs.
  • PostgreSQL testDetailRow.Capabilities was selected into the struct but the field was never read in the row-processing loop. Safe to remove.
  • Provider parity is maintained: neither BigQuery nor PostgreSQL test details queries now return these unused columns. The test status queries (which do use test_suite and capabilities) are untouched in both providers.
