Verdict

APPROVE

Test-only PR that adds thorough, correct integration coverage for the payload query functions. I verified the trickier boundary-condition assertions (inclusive vs. exclusive comparisons against reportEnd, the 14-day window behavior) directly against the SQL and they all check out. Only issue is a small amount of dead fixture code, which is a should-fix, not a blocker.

What this PR does

  • Adds 53 integration tests covering all 11 functions in pkg/db/query/payload_queries.go, no production code touched.
  • Fills a real gap: 8 new tests for GetTestFailuresForPayloadStream, previously untested (6-table join, array aggregation, 14-day window).
  • Explicitly tests boundary semantics (< vs <= against reportEnd) across several functions, and documents where a function has no upper bound at all rather than assuming a bug.
  • Extends test/integration/util/fixtures.go with a functional-options pattern for building test fixtures without breaking existing call sites.
  • CI is fully green (lint, unit, e2e, build, verify, security).

Should fix

Unused fixture options added

test/integration/util/fixtures.go:129-135
func WithPreviousReleaseTag(prev string) ReleaseTagOption {
	return func(rt *models.ReleaseTag) { rt.PreviousReleaseTag = prev }
}

func WithForced(forced bool) ReleaseTagOption {
	return func(rt *models.ReleaseTag) { rt.Forced = forced }
}

WithPreviousReleaseTag and WithForced are added but never used anywhere in this PR or the rest of the repo. Given the PR's goal is exhaustive coverage of existing functions, this looks like dead code — either drop them, or (more likely intended) use WithPreviousReleaseTag in the GetPreviousPayload tests.

Inconsistent constructor style

test/integration/util/fixtures.go:1408-1420 (CreateReleaseJobRun)

CreateProwJobRun, CreateReleaseTag, and CreateReleasePullRequest all gained a variadic ...Option parameter in this PR, but CreateReleaseJobRun still takes everything positionally. Not a functional problem given its current single call-site pattern, just an inconsistency worth noting for future edits.

Questions

question

No "nonexistent payload" empty-result case for GetTestFailuresFor*

TestGetTestFailuresForPayload_NoFailures covers an existing payload with no job runs, but there's no test for a payload tag/release combo that doesn't exist at all. Probably a non-issue (the SQL naturally returns empty), but worth a quick confirmation it was a deliberate omission.

  • No DB client mocking — tests run against real Postgres via testcontainers-go (intutil.NewTestDB), per project convention.
  • Table-driven test used for GetLastPayloadStatus phase-streak cases, consistent with existing repo patterns.

  • Boundary conditions verified line-by-line against payload_queries.go:
