Verdict

Approve.

Well-structured preparatory PR that introduces explicit spot-check classification with component/capability metadata, replacing the generic "rare" tier. The separation of classification from tier assignment is clean, validation is placed at both code paths, and the snapshot updates are mechanically consistent across all releases and platforms. Only minor nits below.

What this PR does

  • Introduces two new variant constants (SpotCheckComponent, SpotCheckCapability) that tag spot-check jobs with their Component Readiness component and capability.
  • Adds a new setter setSpotCheckClassification that matches cpu-partitioning and etcd-scaling jobs by name and assigns the new variants.
  • Modifies setJobTier to auto-assign spotcheck-30d tier when a job has spot-check classification, removing the old rare pattern entries.
  • Adds validateSpotCheckVariants as a safety net: any job with a spotcheck-* tier must have both component and capability defined. Validation runs in both DB-driven and snapshot-driven code paths.
  • Updates ~50 snapshot entries consistently from rare to spotcheck-30d with appropriate component/capability values.

Findings

Nit Stale comment on VariantJobTier constant

pkg/variantregistry/ocp.go:465

VariantJobTier             = "JobTier"      // specifies rare, blocking, informing, standard jobs

The inline comment still lists rare as a tier. The setJobTier godoc was correctly updated to list spotcheck instead, but this comment was missed.

Nit No direct unit test for validateSpotCheckVariants error path

pkg/variantregistry/ocp.go:279-286

func validateSpotCheckVariants(jobName string, variants map[string]string) error {
	if strings.HasPrefix(variants[VariantJobTier], "spotcheck-") {
		if variants[VariantSpotCheckComponent] == "" || variants[VariantSpotCheckCapability] == "" {
			return fmt.Errorf(...)
		}
	}
	return nil
}

The happy path is tested indirectly via TestVariantSyncer, but there is no test that verifies the error is returned when a job has spotcheck-30d tier but is missing one or both of the spot-check variants. Since this validation is a safety net for future classification errors, a small table-driven test covering the error path would add confidence.

Nit spotCheckPatterns substrings slice always has one element

pkg/variantregistry/ocp.go:767-774

spotCheckPatterns := []struct {
	substrings []string
	component  string
	capability string
}{
	{[]string{"-cpu-partitioning"}, "Node / Kubelet", "CPU Partitioning"},
	{[]string{"-etcd-scaling"}, "Etcd", "Scaling"},
}

Each entry uses substrings []string but only ever contains a single element. This mirrors the existing jobTierPatterns convention, so it's fine for consistency. Could be simplified to a single string if multi-match is confirmed unnecessary.

Things I checked and found fine

  • All snapshot.yaml entries consistently updated: rare → spotcheck-30d, correct component/capability per job type across all releases (4.12–5.0) and all platforms including shiftstack OpenStack jobs.
  • adjustJobTierBasedOnView correctly handles spotcheck-30d: the tier is not in any view's include list, so the !tierIncluded early return preserves it without downgrade. The existing test case was updated to verify this.
  • setSpotCheckClassification is placed before setJobTier in the setter chain (line 507 vs 508), so the component variant is guaranteed to be set before setJobTier checks for it.
  • No remaining "rare" references in config YAML/JSON files.
  • Validation is added to both code paths: the DB-driven Identify() in ocp.go and the config-driven Identify() in snapshot.go.
  • View configs in config/views.yaml intentionally do not include spotcheck-30d — views opt in, matching the PR description and the setJobTier godoc.
  • Validation errors are sorted for deterministic output (latest commit).
