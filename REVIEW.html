Verdict: Request changes

Well-engineered performance optimization with solid testing and clear documentation of trade-offs. One compilation break blocks merge. The rest are minor observations and questions for the author.

What this PR does

  • Adds a test_daily_summaries table that pre-aggregates prow_job_run_tests (~100M+ rows) into daily buckets per (test_id, prow_job_id, suite_id, release, date).
  • Rewrites the test report matview definitions (prow_test_report_7d_matview, prow_test_report_2d_matview) to read from the summary table instead of scanning raw rows.
  • Runs daily summary refresh automatically before matview refreshes as part of RefreshData().
  • Adds CLI flags (--rebuild-daily-summaries, --daily-summaries-start, --daily-summaries-end) to the sippy refresh command for manual control.
  • Quantizes matview time boundaries from exact timestamps to calendar-day (midnight UTC) boundaries, trading ~1 day of boundary precision for 2-3x faster refreshes.

Question Stale summaries after source data deletion

pkg/db/dailysummary/dailysummary.go:27-50

If rows are deleted from prow_job_run_tests, orphaned summary rows persist with old counts. The upsert INSERT...SELECT only produces rows for data that currently exists, so deleted-source rows are never corrected. Append-only ingestion makes this unlikely, and --rebuild-daily-summaries covers the exceptional case. Worth a sentence in docs for operators?

Question CASCADE commit overlap with #3658

pkg/db/views.go:156

This PR carries the CASCADE change that is also PR #3658. If #3658 merges first and this is rebased, the change becomes a no-op in the diff. Is the plan to squash, or will #3658 be dropped in favor of this PR carrying it?

Things I checked and was fine with

  • suite_id=0 for NULL suites. COALESCE(suite_id, 0) in upsert + LEFT JOINs to suites and test_ownerships behave identically for id=0 as for NULL (no match, NULL result). Semantics preserved.
  • Date boundary precision. DATE-to-TIMESTAMP comparisons can exclude up to ~1 day at window start. Documented in PR description, acceptable for trend analysis. Midnight-aligned pinned times avoid it entirely.
  • runs column. Counts all rows via COUNT(*) including non-success/failure/flake statuses. Consistent with original matview behavior.
  • valueColumns slice. Generates both SET and WHERE clauses in upsert, preventing column drift between them.
  • Per-release aggregation loop. Avoids 51s planner overhead on 3553 sub-partitions. Well-motivated by benchmarks.
  • Non-fatal daily summary failure. server.go:393-394 logs error and continues matview refresh with stale data.
  • Migration idempotency. IF NOT EXISTS on both table and indexes. Down migration drops cleanly.
  • All RefreshData call sites updated (load.go, refresh.go, seed_data.go, updatesuites.go) except the benchmarking test.
  • No data pruning. Summaries accumulate indefinitely. At a few hundred rows per release per day, stays small for years. summary_date index keeps 14-day filter selective.
  • TestDailySummary model in prow.go matches migration schema.
  • Test coverage. 11 tests cover incremental, caps-at-yesterday, empty-table lookback, rebuild, date overrides, all error paths, and no-releases edge case.
