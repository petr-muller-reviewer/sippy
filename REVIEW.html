Request Changes
One silent error discard and a FirstOrCreate/upsert inconsistency in seed data both warrant fixes before merge. The rest of the findings are nits or questions that can be addressed at the author's discretion. The core approach — syncing BQ release rows into PG and wiring the server/provider to read from there — is sound and the staging verification is thorough.

What this PR does

  • Introduces a release_definitions PostgreSQL table to store release metadata (GA dates, dev start, capabilities, product, status) previously only in BigQuery.
  • Adds a release-definitions loader that fetches release rows from BQ and upserts them into release_definitions during the data load cycle.
  • Replaces the hardcoded releaseMetadata map in the postgres data provider with a live query against release_definitions.
  • Updates Server.getReleases to prefer PG and fall back to BQ when PG is empty or errors.
  • Seeds release definitions for the dev database (4.19–4.22) with relative GA dates and all capabilities.

Findings

Should fix DB error silently discarded when reading releaseConfigs
cmd/sippy/load.go:173

The blank identifier _ drops any error from GetReleasesFromDB. If the release_definitions table is missing (migration not applied), the DB is overloaded, or there is a schema mismatch, releaseConfigs stays an empty slice with no log, no warning, and no early exit. All downstream loaders that consume it — prowLoader, releaseloader.New, featuregateloader.New, the regression-cache loader, and ensurePartitionsForReleases — silently operate on an empty release list. The operator has no signal that the skip was due to an error rather than an intentional first-run empty state.

releaseConfigs := []sippyv1.Release{}
if dbErr == nil {
    releaseConfigs, _ = api.GetReleasesFromDB(context.Background(), dbc)
}

Fix: Log the error and either return early or propagate it so the operator knows why releases are absent.

Should fix seedReleaseDefinitions uses FirstOrCreate instead of upsert
cmd/sippy/seed_data.go:495

FirstOrCreate creates the row on the first seed run and silently does nothing thereafter. The sync loader (releasedefloader) correctly uses clause.OnConflict upsert. If a seed value changes — GA date offset, capabilities, product — re-seeding leaves stale data in the dev database with no error or warning. A developer adjusting, say, 4.21's gaDays and re-running seed will see "Seeded release definitions" in the log but no actual change in the DB.

if err := dbc.DB.Where("release = ?", release).FirstOrCreate(&def).Error; err != nil {
    return fmt.Errorf("failed to create release definition %s: %w", release, err)
}

Fix: Use the same clause.OnConflict upsert pattern the sync loader uses, or at minimum document that re-seeding requires manually dropping the rows first.

Nit GetReleaseRowsFromBigQuery duplicates GetReleasesFromBigQuery body
pkg/api/releases.go:501–527

The new function copies the query string, client call, iterator loop, and all error-handling verbatim. The only difference is omitting transformRelease. The existing function could call the new one and map transformRelease over the result. Any future change to the BQ query path (ordering, label, error log text) must otherwise land in both places or one copy silently drifts.

// existing GetReleasesFromBigQuery — same queryString, same loop
queryString := fmt.Sprintf("SELECT * FROM `%s` ORDER BY DevelStartDate DESC", client.ReleasesTable)
q := client.Query(ctx, bqlabel.ReleaseAllReleases, queryString)
// ... identical iterator pattern
Nit syncReleaseDefinitions is non-transactional
pkg/dataloader/releasedefloader/releasedefloader.go:60–73

Each upsert is a separate statement with no wrapping transaction. A mid-loop DB error leaves some rows updated and others not. This is recoverable on the next loader run, but during the window the table is inconsistent. Wrapping in a transaction gives atomic all-or-nothing semantics with no extra complexity.

for _, def := range defs {
    err := dbc.DB.Clauses(clause.OnConflict{...}).Create(&def).Error
    if err != nil {
        return fmt.Errorf("upserting release definition %s: %w", def.Release, err)
    }
}
Nit develStart for in-development releases is an arbitrary relative date
cmd/sippy/seed_data.go:479

develStart := now.AddDate(0, 0, m.gaDays-180) computes development start as now - 180 days when gaDays == 0 (e.g. 4.22). The value is semantically arbitrary and not tied to when development actually started. If FirstOrCreate is ever changed to upsert, this date will shift on each seed run. The comment documents gaDays: 0 = no GA but the effect on develStart is non-obvious.

develStart := now.AddDate(0, 0, m.gaDays-180)   // 4.22: now - 180 days
Question No log when PG returns empty without error and falls back to BQ
pkg/sippyserver/server.go:193–199

When GetReleasesFromDB returns (nil, nil) — empty table, no error — the code silently falls through to BQ. Only the error path emits a Warn. During first-boot or a post-wipe scenario an operator monitoring logs sees no indication the BQ fallback is active. Is this intentional? A log.Info("release_definitions empty, falling back to BigQuery") would make the bootstrapping path visible.

releases, err := api.GetReleasesFromDB(ctx, s.db)
if err == nil && len(releases) > 0 {
    return releases, nil
}
if err != nil {
    log.WithError(err).Warn("error querying releases from database, trying bigquery fallback")
}
// silent fallthrough to BQ when table is empty

Things I checked and was fine with

  • Staging verification covered all key endpoints (/api/releases, /api/releases/health, /api/component_readiness) with 36 real releases synced from BQ.
  • forceRefresh query parameter: the sippy-ng frontend does not reference it (grep returned empty), so dropping it from getReleases is safe.
  • QueryReleaseDates ignoring request options by design — PG derives dates from actual prow_job_runs min/max timestamps, not filtered by options. The _ parameter is intentional.
  • release-definitions correctly placed first in loaderOrder so downstream loaders can rely on an up-to-date table within a single run.
  • BQ fallback in getReleases is reachable when PG is up but the table is empty — the flow correctly falls through the err == nil && len > 0 guard to the BQ branch.
  • DefinitionToRelease uses map[ReleaseCapability]bool for capabilities — not a CLAUDE.md violation because this is the existing sippyv1.Release API type, not a hand-rolled set choice by this PR.
  • Migration: ReleaseDefinition added to modelsToMigrate slice before ReleaseTag, correct ordering.

Open questions for the author

  • Should GetReleasesFromDB return a sentinel error (or at least log) when the table exists but is empty, to distinguish "first run" from "DB problem"? Right now both cases look the same to callers.
  • The comment on the releaseConfigs read says "On the first run the table may be empty; the release-definitions loader will populate it for subsequent runs." But release-definitions is now first in the default loader list — so on the very first run, won't the loader populate the table before the prow/releases loaders consume releaseConfigs? If so, the comment and the empty-slice initialization may be unnecessary complexity (the table will always be populated by the time downstream loaders run).
