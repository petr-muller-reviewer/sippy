Verdict: Needs Discussion

The architecture is sound — nested LIST→RANGE partitioning with lifecycle management is the right call for this data scale. Two blocking issues remain: the down migration would destroy production data, and the test_analysis_by_job_by_dates partitioning strategy change is invisible to existing databases via golang-migrate. The migration ordering uncertainty (previously blocking) was resolved in 6ecf3771f.

What this PR does

  • Introduces PostgreSQL nested LIST→RANGE partitioning for prow_job_run_tests, prow_job_run_test_outputs, and test_analysis_by_job_by_dates via explicit SQL migration DDL, replacing GORM AutoMigrate management.
  • Adds partition lifecycle management (create/detach/drop) using the author's gopar library, integrated into both the data loader and the load command.
  • Updates ~20 queries across views, functions, and API handlers to filter on denormalized release/timestamp columns, enabling partition pruning and dropping unnecessary joins.
  • Sets plan_cache_mode = force_custom_plan and work_mem = 128MB globally to prevent 17-minute generic plan generation on tables with 10k+ partitions.
  • Adds comprehensive plan documentation (phases 2–4) and an e2e partition lifecycle test.

Since previous review (b80e1abd → 6ecf3771, 2 commits):

  • Resolved migration ordering uncertainty — comments replaced with clear forward-looking notes.
  • Added release filters to several queries (JobRunTestCount, QueryTestAnalysis, IsNewTest, JobsRunsReportFromDB ran_test subquery) for proper partition pruning.
  • Added work_mem = "128MB" global runtime parameter and increased load timeout from 4h to 14h.
  • Rewrote phase 4 plan doc to scope 4a (3 tables) vs 4b (remaining 3 tables).
  • Added ~491 lines of benchmark tests covering matviews, API endpoints, and single-release matview creation.

Findings

Blocking

Blocking Down migration drops production tables unconditionally

pkg/db/migrations/000001_create_partitioned_tables.down.sql:6-8

DROP TABLE IF EXISTS prow_job_run_tests CASCADE;
DROP TABLE IF EXISTS prow_job_run_test_outputs CASCADE;
DROP TABLE IF EXISTS test_analysis_by_job_by_dates CASCADE;

These are the production table names, not _new suffixed staging tables. A migration rollback permanently destroys all test result data. The down migration should either be a no-op with a comment explaining why rollback is unsupported, or it should only drop staging tables.

Blocking test_analysis_by_job_by_dates partitioning changed from RANGE to LIST in same migration version

pkg/db/migrations/000001_create_partitioned_tables.up.sql:87-98

CREATE TABLE IF NOT EXISTS test_analysis_by_job_by_dates (
    ...
) PARTITION BY LIST (release);

The old migration 000001 created this table as PARTITION BY RANGE (date). The replacement uses PARTITION BY LIST (release). On existing databases, golang-migrate sees version 1 as already applied and skips it — the table keeps its old RANGE schema but the code now creates LIST→RANGE partitions against it. Additionally, the inline partition-creation code in loadDailyTestAnalysisByJob that created date-based RANGE partitions was removed, so no new partitions will be created for the old schema either.

Resolved

Resolved Unresolved uncertainty about migration ordering

pkg/db/db.go:100-103

Should Fix

Should Fix gopar is a pre-release personal dependency by the PR author

go.mod:27

github.com/neisw/gopar v0.0.0-20260602170650-3755a6d55bbe

This pre-release library authored by the same person submitting the PR becomes a critical infrastructure dependency (partition lifecycle management). The code looks reasonable (proper SQL injection prevention), but it should have explicit team review/ownership. Consider moving it under the org or tagging a v0.1.0 release.

Should Fix force_custom_plan and work_mem applied globally to all connections

pkg/db/db.go:67-72

pgxConfig.RuntimeParams["plan_cache_mode"] = "force_custom_plan"
pgxConfig.RuntimeParams["work_mem"] = "128MB"

Both settings are applied to all connections. force_custom_plan prevents plan caching for any prepared statement. work_mem = "128MB" (added in 6ecf3771f) sets memory per sort/hash operation — with connection pooling, this could mean significant total memory usage. Consider documenting the measured trade-off or scoping if possible.

Should Fix TestOutputs query adds status filter — behavioral change beyond partitioning

pkg/db/query/test_queries.go:284

Where("prow_job_run_tests.status IN ?",
    []int{int(v1.TestStatusFailure), int(v1.TestStatusFlake)})

Previously all test outputs were returned regardless of status. This is a semantic change beyond the partitioning refactor. If intentional (outputs only exist for failures/flakes), it should be called out explicitly. If not, it silently filters data.

Should Fix TestOutputs join on prow_job_run_test_outputs missing release column

pkg/db/query/test_queries.go:279

Joins("JOIN prow_job_run_test_outputs ON
    prow_job_run_test_outputs.prow_job_run_test_id = prow_job_run_tests.id
    AND prow_job_run_test_outputs.prow_job_run_test_timestamp
        = prow_job_run_tests.prow_job_run_timestamp")

The join matches on id + timestamp but omits release. With both tables LIST-partitioned by release, cross-partition ID collisions are theoretically possible. The join should also include prow_job_run_test_outputs.prow_job_run_test_release = prow_job_run_tests.prow_job_run_release.
