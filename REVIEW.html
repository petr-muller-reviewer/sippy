Verdict: Needs discussion

Solid, well-tested rework — a clear improvement over the earlier WIP revision (cleaner TestDetailsSummary type, real end-to-end tests closing prior coverage gaps). One should-fix item carries over unresolved from the earlier review round: the aggregate fallback gate is all-or-nothing across a whole multi-test query batch, which could silently suppress the fallback for some tests when cache-priming a view. Worth a definitive answer from the author before merge; everything else is nit-level.

What this PR does

  • Replaces raw per-run TestJobRunRows with pre-aggregated crstatus.TestDetailsSummary (per job/test, with optional []JobRunDetail) as the return type from both providers.
  • Adds SummarizeTestJobRuns (new file crstatus/summarize.go) to group raw rows into summaries, applied identically by BigQuery and Postgres providers.
  • Adds a Postgres-only fallback (queryBaseAggregateTestDetails) that reads test_cumulative_summaries (prefix-sum, non-GA releases) or prow_ga_raw_test_data (GA releases) when the per-run query returns nothing for the base release — aggregate rows have no JobRuns, so the UI just omits run links.
  • Bumps the BQ Redis cache key V2→V3 (the cached type shape changed) and fixes TestKeyStr serialization so grouping survives the cache round-trip.
  • Simplifies test_details.go report generation via a new splitByTestKey helper, collapsing three near-identical map-building blocks into one.

Findings

Should fix All-or-nothing fallback gate for multi-test batches

pkg/api/componentreadiness/dataprovider/postgres/provider.go:233-249 (QueryBaseJobRunTestStatus)

The aggregate fallback triggers only when len(result) == 0 across the entire reqOptions.TestIDOptions batch. GenerateComponentTestDetailsReportMultiTest can call this with multiple test IDs at once (e.g. cache-priming a view). If even one test/job in the batch has per-run data, the fallback is skipped for every other test in the batch, silently leaving them at zero base stats. This was flagged against the prior WIP revision and still applies. Likely fine if a release's backfill is truly all-or-nothing, but that assumption isn't asserted or tested anywhere.

result, errs := p.queryTestDetails(...)
if len(errs) > 0 {
    return result, errs
}
if len(result) > 0 {
    return result, nil
}
log.WithField("release", reqOptions.BaseRelease.Name).
    Info("no per-run base test details found, falling back to aggregate tables")
return p.queryBaseAggregateTestDetails(ctx, reqOptions)

Nit processAggregateRows duplicates queryTestDetails row-processing logic

pkg/api/componentreadiness/dataprovider/postgres/provider.go:407-472 vs 196-228

Job-variant batch-fetch, RequestedVariants matching, filterByDBGroupBy, JiraComponentID conversion, and result-map assembly are copy-pasted nearly verbatim between the two functions. A shared helper would remove the duplication and prevent drift.

Nit New prefix-sum/GA query builders bypass existing shared query abstraction

pkg/api/componentreadiness/dataprovider/postgres/provider.go:321-405 vs cr_queries.go (testStatusSpec/queryTestStatus)

cr_queries.go already factors the prefix-sum-vs-GA split into a shared abstraction used elsewhere. buildAggregatePrefixSumQuery/buildAggregateGAQuery reimplement the same shape with hand-written SQL instead of reusing it, doubling the surface area a future schema change must touch.

Nit Unexplained nolint suppression

test/integration/component_readiness_test.go:1055

//nolint:unparam added to createGARawData with no comment on why the flagged parameter can't be removed; project convention favors explaining "why", not bare suppressions.

Nit TestDetailsSummary/JobRunDetail lack json tags, inconsistent with sibling type

pkg/apis/api/componentreport/crstatus/types.go:51-73

TestJobRunStatuses uses explicit snake_case json tags; the new structs have none (default Go field names) except JobRuns. Not a correctness issue — confirmed this type only round-trips through the internal Redis cache and never reaches the frontend directly — but cosmetically inconsistent.

Question Is Postgres-only fallback intentionally exempt from data-provider parity convention?

pkg/api/componentreadiness/dataprovider/bigquery/provider.go:88-127

BigQuery/Mixed providers only get the type-signature change, no aggregate-fallback logic. Presumably intentional since BQ retains full history, but the project convention calls for provider parity on data-provider changes — worth confirming this asymmetry is deliberate and permanent.

Things I checked and was fine with

  • gofmt clean; sets.New[uint]() used instead of hand-rolled map[uint]bool per project convention.
  • SummarizeTestJobRuns accumulates raw counts with AddTestCount(row.Count, false) (policy-independent), and callers recompute SuccessRate via Stats.Add(summary.Stats, faf) with the real FlakeAsFailure setting — verified this doesn't reintroduce a double-aggregation bug.
  • No SQL injection risk: all query args go through gorm ? placeholders, including IN (?) slice expansion.
  • Explanations: []string{} replacing the old conditional "base details not available" message is correct — other middleware still appends its own explanations independently; nothing else relied on the removed message.
  • New end-to-end integration tests (TestTestDetailsReport_AggregateBaseStats, TestTestDetailsReport_LastFailureTracking, TestTestDetailsReport_FlakeAsFailure) exercise the full pipeline with aggregate-only base data — closes the "no end-to-end coverage" gap from the prior WIP-revision review.
  • TestQueryBaseJobRunTestStatus_AggregateFallback covers prefix-sum, GA, precedence-over-per-run, variant filtering, multi-job, zero-delta HAVING exclusion, and no-suite ownership.

Open questions for the author

  • Can a base release realistically have partial per-run backfill within the same request batch (some jobs/tests present in prow_job_run_tests, others not), or is per-release backfill always all-or-nothing? This determines whether the fallback-gate finding above is a real bug.
  • Is a BigQuery-side equivalent of this fallback planned, or is this permanently Postgres-only by design?
