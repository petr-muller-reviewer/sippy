Verdict: Approve

Well-structured integration of partition management. The vendor patch is thoroughly documented, error handling degrades gracefully, and the security-sensitive DDL construction in sippy-owned code properly validates inputs. The findings below are nits and questions, none blocking.

What this PR does

  • Wraps the go_partman library in pkg/db/partitionmanager/, bridging GORM to go_partman's sqlx-based API.
  • Integrates into the load path: calls Maintain() for forward-looking partitions, then EnsurePartition() per historical date being imported.
  • Integrates into the serve path: starts a background goroutine running Maintain() on a 1-hour ticker.
  • Patches vendored go_partman to handle non-multi-tenant tables (inserts a default empty-string tenant row).
  • Adds E2E tests covering partition creation, idempotency, data routing, retention-based cleanup, and SQL injection rejection.

Findings

nit dropPartition in go_partman uses unquoted identifiers

vendor/github.com/jirevwe/go_partman/queries.go:105

DROP TABLE IF EXISTS %s.%s; interpolates schema and table name without quoting. Values come from pg_tables (database-controlled, not user-controlled), so this is not exploitable in practice. But it diverges from sippy's own EnsurePartition which properly quotes identifiers. Worth noting in the vendor patch doc or as an upstream issue.

var dropPartition = `DROP TABLE IF EXISTS %s.%s;`

nit Maintain() + EnsurePartition() dual strategy lacks comment

pkg/dataloader/prowloader/prow.go:379-406

Maintain() creates future partitions and drops expired ones; EnsurePartition() then handles the specific historical date being imported. This two-tier approach is correct but non-obvious. A brief comment at line 379 explaining why both calls are needed would help future readers understand the forward-looking vs. historical-backfill distinction.

if pl.partMgr != nil {
    if err := pl.partMgr.Maintain(ctx); err != nil {
        log.WithError(err).Warn("partition manager maintenance failed, will create partitions on demand")
    }
}
// ... later, per date:
if err := partitionmanager.EnsurePartition(pl.dbc.DB, "test_analysis_by_job_by_dates", dateToImport, nextDay); err != nil {

question context.Background() in serve.go partition manager startup

cmd/sippy/serve.go:261

Creates a new context.Background() rather than deriving from the command's context. If the cobra command has signal-handling context, the partition manager won't respond to graceful shutdown signals through context cancellation — only via defer partMgr.Stop(). This may be intentional (Stop() is the primary shutdown mechanism) but worth confirming.

ctx, cancel := context.WithCancel(context.Background())
defer cancel()
if startErr := partMgr.Start(ctx); startErr != nil {

question 365-day retention default

pkg/db/partitionmanager/manager.go:36

RetentionPeriod: 365 * 24 * time.Hour — is this aligned with the existing data lifecycle for test_analysis_by_job_by_dates? If no prior pruning policy existed, 365 days is reasonable, but should be confirmed against actual usage patterns.

Things I checked and was fine with

  • EnsurePartition validates table names via validIdentifier regex and dates via time.Parse before DDL string interpolation — safe against SQL injection.
  • Vendor patch doc (SIPPY_VENDOR_PATCHES.md) thoroughly documents the empty-string tenant fix with a guard-condition analysis across all go_partman code paths.
  • Graceful degradation: partition manager failures are logged as warnings, never fatal, in both load and serve paths.
  • E2E tests cover create, idempotent re-create, data routing through parent table, retention-based drop, invalid table name rejection (robert'; DROP TABLE students;--), and invalid date rejection.
  • dropPartmanState cleanup in tests properly records errors via t.Logf instead of silently ignoring them (latest commit).
  • Embedded web assets placeholder resolves the //go:embed web/dist build failure without pulling in unused UI code.
  • The logrusLogger bridge correctly implements all methods of go_partman's Logger interface.

Open questions for the author

  • Is context.Background() in serve.go:261 intentional, or should the partition manager derive its context from the cobra command's context for signal-aware shutdown?
  • Does the 365-day retention period match the expected data lifecycle? Is there an existing pruning policy this should align with?
