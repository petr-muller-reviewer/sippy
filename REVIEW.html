Verdict

APPROVE

The core design (in-memory TaskStore with copy-on-read semantics, panic recovery, TTL + stuck-task cleanup, bounded concurrency) is sound and already went through visible self-hardening in the commit history. Remaining gaps are minor: missing handler-level tests, a small frontend UX/timeout mismatch, and one dead ref. None block merge.

What this PR does

  • Converts POST /api/jobs/runs/reevaluate to async-by-default: creates a task, launches a background goroutine, returns 202 with a task ID and HATEOAS polling link.
  • Adds GET /api/jobs/runs/reevaluate/{task_id} to poll status, progress, and (partial or final) results.
  • Preserves the old synchronous behavior via ?sync=true (50-run cap); async cap raised to 500.
  • New thread-safe TaskStore with TTL cleanup, concurrency semaphore (MaxConcurrentTasks = 5), panic recovery, and graceful shutdown.
  • Rewrites the React ReEvaluateSymptoms.jsx component to submit the whole batch once and poll every 2s, replacing the old client-side concurrency-limited per-ID request pool.

Findings

should-fix

No handler-level tests

pkg/sippyserver/job_run_scan.go — jsonReEvaluateJobRunSymptoms, jsonGetReEvaluationTask

TaskStore and ValidateReEvalRequest are well unit-tested, but the actual HTTP surface — 202/400/429/503 on POST, 200/404 on GET, HATEOAS link injection, sync-vs-async branching — has no test coverage. This is the contract clients actually depend on.

nit

Dead ref in frontend

sippy-ng/src/jobs/ReEvaluateSymptoms.jsx:106,222

const taskIDRef = useRef(null)
...
taskIDRef.current = taskID
pollingActiveRef.current = true

taskIDRef.current is set in startPolling but never read anywhere else. Either it was meant to back a guard that got dropped, or it's leftover and can be removed.

nit

Frontend poll timeout shorter than backend task timeout

ReEvaluateSymptoms.jsx (MAX_POLL_COUNT=300, POLL_INTERVAL_MS=2000) vs job_run_scan.go (context.WithTimeout(..., 30*time.Minute))

The frontend gives up polling after ~10 minutes and shows a "timed out" error, while the server keeps processing for up to 30 minutes. For a large async batch (up to the new 500-run cap) that legitimately runs past 10 minutes, the UI reports failure while the task actually completes server-side, unobserved. Not a correctness bug, but a UX/tuning mismatch worth aligning.

question

Retry can create orphaned duplicate tasks

ReEvaluateSymptoms.jsx — handleReEvaluate retry loop

Retries only trigger on TypeError (network-level failures). But if the POST succeeds server-side (202, task created) and the client merely fails to read/parse the response body — e.g. a connection drop right after headers — that also surfaces as a TypeError, and the retry resubmits the same batch, creating a second orphaned task. It self-expires via TTL so impact is low — is this an accepted tradeoff?

question

Global concurrency cap vs. new 500-run async ceiling

pkg/api/jobrunscan/reevaluate.go — MaxConcurrentTasks = 5

The cap is process-wide across all users, and each task processes buildIDs sequentially in a single goroutine. With the async cap raised to 500 runs/request, is 5 concurrent tasks system-wide sized correctly for expected usage, or could legitimate concurrent submissions from multiple users routinely hit 429?

Things I checked and was fine with

  • go build -mod=vendor ./pkg/... and go vet on the touched packages — clean.
  • go test ./pkg/api/jobrunscan/..., including -race on TestTaskStoreConcurrentAccess — all pass.
  • TaskStore.Get() returns a full deep copy (including the CompletedAt pointer and Links map) — no shared-memory races with callers; backed by dedicated tests.
  • Create() returns an immutable TaskCreated snapshot rather than a pointer into the map; the handler builds the 202 response from this before launching the goroutine, avoiding a data race.
  • Panic recovery, idempotent Stop() via sync.Once, and stuck-task cleanup keyed on CreatedAt (not just CompletedAt) are present and tested — this addresses the goroutine-leak/panic risk inherent to a fire-and-forget background task pattern.
  • google/uuid was already an indirect dependency in go.mod/vendor prior to this PR — no new third-party dependency risk.
  • Capability gating is consistent with existing conventions: POST keeps WriteEndpointsCapability, GET is read-only under LocalDBCapability.
  • Documentation (pkg/api/README.md, docs/features/job-analysis-symptoms.md) was updated in the same PR, per project convention.

Open questions for the author

  • Is the 10-minute frontend poll ceiling intentional, or should it be raised (or made configurable) to match the 30-minute backend task timeout for large batches?
  • Is MaxConcurrentTasks = 5 based on a specific resource budget (memory, BigQuery/GCS rate limits), or a placeholder to revisit once there's real usage data?
  • Any plan to add handler-level (httptest-based) tests for the new POST/GET endpoints before or shortly after merge?
