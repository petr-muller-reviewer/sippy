What this PR does

  • Creates a release_definitions PostgreSQL table to store release metadata (GA dates, development start dates, capabilities, previous-release chain, product, status) previously only available from BigQuery.
  • Adds a ReleaseDefinitionLoader that fetches release rows from BQ and upserts them into PG during load cycles.
  • Migrates all release-data consumers (API endpoints, component readiness, metrics, triage, Jira automation, MCP tools) from v1.Release to models.ReleaseDefinition, reading from PostgreSQL instead of BigQuery.
  • Removes QueryReleases and QueryReleaseDates from the DataProvider interface, and deletes the hardcoded releaseMetadata map from the Postgres provider.
  • Adds seed data for release definitions so the dev/test environment works without a BQ connection.

Since previous review:

  • Partition creation block moved from after loaders back to before loaders, reusing the initial releaseDefs read (eliminates the second GetReleasesFromDB call).
  • seed_data.go now uses capability constants (models.CapComponentReadiness, etc.) instead of string literals.
  • loaderwithmetrics.go adds release-definitions to the loaderOrder list so it runs first.

Findings

Blocking

Blocking ReleaseFallback middleware created with potentially nil dbc, causing panic

pkg/api/componentreadiness/component_report.go:280-281

initializeMiddleware() passes c.dbc to NewReleaseFallbackMiddleware unconditionally, but c.dbc can be nil. The nil guard at line 283 for the regressiontracker middleware proves this is a real case. When ReleaseFallback.QueryTestDetails or getFallbackBaseQueryStatus runs, it calls GetReleaseDatesFromDB(ctx, r.dbc, ...) which dereferences dbc.DB.WithContext(ctx) and panics.

The test at releasefallback_test.go:167 passes nil for dbc but only exercises PreAnalysis, which does not touch dbc, so the panic path is untested.

if c.ReqOptions.AdvancedOption.IncludeMultiReleaseAnalysis && c.ReqOptions.SampleRelease.PullRequestOptions == nil {

Open questions for the author

  • Is the first-run no-op by design? If so, should the load command log a clear message ("no release definitions found, first load will be partial, re-run to load all data") rather than silently proceeding?
  • The old Postgres provider's QueryReleaseDates derived time ranges from actual prow_job_runs data (MIN/MAX timestamps). The new GetReleaseDatesFromDB uses only GA dates. For BigQuery users this is identical behavior, but for Postgres-only users who relied on data-derived ranges, is this intentional?
  • Moving partition creation before loaders means it no longer benefits from the release-definitions loader having populated the table. Was this intentional, or should partition creation remain after loaders?
