Verdict: Approve. Small, clean, additive change that follows existing patterns. No correctness issues found.

What this PR does

  • Adds two new fields to the Job struct: CurrentAverageDurationMinutes and PreviousAverageDurationMinutes (both int).
  • Extends the job_results PostgreSQL function to compute average job run duration (in minutes) for both the current and previous time windows, using AVG() with CASE WHEN timestamp filters.
  • Converts nanosecond-stored durations to minutes by dividing by 60e9.
  • Registers both fields in GetNumericalValue so they can be queried as numerical parameters.

Findings

No findings. Nothing survived verification.

Things I checked and was fine with

  • AVG correctness with LEFT JOIN to bug_jobs: The join is on prow_jobs.id, so all runs of a given job are multiplied by the same factor (number of bug associations). This preserves AVG correctness, unlike a join that would multiply runs unevenly.
  • Nanosecond-to-minutes divisor: 60000000000.0 = 60e9 ns = 1 minute. Correct for Go's time.Duration (int64 nanoseconds).
  • coalesce(..., 0) for NULL averages: Consistent with all other aggregates in the same query. The Go field is int (not *int), so NULL would map to 0 regardless.
  • RETURNS TABLE signature and outer SELECT: Both updated to include the two new columns.
  • Cross-file impact: GORM scans by struct tag name, not column position. No explicit column enumeration elsewhere that would break.
  • BigQuery parity: job_results is a PostgreSQL-only aggregation function with no BigQuery equivalent. The CLAUDE.md parity rule does not apply here.
  • GetNumericalValue: Both new param names added, converting int to float64 correctly.
  • JSON tags: Match SQL column names exactly.

Open questions for the author

  • The fields use int (not *int), so jobs with zero runs in a period show 0 minutes rather than null in JSON. This is consistent with how other zero-value fields behave in this struct, but worth confirming you're comfortable with that for duration specifically: 0 minutes is a meaningful value (a very fast job), unlike 0 passes which unambiguously means "no data."
