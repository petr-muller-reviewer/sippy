Verdict

Approve

This is a small, well-targeted, well-evidenced fix for an active production timeout. The partition-pruning reasoning is correct, and I independently verified the two assumptions it depends on (that prow_job_run_release matches ReleaseTag.Release semantics, and that prow_job_run_timestamp and prow_job_runs.timestamp are the same denormalized value) directly against the schema and dataloader code. No blocking issues; two minor notes below aren't worth holding the PR for.

What this PR does

  • Fixes a query timeout in /api/payloads/test_failures caused by GetTestFailuresForPayload and the payloadTestFailuresMatView joining prow_job_run_tests (~3,500 LIST/RANGE partitions) with no filter on the partition keys.
  • Adds release and releaseTime parameters to GetTestFailuresForPayload, sourced from the already-loaded ReleaseTag, and uses them as bind params: an equality filter on prow_job_run_release and a >= lower bound on prow_job_run_timestamp.
  • Adds equivalent join predicates (pjrt.prow_job_run_release = rt.release and pjrt.prow_job_run_timestamp = pjr.timestamp) to the matview definition so the planner can prune during refresh too.
  • Single call-site update in pkg/api/releases.go; no other functional changes.
  • PR description documents staging benchmarks: planning >60s→~6ms, execution >90s→~115ms, partitions scanned ~3,500→2-5, plus row-count parity verification.

Things I checked and was fine with

  • prow_job_run_tests.prow_job_run_release is populated from ProwJob.Release (pkg/dataloader/prowloader/prow.go:1116), matching ReleaseTag.Release string semantics (e.g. "4.15") — the new equality bind compares like-for-like values.
  • prow_job_run_tests.prow_job_run_timestamp and prow_job_runs.timestamp are both set from the same source value at insert time (pj.Status.StartTime) — the matview's new equality join (pjrt.prow_job_run_timestamp = pjr.timestamp) is a correctness-neutral pruning hint, not a lossy filter.
  • Partition scheme confirmed in pkg/db/migrations/000001_create_partitioned_tables.up.sql: LIST by prow_job_run_release → RANGE by prow_job_run_timestamp, matching the stated pruning strategy.
  • The >= (not bounded both sides) filter on releaseTime is intentional and reasonable: job runs against a payload only occur at or after its release_time, and failures should remain visible indefinitely (no natural upper bound to add).
  • No BigQuery equivalent of this matview/query exists, so the project's data-provider-parity convention doesn't apply here.
  • Single call site updated correctly; no other callers of GetTestFailuresForPayload exist in the repo.
  • No injection risk: new params come from an already-fetched trusted ReleaseTag row and are passed as bind params, not interpolated into SQL text.
