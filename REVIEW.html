Needs Discussion — The design is sound and the middleware refactoring is well-executed. Two issues need resolution before merge: a casing mismatch between variant registry and BQ fallback SQL that can create duplicate groups during transition, and a SpotCheckSample fallback that causes every CR report (across all 61 views) to run a spot-check BQ query even when the view doesn't configure spot-check analysis. Neither is hard to fix, but both affect correctness or cost.

What this PR does

  • Introduces spot-check jobs to Component Readiness: rarely-run CI jobs (cpu-partitioning, etcd-scaling) evaluated on a simple "did the job pass at least once in 30 days" heuristic, rather than per-test-case Fisher's Exact analysis.
  • Adds SpotCheckComponent and SpotCheckCapability variant classification, a new spotcheck job tier (replacing rare), and BigQuery queries to fetch job-level pass/fail data.
  • Implements a spotcheckjobs middleware that injects synthetic test results into the component report and claims analysis for spot-check tests.
  • Refactors the analysis pipeline: extracts assessComponentStatus into three middleware packages (NewTestPassRate, AllTestsPassRate, FisherExact) using a first-responder-wins Analyze method on the middleware interface.
  • Frontend conditionally hides basis-related columns and stats for spot-check tests.

Findings

Should Fix

should fix Component name casing mismatch between variant registry and BQ fallback

pkg/variantregistry/ocp.go:768 vs pkg/api/componentreadiness/dataprovider/bigquery/provider.go:385

The variant setter uses "Node / kubelet" but the BigQuery COALESCE fallback produces 'Node / Kubelet'. During the transition period when both paths can fire for the same job, COALESCE prefers the variant value (lowercase k), so groups with variants populated will have a different component string than groups without. This can create duplicate rows in the CR grid or cause drill-down queries to miss results.

// ocp.go:768
{[]string{"-cpu-partitioning"}, "Node / kubelet", "CPU Partitioning"},

// provider.go:385  (BQ fallback)
WHEN LOWER(jobs.prowjob_job_name) LIKE '%%cpu-partitioning%%' THEN 'Node / Kubelet'

Pick one casing and use it in both places. Verify which is the correct OCPBUGS component name.

should fix SpotCheckSample always-on fallback causes unnecessary BQ queries

pkg/api/componentreadiness/utils/queryparamparser.go:227-235

When no view provides SpotCheckSample, the parser defaults it from the sample release dates. This means SpotCheckJobs middleware is instantiated and runs a BigQuery query on every component report request for all 61 views, not just the one with spot_check_sample configured. The middleware's Analyze correctly skips non-spot-check tests, but the BQ query cost is incurred unconditionally.

// queryparamparser.go:227-235
if opts.SpotCheckSample == nil && !opts.SampleRelease.Start.IsZero() &&
    !opts.SampleRelease.End.IsZero() {
    opts.SpotCheckSample = &reqopts.Release{
        Name:  opts.SampleRelease.Name,
        Start: opts.SampleRelease.Start,
        End:   opts.SampleRelease.End,
    }
}

Consider limiting the fallback to test details drill-down requests that target a spotcheck: test ID, or document why the always-on behavior is intentional.

Questions

question Postgres provider silently returns empty

pkg/api/componentreadiness/dataprovider/postgres/provider.go:799-814

Both spot-check methods return nil, nil — no error, no results, no log. If someone runs Component Readiness against Postgres with a spot-check-enabled view, spot-check tests will silently not appear. A log.Warn or a comment explaining "BigQuery-only, intentionally no-op" would help future debugging.

question Only 5.0-main view has spot_check_sample

config/views.yaml:12-14

Only 1 of 61 views has spot_check_sample configured. Is this intentional for initial rollout? The snapshot.yaml changes show spot-check variants assigned to jobs from 4.12 through 4.22, suggesting the feature could apply to other release views too.

Things I checked and was fine with

  • Analysis refactoring preserves behavioral equivalence. The three new analysis middleware (NewTestPassRate → AllTestsPassRate → FisherExact) reproduce the exact control flow of the old assessComponentStatus — confidence initialization, MinimumFailure early return, pity factor, MissingBasis override all preserved.
  • Middleware ordering is correct. Synthetic injection (SpotCheckJobs) → data adjustment (ReleaseFallback, RegressionTracker, RegressionAllowances) → analysis (NewTestPassRate, AllTestsPassRate, FisherExact) → decoration (LinkInjector).
  • Analyze first-responder-wins semantics in List.Analyze correctly short-circuits on first handled=true.
  • SpotCheckJobs.Analyze status ladder covers all cases: 0 runs, 1 failure (pending retry), 2 failures (significant), 3+ failures (extreme), any passes (not significant).
  • BQ queries use parameterized values for user-controlled inputs; variant names go through param.Cleanse consistent with existing patterns.
  • BQ transition strategy (IN ('spotcheck', 'rare') + COALESCE fallback) is sound.
  • validateSpotCheckVariants prevents adding spotcheck tier without component/capability.
  • Frontend changes are minimal: isSpotCheck conditional hides basis columns/stats without restructuring components. Null-safe since === 'spot_check' is false for undefined.
  • Test coverage is solid. Unit tests for each new middleware, spot-check analyze logic, variant matching, query filtering.
  • assessComponentStatus fully removed from both component_report.go and test_details.go.
  • Regression tracking works with spot-check tests because RegressionTracker.PostAnalysis only checks ReportStatus value, not basis data.

Open questions for the author

  • Is the always-on SpotCheckSample fallback (queryparamparser.go:227-235) intentional? It means every CR report request for every view runs a spot-check BQ query, even when the view has no spot_check_sample configured.
  • Should other release views beyond 5.0-main also get spot_check_sample configured?
  • Is "Node / kubelet" the correct OCPBUGS component name? The casing is unusual (lowercase k) and doesn't match the BQ fallback ("Node / Kubelet").
