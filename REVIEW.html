PR #3409: Cache Risk Analysis responses

Overview

Adds matview-aware Redis caching for test query results used by both Risk Analysis and the classic Sippy test API. Cache entries are invalidated when the underlying materialized view is refreshed, rather than relying solely on TTL expiration.

Three-step approach:

  1. Record matview refresh timestamps in Redis after each refresh completes
  2. Store cached results wrapped with a timestamp
  3. On cache hit, compare timestamps to decide freshness

Also removes the dead /api/canary endpoint and the HTTP-level CacheTime on /api/tests (replaced by the new application-level cache).

Issues

logrus.Fatalf on Redis connection refused

pkg/api/cache.go:213

} else if strings.Contains(err.Error(), "connection refused") {
    logrus.WithError(err).Fatalf("redis URL specified but got connection refused; exiting due to cost issues in this configuration")
}

This kills the entire process on a transient Redis connection failure during a single cache lookup. The comment says "cost issues" but this is a very aggressive response to what could be a momentary network blip. A Fatal in a cache helper called from HTTP request handlers is surprising and could cause an outage from a brief Redis hiccup.

At minimum this deserves a clearer comment explaining the rationale. Better: a more targeted response (circuit breaker, or only fatal during startup probing).

Wrong log message in BigQuery path

pkg/api/tests.go, in buildTestsResultsFromBigQuery (diff line 824)

}).Debug("buildTestsResultsFromPostgres completed")

This is inside buildTestsResultsFromBigQuery but the log message says "Postgres". Copy-paste bug from the rename. Should say "buildTestsResultsFromBigQuery completed".

context.TODO() instead of real context

pkg/api/tests.go, in buildTestsResultsFromPostgres (diff line 731)

result, errs := GetDataFromCacheOrMatview(context.TODO(), cacheClient, ...

The calling chain has a context.Context available (from the HTTP request in PrintTestsJSONFromDB, or from variantsTestResultFunc). Passing context.TODO() means cache operations won't respect request cancellation. Consider threading the context through TestResultsSpec or as a parameter.

Observations

Thorough test coverage

Tests for GetDataFromCacheOrMatview cover: nil cache, miss, hit with/without refresh timestamp, invalidation after refresh, exact timestamp boundary, error result skipping, invalid refresh timestamp, different matviews invalidated independently, and cache duration propagation.

Graceful degradation

When the matview refresh timestamp is missing from Redis, cached data is used until normal TTL expiry. When cacheClient is nil, the code falls through to direct DB queries. Good resilience design.

Cleanup

Dead code removal (PrintCanaryTestsFromDB, /api/canary route) and replacing the HTTP-level CacheTime with proper application-level caching are welcome improvements. Confirmed no other callers exist for the removed code.

Verdict

Good PR. The matview-aware invalidation is a practical approach that avoids both stale data and unnecessary cache misses. The Fatalf on connection refused is the main concern worth discussing before merge. The BQ log message typo and context.TODO() are minor fixes.
