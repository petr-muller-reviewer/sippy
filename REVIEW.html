Verdict

Approve.

Clean, config-only change to view definitions. Renames are consistent across all four release versions, new shell views are structurally correct, and regression tracking is enabled uniformly on all MPIIT-owned views. No code logic is touched.

What this PR does

  • Renames *-LP-Interop views to *-LP-OCP-Compat across releases 5.0, 4.22, 4.21, and 4.20 — filters and product lists unchanged, only the view name changes.
  • Adds two new 5.0-only shell views (5.0-LP-Interop, 5.0-LP-Chaos) with empty LayeredProduct: [] lists, intended for incremental component onboarding.
  • Enables regression_tracking on all MPIIT-owned LP views (both the renamed LP-OCP-Compat views and the two new shell views).
  • Three well-separated commits: rename first, then add new views, then enable tracking.

Findings

Nit — Name reuse may confuse git history

config/views.yaml:617

The new 5.0-LP-Interop (empty product list, onboarding shell) reuses the exact name that the old view had before it was renamed to 5.0-LP-OCP-Compat. Anyone doing git log -S "5.0-LP-Interop" will find this view's history interleaved with the old one, making it harder to trace intent. Not blocking since the PR description documents this clearly, but a distinct name (e.g. 5.0-LP-Interop-Onboarding) would make the history cleaner.

Question — Identical new views

config/views.yaml:617-708

5.0-LP-Interop and 5.0-LP-Chaos are byte-for-byte identical (same base/sample releases, same variant options, same advanced options, same empty product list). Is the expectation that they'll diverge soon with different LayeredProduct entries? If they're meant to track the same set of products, one view would suffice.

Things I checked and was fine with

  • All four release versions (5.0, 4.22, 4.21, 4.20) renamed consistently from LP-Interop to LP-OCP-Compat.
  • No stale LP-Interop references in Go code, JS/TS, JSON, or documentation files.
  • The renamed 5.0-LP-OCP-Compat retains its original LayeredProduct list intact — rename is name-only.
  • New shell views structurally match the existing pattern (same column_group_by, db_group_by, advanced_options fields).
  • regression_tracking: enabled: true set uniformly on all six affected views.
  • New views are 5.0-only — no 4.x counterparts, consistent with the "5.0 only" scope described in the PR.
  • Adjacent views (5.0-lp-Interop-coo, etc.) are not touched and remain unaffected.

Open questions for the author

  • Is the name reuse of 5.0-LP-Interop intentional, or would a distinct name (e.g. 5.0-LP-Interop-Onboarding) be preferable to avoid confusion in git history?
  • Will 5.0-LP-Interop and 5.0-LP-Chaos receive different LayeredProduct entries soon, or might they stay identical for an extended period?
