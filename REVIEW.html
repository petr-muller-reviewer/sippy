Approve

The original blocking concern (grouped CASE-WHEN prefix-sum losing the self-join's per-key start/end pairing) was verified against both cumulative-summary write paths and does not hold in practice: every key, once created, persists (flat if inactive) on every later date, so the row shape it assumed can't occur. All duplication findings the author chose to address are resolved, and every CodeRabbit finding was fixed or explained to CodeRabbit's satisfaction (final state: APPROVED). Two should-fix duplication/maintainability items remain open but are not correctness blockers.

What this PR does

  • Introduces queryCombinedTestStatus, which folds the sample and base test-status queries into a single SQL statement using two materialized CTEs (sample_agg, base_agg) joined via UNION ALL, instead of running them as two separate queries.
  • Goal: eliminate concurrent partition scans / buffer cache contention from running sample and base queries in parallel against the same tables.
  • Rewrites the prefix-sum base-status query (prefixSumSpec) from a self-join pairing each key's start/end row to a grouped SUM(CASE WHEN date = end ...) - SUM(CASE WHEN date = start ...) aggregation.
  • Refactors join/filter construction (prepareVariantQuery, buildInnerAggregation, buildStatusCTE).

Since original review:

  • Author extracted the previously-duplicated prow_jobs join and variant-filter/lookup construction into shared helpers (prowJobVariantJoin, resolveVariantFilter in variants.go).
  • Author replaced an untyped bind-parameter source tag in the combined query's UNION branches with typed literals, fixing a CodeRabbit-flagged potential Postgres type-inference error and incidentally shrinking the hand-synced arg list.
  • Per-request Info-level logs in the combined query path were lowered to Debug.

Resolved

Verified: not a bug prefixSumSpec GROUP BY drops prow_job_id/lifecycle, corrupting totals when a key vanishes across the window
pkg/api/componentreadiness/dataprovider/postgres/cr_queries.go:137 (GROUP BY), cr_queries.go:255- (prefixSumSpec CASE-WHEN)

Original concern: buildInnerAggregation's GROUP BY (test_id, suite_id, variant_group_id — no prow_job_id/lifecycle) is shared by prefixSumSpec, which computes SUM(end) - SUM(start) across the whole group. The prior self-join paired each (test_id, prow_job_id, suite_id, lifecycle) key's own start/end rows before subtracting. Worry: a key present only at lookupStart (e.g. reclassified to a new lifecycle key) would still contribute its full start-of-window value to the group sum with nothing at lookupEnd to offset it.

Worked example (as originally filed; premise since shown false — see verification): a test's lifecycle reclassifies from blocking to informing mid-window. Old key: prefix_sum_runs=500 at lookupStart, assumed no row at lookupEnd. New key: prefix_sum_runs=50 at lookupEnd only.
Old (self-join) result: 50 - 0 = 50 — correct.
Grouped CASE-WHEN result under the assumed (incorrect) row shape: SUM(end)=50, SUM(start)=500 → total_count = 50 - 500 = -450.
Author response

mstaeble, 2026-08-19: The self-join and the grouped CASE-WHEN only diverge when a key has a lookupStart row but no lookupEnd row. That state can't arise from the cumulative-summary loader: any key present on a given date is carried forward to every later date. More fundamentally, prefix sums are monotonic by definition, so a key present at start but absent at end is a data-consistency violation, not an input the read path should paper over. Handling it in the query would just mask a loader/data bug.

Verified 2026-08-19T16:35:12Z

Read both write paths end-to-end. The author is correct.

1. pkg/db/cumulativesummary/cumulative_summary.go (batch Backfill path): insertSQL (lines 77-99) rebuilds each day from a FULL OUTER JOIN of yesterday's row (prev) and today's daily totals (tds) on the full key. When a key exists in prev with no matching tds row today (the reclassification case), the join still emits a row via COALESCE(prev.*, tds.*) — carrying every prev field forward unchanged. The old key is never dropped; it persists flat forever. The comment above deleteSQL ("rows whose daily-total key changed ... are dropped instead of persisting forever") does not match what the SQL does.

2. pkg/dataloader/prowloader/pgwriter/pgwriter.go (incremental path that drives production ingestion): ensureCumulativeSummaryRows (line 527) creates a zero-baseline row for any key seen in the batch on-or-before the day being processed; updateCumulativeSummaries (line 550) adds that batch's deltas. Both run once per day for every day from the batch's earliest date through "tomorrow", so an inactive key still gets ensured+updated (flat) every subsequent day. CarryForwardCumulativeSummaries/carryForwardRelease (lines 586-624) separately copies the previous day's full row set verbatim into any full gap day, for every existing key.

Net effect: once a key has a row on any date, it has a row (flat if inactive) on every later date, under both write paths. The row shape this finding assumed is not reachable from either write path during normal operation.

Residual caveat, not blocking: a full historical re-run of Backfill after retroactively relabeling test_daily_totals lifecycle values across history (a data-correction operation, not routine ingestion) could in principle produce a gap if processed sequentially from the relabel point — worth a comment in the loader if ever exercised, not a reason to hold this PR.

Resolution: downgraded from blocking to a documentation note; no SQL change made or required. Worth fixing the misleading deleteSQL comment at cumulative_summary.go:74 separately (unrelated to this PR).
